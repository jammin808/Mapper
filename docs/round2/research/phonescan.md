## 2. Phones as cameras from the browser (2026)

### 2.1 Secure context and camera access

| Fact | Evidence |
|---|---|
| A page served over **plain HTTP from a LAN address** is not a secure context: `navigator.mediaDevices` is `undefined` and `navigator.serviceWorker` is absent | Bench `out_http.json`: `isSecureContext:false, mediaDevices:false`. **V** (measured) |
| The same page over **HTTPS with a self-signed certificate whose error is bypassed** is a secure context: `getUserMedia`, `ImageCapture`, `MediaStreamTrackProcessor`, `VideoEncoder`, `navigator.gpu` and `navigator.xr` are all present | Bench `out_https_*.json`: `isSecureContext:true`. **V** (measured with Playwright's `ignoreHTTPSErrors`, which stands in for a person tapping "Proceed"; behaviour after a real interstitial click-through on a phone is **U** and needs the R0.5 lab) |
| **Service-worker registration fails** on a page whose certificate is not trusted: `SecurityError … An SSL certificate error occurred when fetching the script` | Bench, both HTTPS runs. **V**. So a self-signed node gets no offline cache, but installation does not need a service worker (§2.8) |
| `localhost` / `127.0.0.1` are secure contexts over plain HTTP. On Android, `adb reverse tcp:P tcp:P` makes the node appear at `http://localhost:P` on the phone | MDN install guide: PWAs are installable "from a local development environment using localhost or 127.0.0.1". **V**. The `adb reverse` behaviour is standard Android tooling, **U** here (no device) |
| **Local Network Access** (Chrome 142, desktop and Android): a "local network request" is "any request from a public website to a local IP address or loopback, or from a local website (for example, intranet) to loopback". It needs a permission prompt and a secure context. WebSockets and WebTransport were to be "expanded" later. Android WebView grants it unconditionally | [chromestatus](https://cr-status.appspot.com/feature/5152728072060928) and the [Chrome blog](https://developer.chrome.com/blog/local-network-access) (9 Jun 2025, updated 29 Sep 2025). **V**. Consequence: **a page served by the node itself, talking only to its own origin, is not a local-network request**. A cloud-hosted page that talks to a LAN node now meets a prompt and mixed-content rules |

**Chrome Android details that matter for structured light** (from `VideoCaptureCamera2.java`, main, **V**):

- `exposureMode: "manual"` maps to `CONTROL_AE_MODE_OFF` plus `SENSOR_EXPOSURE_TIME` = the **last exposure the
  auto-exposure chose** (`mLastExposureTimeNs` from capture results), else the middle of the sensor's range. ISO is
  set only when the page gives one (`if (mIso > 0) … SENSOR_SENSITIVITY`). **A page that locks must read
  `getSettings()` first and pass `exposureTime` and `iso` explicitly**, or the brightness can jump at the lock.
- `exposureTime` is in **100 µs units** (`NANOSECONDS_PER_100_MICROSECONDS`).
- The `manual` exposure mode is offered when `CONTROL_AE_LOCK_AVAILABLE` is true. Manual focus sets `CONTROL_AF_MODE_OFF`
  and `LENS_FOCUS_DISTANCE = 1/focusDistance`. White balance "manual" sets `CONTROL_AWB_LOCK`.
- Torch with manual exposure keeps AE off and sets `FLASH_MODE_TORCH`.

**iOS has no exposure lock from the web.** That is the one fact that shapes the iPhone path most: the scan must keep the
camera's auto-exposure steady instead of locking it (design: an "AE-steady" plan, §7).

### 2.4 Frame timing: which picture shows which pattern

| API | Support | Bench result (V) |
|---|---|---|
| `HTMLVideoElement.requestVideoFrameCallback` (rVFC) | Chrome 83, **Safari 15.4**, Firefox 132 (BCD **V**) | Metadata keys on a camera track: `captureTime, expectedDisplayTime, height, mediaTime, presentationTime, presentedFrames, width`. **`captureTime` is on the `performance.now()` clock**, 21 ms (median) before the callback with a canvas read per frame (max 49 ms). Under that load **3 of 23 callbacks skipped a frame** (`presentedFrames` jumped by 2): rVFC is display-paced and lossy |
| `captureTime` in WebKit | WebKit's `VideoFrameMetadata.idl` declares `captureTime`, `receiveTime`, `rtpTimestamp` as optional | Whether iOS fills `captureTime` for a local camera: **U** |
| `MediaStreamTrackProcessor` → `VideoFrame` | Chrome 94 (BCD "partial"), **Safari 18**; workers per spec | **Every frame delivered** (tags 31→42 consecutive). `VideoFrame.timestamp` is in µs on a **different time base** from `performance.now()` (1 888 926 303 µs against 1 244 100 µs): map it by a running minimum of arrival − timestamp. `format: I420`; **the default fake device codes 640×480 with a visible 640×360**: read `visibleRect`, not `codedHeight` (the bench's first tag read failed for exactly that reason) |
| `VideoFrame.copyTo` | Chrome 94, Safari 16.4; `format` conversion option Chrome 127 only | The Y plane of I420/NV12 is the gray8 a structured-light decode needs: no canvas, no colour conversion |
| `MediaStreamTrackGenerator` (Chrome 94, non-standard) / `VideoTrackGenerator` (Safari 18) | BCD **V** | Lets a test page synthesise a camera track frame by frame (used in the E2E plan, §5) |
| `DeviceMotionEvent` | everywhere; `requestPermission()` Safari iOS 14.5 (and Chrome 152) | Phone-moved detection; on iOS it needs a user gesture |
| `navigator.wakeLock` | Chrome 84, **Safari iOS 18.4** | Keeps the screen on during a scan |

**Frame IDs in the pattern work** (bench, **V**). A 16-cell band encodes an 8-bit tag as 8 differential pairs (cell 2b
is bit b, cell 2b+1 its inverse). It reads back exactly from the Y plane, with a pair margin of 219 levels on a clean
signal, and through a canvas on the rVFC path. Differential pairs need no threshold: the sign of A − B is the bit, and
|A − B| is the confidence.

**Rolling shutter** (**U**; general CMOS knowledge, not measured here): phone sensors read rows over roughly 10–30 ms. A
pattern change during readout gives a frame whose top rows show one pattern and whose bottom rows show the next. Tags at
two places far apart **in camera rows** that agree prove that the rows between them saw one pattern.

## 3. What "phones as the scan camera" needs that a webcam does not

1. **Exposure**: Android can lock exposure (with explicit `exposureTime`/`iso`). iOS cannot. Every pattern frame must
   then keep the scene's mean brightness constant: Gray code with its inverse and N-step sinusoids already sit at 50 %.
   Full white and black frames swing auto-exposure and must leave the coded sequence (§2.2).
2. **Timing over Wi-Fi**: arrival time is useless (tens of ms of jitter). Use the frame's **capture time**
   (rVFC `captureTime`, or `VideoFrame.timestamp` mapped to the page clock), mapped to the node's clock by a ping
   exchange, and **confirm with a tag in the pattern** (§2.4).
3. **Bandwidth**: 1080p gray8 is 2.07 MB a frame. The phone must choose the settled frame itself and send only that,
   losslessly, ROI-cropped (§2.5).
4. **Lens**: phones switch between physical cameras (a "virtual" multi-camera device chooses wide, ultra-wide or macro
   by distance; **U** for the web labels) and breathe with focus. Pick one physical back camera, lock focus where the
   platform allows, zoom 1.
5. **Motion**: a phone on a stand still gets bumped. `devicemotion` warns at once, and a black or reference frame
   compared at the start and end of a view proves stillness.
6. **Unknown intrinsics**: browsers do not expose focal length. Self-calibration must solve the phone's focal length,
   which several views and several projectors make well posed (§7).
7. **Screen and thermals**: the wake lock keeps the screen on. 1080p at 30 fps for about 15 s per projector does not
   heat a phone the way 4K does (**U**).

## 6. Risks found while researching

- **Patent**: Summit's US 11924556 covers predicting exposure from captured reference images with a saturation
  criterion. Locking auto-exposure on a stripe frame and checking for clipping is generic. A PlayMap step that
  "captures a reference at several exposures and picks the least-saturated" comes close to the abstract and needs a
  freedom-to-operate review before it ships. The design avoids multi-exposure prediction (§7 of the spec).
- **Untrusted-certificate behaviour on real phones** (a click-through rather than a flag, Safari WebSocket over an
  untrusted certificate, how long exceptions last) is **U**. The page falls back from WebSocket to `fetch` POST and
  server-sent events on the same origin.
- **iOS lens switching** in browser camera devices is **U**. The page reports the label it chose, and the node refuses
  to merge views taken with different labels or resolutions into one intrinsics set.

## 7. Design implications for PlayMap

1. **Serve the camera page from the node** (`https://<node>:<port>/scan`): same origin, no cloud, no Local Network Access
   prompt, works with the node's self-signed certificate after one tap-through. Ship it as embedded static files under
   a strict CSP. Make it installable (a manifest) but do not depend on a service worker.
2. **Pair with a QR code carrying a one-time ticket in the URL fragment.** Swap it for a revocable per-phone key held
   hashed on the node. The phone gets a scoped capability (camera ingest and scans through its own camera), never the
   node token.
3. **Pair frames with patterns by observation**, not by time alone. Draw small **tag sites** (4×4 cells, differential
   pairs, parity) into every pattern at places the camera is known to see, found by a short **cell-locate** sequence
   first. The phone reads the tags from the Y plane (`MediaStreamTrackProcessor`, rVFC fallback), waits until two
   consecutive frames agree (settle), and sends only that frame. Tags far apart in camera rows reject rolling-shutter
   mixes. Timing (capture time on the node's clock via ping) is the cross-check and the fallback.
4. **Lock-step with pipelining**: the node shows the next pattern when the phone has *seen* the current one. Uploads
   trail (≤6 in flight), lossless gray8 deflate-raw, ROI-cropped, optionally averaged as gray16.
5. **Exposure by platform**: Android locks exposure, focus and white balance explicitly after auto-exposure has settled
   on a 50 % stripe frame, then checks for clipping once (no multi-exposure prediction). iOS uses the **AE-steady plan**:
   no full white/black in the coded run, references synthesised from the coarsest Gray pair, white balance locked, and
   brightness drift measured and reported.
6. **Multi-view, multi-projector, curved**: tracks keyed by **projector pixel**. The projectors are the fixed anchors,
   and every phone position is one more view in a projector-anchored bundle adjustment that solves the phone's
   intrinsics as well. Dense geometry comes per projector (a projector-space depth map), which gives curved surfaces
   for free.
7. **Metric scale**: a tape-measure distance on the smart scan (any phone). On Chrome Android, WebXR depth at projected
   dots (0.5–5 m) as a should. LiDAR iPhones need a native app (later).
8. **Safe AI**: suggestions come from measured geometry plus the local segmenter. An assistant only names and ranks
   them from text descriptors (no pixels leave the node) and proposes `SCAN SURFACE` lines that a person approves on
   the phone or the desk. Nothing previews on the wall in Show Mode.
9. **Tests**: page logic under Node plus headless Chromium (the default fake device = "Android with locks", the Y4M
   device = "iPhone without locks"). The closed loop (render host on Xvfb → `SceneCamera` → a synthesised camera track
   in the page → upload → decode → solve → pose error against the simulator's truth) runs in this container. Real
   phones, real Wi-Fi and real certificate prompts are R0.5 lab work.
