# Rebuild PlayMap's Engine Around Direct3D 12

**Direct3D 12 should be PlayMap's renderer.** PlayMap is a Windows-only, NVIDIA-first media server that ranks capability, latency and reliability above portability, and D3D12 serves that brief best on four counts. New GPU features reach Windows through it first. It sits directly on DXGI's flip model and on NVIDIA's framelock present barrier. It is the native currency of D3D12 Video, NVENC, Spout, DirectStorage and the desk's own GPU import. And it is the only API with PIX, GPU-less CI through WARP, and full crash forensics from both NVIDIA and AMD. OpenGL 4.6 is maintenance-only: Intel calls it "low priority" and AMD's tools ignore it. It should survive only as the reference backend while an RHI (rendering hardware interface) is cut at today's `GlDevice` seam. Vulkan is a credible runner-up, since Watchout 7 and TouchDesigner chose it. On Windows, though, it inherits presentation behaviour that depends on each vendor and needs a DirectX bridge for nearly everything else, so it is worth keeping only as a cheap option, through a shared SPIR-V shader front end. Tearing is really two problems. Inside one output, a flip-model swap chain that presents on vblank in Independent Flip removes it completely, provided that mode is proven for each output rather than assumed. Between outputs and machines, tearing is a phase error that only hardware removes: internal framelock or Mosaic on an RTX PRO card, and RTX PRO Sync with the D3D12 present barrier across machines. AMD withdrew framelock in 2023, GeForce never had it, and network time aligns which frame is drawn but not when it scans out. Builds should take one version from git and render it in each format its consumers require: SemVer plus the commit for people and the wire, a FileVersion whose parts fit 16 bits, and an MSI version whose major stays at or below 255. That version belongs in every hello, STATE line, journal row and crash dump. Games and medical devices agree on the rest. Never compile, allocate or wait on the render thread. Drive every stage from a predicted display time. Rehearse device loss. And prove what the audience saw with an in-picture counter read by an independent observer, because a frozen frame looks normal to everyone watching it. PlayMap has not yet adopted that last lesson.

## Direct3D 12 is where Windows GPU capability lands first

On Windows, new GPU capability now ships in a settled order: **Direct3D 12 first, Vulkan extensions second, OpenGL not at all**. Microsoft releases D3D12 features as paired retail and preview Agility SDKs, each with a published per-vendor driver matrix. Agility 1.619 took Shader Model 6.9 to retail on February 26, 2026, with support listed for every NVIDIA RTX card, AMD RX 9000 and Intel Arc B ([DirectX blog](https://devblogs.microsoft.com/directx/shader-model-6-9-retail-and-more/); [VideoCardz](https://videocardz.com/newz/microsoft-ships-shader-model-6-9-in-directx-12-agility-sdk-1-619)). Point releases were still shipping debug-layer and DRED fixes in September 2026 ([Agility SDK downloads](https://devblogs.microsoft.com/directx/directx12agility/)). All three vendors ship conformant Vulkan 1.4 drivers ([Khronos](https://www.khronos.org/blog/vulkan-continuing-to-forge-ahead-siggraph-2025)).

OpenGL's newest core, 4.6, dates from 2017, and even its maintenance breaks things. AMD's 2022 driver rewrite removed about 60 extensions and changed GLSL compilation, so previously working shaders had to be rewritten ([Geeks3D](https://geeks3d.com/20220804/amd-radeon-adrenalin-22-7-1-opengl-changes-tested/)). Applications that asked for a 3.3 core context received a 4.6 compatibility context, with heavy slowdowns ([Vintage Story #2454](https://github.com/anegostudios/VintageStory-Issues/issues/2454)). Intel's issue tracker says "OpenGL unfortunately has low priority" ([IGCIT #402](https://github.com/IGCIT/Intel-GPU-Community-Issue-Tracker-IGCIT/issues/402)). An Arc B580 scored **4,570 in OpenGL against 12,281 in Vulkan and 12,082 in DX12** before a later driver fix ([IGCIT #1148](https://github.com/IGCIT/Intel-GPU-Community-Issue-Tracker-IGCIT/issues/1148); [Intel](https://www.intel.com/content/www/us/en/support/articles/000101542/graphics.html)). Even 10-bit output, which projection work wants, needed OS workarounds under OpenGL; Smode notes these are unnecessary "with DirectX12 with native 10-bit support" ([Smode GPU settings](https://doc.smode.io/reference/preferences/engine/other/gpu-settings/)). Building a renderer meant to last a decade on an API its vendors are quietly retiring is the one option the evidence rules out.

### Both explicit APIs cover what PlayMap needs; D3D12 adds the extras

D3D12 and Vulkan both provide the features that change outcomes for PlayMap's workload. These are dedicated copy queues, which keep uploads and readbacks off the render queue, and 64-bit timeline fences that the decode and encode engines can share. Both also offer HDR and 10-bit flip-model output, bindless resources, and direct CPU writes into VRAM over resizable BAR.

D3D12 leads on the cross-vendor extras: work graphs, sampler feedback, and DXR 1.2's Opacity Micromaps and Shader Execution Reordering. It also has GPU upload heaps, which need **Windows 11 build 26080 or later plus ReBAR enabled in firmware** ([DirectX blog 1.613](https://devblogs.microsoft.com/directx/agility-sdk-1-613-0/); [AMD GPUOpen](https://gpuopen.com/news/microsoft-work-graphs-1-0-now-available/)). The February 2026 preview added Fence Barriers inside the command stream and 3D LUTs on the video-processing block ([VideoCardz](https://videocardz.com/newz/microsoft-ships-shader-model-6-9-in-directx-12-agility-sdk-1-619)). Vulkan's 2026 bindless answer, `VK_EXT_descriptor_heap`, is meant to "completely replace" descriptor sets. It arrived only in January 2026, as an EXT with a KHR version still to come ([Khronos](https://www.khronos.org/blog/vulkan-introduces-roadmap-2026-and-new-descriptor-heap-extension)), so bindless Vulkan code written now faces one more migration.

### Presentation decides it

Presentation is the deciding difference for a show renderer. D3D12 sits directly on DXGI's flip model. That gives it Independent Flip, a frame-latency waitable object that reaches **one frame of latency**, and `GetFrameStatistics` with QPC vblank times in both windowed and full-screen mode ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model); [DXGI flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-flip-model)). Windows 11's composition swapchain adds presents that target a specific time, "whereas DXGI doesn't" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/comp_swapchain/comp-swapchain)). That is PlayMap's rule, frame = f(leader time at vblank), expressed as an OS API. NVIDIA's present barrier for framelock is created from a D3D12 device and a DXGI swap chain ([NVIDIA](https://developer.nvidia.com/blog/synchronizing-present-calls-between-applications-on-distributed-systems-with-directx-12/)).

Vulkan gained real pacing tools in 2025: `present_wait2`, and `VK_EXT_present_timing` with absolute and relative target times. At announcement, though, present timing was only in NVIDIA developer drivers, and Khronos itself says complex display topologies are "not yet possible with this extension alone" ([Khronos](https://www.khronos.org/blog/vk-ext-present-timing-the-journey-to-state-of-the-art-frame-pacing-in-vulkan)). On NVIDIA hardware, OpenGL and Vulkan get flip-model behaviour only when a driver setting is switched to "Prefer layered on DXGI swapchain" ([NVAPI settings](https://docs.nvidia.com/nvapi/NvApiDriverSettings_8h.html); [MonoGame #8629](https://github.com/MonoGame/MonoGame/issues/8629)). PlayMap's experimental D3D11 presenter exists, through ANGLE, precisely because GL cannot do this natively. A D3D12 renderer keeps the same DXGI semantics and removes the ANGLE layer.

### The rest of Windows speaks DXGI handles and fences

Most of the Windows media stack already trades in D3D resources, NT handles and fences. FFmpeg's D3D12VA decoders hand back D3D12 resources. NVENC's D3D12 interface takes explicit fence-and-value pairs ([NVIDIA](https://developer.nvidia.com/blog/encoding-for-directx-12-with-video-codec-sdk-11-1/)), and D3D12 Video encode has covered AV1 since Windows 11 24H2 ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/video-encoding-d3d12)). Spout shares D3D11 textures ([Spout](https://spout.discourse.group/t/directx-12-support/216)), and DirectStorage, Windows ML and Avalonia's GPU import all bind to the same DirectX objects.

A Vulkan engine reaches these only through external-memory import, which is optional and fails on some hardware. TouchDesigner's Vulkan build could not receive Spout on an Intel UHD 730, because the feature it needs "isn't necessarily available on all GPUs" ([TouchDesigner forum](https://forum.derivative.ca/t/spout-on-intel-uhd-graphics-card/811529)). In one Vulkanised 2025 table, Intel's Windows Vulkan Video passed **0 of 242 AV1 conformance vectors** ([Igalia](https://www.vulkan.org/user/pages/09.events/vulkanised-2025/T31-Stephane-Cerveau-Igalia.pdf)).

### Diagnostics and CI: only D3D12 has the full set

D3D12 also has the deepest stack for diagnosing faults in the field: PIX ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/general/pix-overview)), the debug layer and GPU-based validation, DRED and dump files, NVIDIA Aftermath and AMD Radeon GPU Detective ([Aftermath](https://developer.nvidia.com/nsight-aftermath/getting-started); [RGD](https://gpuopen.com/radeon-gpu-detective/)). AMD's profiler "will NOT work with older graphics APIs such as DirectX11 or OpenGL" ([RGP](https://github.com/GPUOpen-Tools/radeon_gpu_profiler/blob/master/docs/source/index.rst)), and Aftermath lists no OpenGL support. Leaving GL is therefore a precondition for diagnosing a TDR (a GPU timeout and reset) on a show machine. WARP from NuGet now claims **feature level 12_2 with SM 6.9**, work graphs and D3D12 video ([NuGet](https://www.nuget.org/packages/Microsoft.Direct3D.WARP)). That gives Windows CI a GPU-less runner for the real renderer, although the NuGet WARP binaries cannot be redistributed ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/directx-warp)).

### Peer products left OpenGL, in both directions

Every peer product that rewrote its renderer since 2021 left OpenGL, but not all in the same direction. Smode made DirectX 12 the default for outputs and genlock/multi-server sync in December 2024 ([Smode 10.2](https://doc.smode.io/changelog/Smode102/)). Unity made DX12 its Windows default in 6.1 ([Unity](https://unity.com/blog/directx-12-improvements-in-unity-6)), and Ventuz is DirectX-only ([Ventuz](https://www.ventuz.com/resources/system-requirements/)). Against that, Dataton built the Windows-only Watchout 7 on Vulkan 1.3 "to achieve lower overhead and efficient GPU resource management" ([Dataton](https://docs.dataton.com/watchout-7-new/watchout/getting-started/installing-watchout.html)). TouchDesigner's Vulkan move cut CPU cook times by "about 50%" ([TouchDesigner forum](https://forum.derivative.ca/t/what-does-the-adoption-of-vulcan-mean-for-the-future-of-touchdesigner/144033)).

The case for Vulkan is real: one cross-vendor video API, present timing, native SPIR-V for user GLSL, and a route to Linux nodes. It loses here because PlayMap prizes Windows capability over portability, and every Windows-specific strength sits on the DirectX side. One NVIDIA forum report shows `VK_NV_present_barrier` refusing a second swap chain on a Quadro Sync II wall that worked under OpenGL swap groups ([NVIDIA forum](https://forums.developer.nvidia.com/t/cant-create-more-than-1-swapchain-with-vk-nv-present-barrier/349276)).

| Criterion (Windows only) | Direct3D 12 | Vulkan 1.4 | OpenGL 4.6 |
|---|---|---|---|
| Vendor investment | Highest: Agility SDK, day-one drivers, published matrix | High; extensions often NVIDIA/AMD first | Maintenance only |
| Presentation and framelock | DXGI flip/iflip, frame statistics, composition-swapchain target time, NvAPI present barrier | `present_wait2`; present timing new and NVIDIA-first; `VK_NV_present_barrier` | wgl swap control, `WGL_NV_swap_group`; flip model only through driver layering |
| Video zero-copy | D3D11VA/D3D12VA, NVENC D3D12, D3D12 Video, Spout native | Vulkan Video good on NVIDIA/AMD, weak on Intel; Spout import optional | Copies through interop or ANGLE |
| Tools, crash forensics, CI | PIX, DRED, Aftermath, RGD, WARP at FL 12_2 | Nsight, Aftermath, RGD, validation layers; no PIX | No RGP, RGD or Aftermath |
| User GLSL/ISF | Needs a SPIR-V→DXIL step | Native SPIR-V via glslang `-R` | Native |
| .NET 10 bindings | Vortice 3.8.3, TerraFX (Agility 1.619.2) | Silk.NET 2.x volunteer-maintained, 3.0 pending | Silk.NET |

One gap in this verdict remains. No source compares D3D12, Vulkan and OpenGL latency on identical show hardware. PlayMap's present ledger must establish parity before GL is retired, as the doctrine of "measured, then governed" requires.

### Migration: cut an RHI at GlDevice and keep GL until parity

This is a rewrite of the GPU layer lasting several quarters, not a port. TouchDesigner announced its move in 2020, shipped an experimental Vulkan build on December 17, 2021 and an official release on May 25, 2022. Along the way it broke its Custom TOP API, removed the SVG TOP and changed point-sprite shaders ([Experimental 2021.38110](https://derivative.ca/release/experimental-202138110/65595); [2022 Official](https://derivative.ca/community-post/2022-official-update/66222)). Stride still describes its D3D12 backend as less stable than its D3D11 one ([Stride manual](https://doc.stride3d.net/latest/en/manual/graphics/graphics-api.html)).

PlayMap starts from a better place. Direct GL calls sit in about 10 of the 89 files in `PlayMap.Render`, behind a `GlDevice` wrapper that about 40 files use, and a render graph and an `IOutputPresenter` seam already exist ([docs/ARCHITECTURE.md](/home/user/mapper/docs/ARCHITECTURE.md)). The low-risk order runs in six steps. First, extract an RHI interface from `GlDevice` (resources, pipelines, binding sets, command lists, queues, fences, presenters, importers), with GL 3.3 as the reference implementation. Second, add a D3D12 backend for offscreen passes, checked by the existing pixel tests running on WARP. Third, move presentation to D3D12 flip-model presenters, retiring ANGLE, and then add the present barrier and the composition swapchain as the framelock and timing tiers. Fourth, move decode to D3D12VA and shared NT handles, and move Spout to a D3D11 side device with shared fences, a bridge the vvvv community already uses for zero-copy D3D11↔D3D12 work ([VL.Stride.DX12Bridge](https://www.nuget.org/packages/VL.Stride.DX12Bridge/)). Fifth, move the ISF chain onto the shader pipeline described below. Sixth, retire GL only when the timing and pixel tests observed through STATE reach parity.

NVRHI's lifetime tracking, automatic barriers, explicit queues and native-handle escape hatches are a good template for the interface ([NVRHI guide](https://github.com/NVIDIA-RTX/NVRHI/blob/main/doc/ProgrammingGuide.md)). Two .NET bindings are maintained: **Vortice.Windows 3.8.3** targets net10 and now wraps the D3D12 Memory Allocator ([Vortice changelog](https://github.com/amerkoleci/Vortice.Windows/blob/main/CHANGELOG.md)), while **TerraFX** offers raw interop tracking Agility 1.619.2 ([TerraFX](https://github.com/terrafx/terrafx.interop.windows)). By contrast, Silk.NET 2.x is now "released ad-hoc" by volunteers ([Silk.NET](https://github.com/dotnet/Silk.NET/blob/main/README.md)), and Veldrid has published nothing since 2023 ([Veldrid](https://github.com/veldrid/veldrid)). A WebGPU layer would hide the native device that the present barrier, NVAPI and D3D12 Video all need, so it is not an option here.

**Shader pipeline.** Engine-owned shaders should be rewritten once in HLSL and compiled with DXC, which is on NuGet ([DXC 1.9.2602](https://github.com/microsoft/DirectXShaderCompiler/releases/tag/v1.9.2602)). DXC's PDBs are what PIX and RGD use to map a GPU crash back to a source line ([GPUOpen](https://gpuopen.com/learn/enhancing-amd-radeon-gpu-detective-output-with-directx-debug-information/)). User ISF and GLSL take a longer path. PlayMap's IsfTranslator first normalises the source to GLSL 4.50 or later. glslang's relaxed mode (`-R`) then compiles "existing OpenGL GLSL … without requiring any edits" to SPIR-V ([Khronos GLSL](https://github.com/KhronosGroup/GLSL/blob/main/extensions/ext/GL_EXT_vulkan_glsl_relaxed.txt)). Finally, Mesa's MIT-licensed spirv_to_dxil turns that SPIR-V into DXIL, a route Godot found "much more convenient" than going through SPIRV-Cross ([Godot](https://godotengine.org/article/d3d12-adventures-in-shaderland/)). Microsoft has committed that D3D12 will accept SPIR-V from Shader Model 7 ([DirectX blog](https://devblogs.microsoft.com/directx/directx-adopting-spir-v/)), which eventually removes that last step. The same SPIR-V front end keeps a future Vulkan backend cheap.

The largest risk is the one TouchDesigner hit: under an explicit API "it's much easier for incorrectly written GLSL to cause a full application crash" ([Derivative](https://derivative.ca/UserGuide/Write_a_GLSL_TOP)). The compile lane must treat user shaders as untrusted, with SPIR-V validation, robust buffer access and a per-shader GPU-time guard. Device-lost recovery becomes part of normal operation rather than an exception path.

## Flip model ends tearing inside an output; only sync hardware ends it between outputs

A tear is two frames in one scanout. Operators use the word for two different failures. A tear inside one output is a presentation fault, and software can remove it completely. A mismatch between outputs or machines is a phase fault, and only hardware can remove it.

### One output: Independent Flip, proven rather than assumed

D3D12 supports only flip-model swap chains and "doesn't support full-screen exclusive mode" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3d12/swap-chains)). Consider a borderless window that covers the output, with buffers matching the display mode, presenting on vblank. The OS promotes it to DirectFlip and then Independent Flip, where "the DWM can go to sleep" and frames reach the screen "with the same efficiency as fullscreen exclusive" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)). Such an output cannot tear. Three traps remain. If the requested refresh rate does not match an enumerated mode, for example 60 against 60000/1001, DXGI is forced to blit ([DXGI best practices](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/dxgi-best-practices)). By default DXGI queues three frames and blocks on the fourth Present ([NVIDIA](https://developer.nvidia.com/blog/advanced-api-performance-swap-chains/)). And a composed DXGI swap chain follows the primary monitor's cadence, whichever display it is on ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/directcomp/compositor-clock/compositor-clock)).

Because Windows silently demotes a swap chain to composition when anything overlaps it, "this output is in Independent Flip" must be an observed fact. PresentMon reports the mode of each present from outside the engine ([PresentMon](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md)). Continuous DXGI statistics give the engine its own check from inside. PlayMap's experimental D3D11 presenter already follows the documented best practice (a waitable `FLIP_DISCARD` swap chain at latency 1, with frame statistics feeding a vblank fit). The D3D12 presenter should inherit it and make it the default.

**Specialized displays.** Windows can take a display away from the desktop entirely. The DWM then ignores it: no cursor, no taskbar, no window can overlap it. A custom compositor drives it through `Windows.Devices.Display.Core`, NVIDIA's `configureDdisplay.exe` with a DDisplay present barrier, or `VK_KHR_display` ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/specialized-monitors-compositor); [NVIDIA DDisplay](https://www.nvidia.com/en-us/drivers/ddisplay-utility/)). The catch is the edition: it requires **Windows Enterprise, Pro for Workstations or IoT Enterprise**. A display must be designated by a user toggle or an EDID block, and Microsoft forbids doing so "by overriding the EDID in software" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/specialized-monitors-edid-extension)). TouchDesigner's Direct Display Out uses this route, limited to three outputs on workstation NVIDIA GPUs ([Derivative](https://docs.derivative.ca/Direct_Display_Out_TOP)). PlayMap should offer it as a "dedicated output" presenter tier on nodes running the right edition.

**VRR.** Variable refresh stays off for any output in a lock group or feeding genlocked LED processors or projectors. NVIDIA's own setup order says to disable G-SYNC before enabling framelock ([RTX PRO Sync guide](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)).

### Many outputs: tearing is phase, and phase is hardware

Two outputs at the same nominal 60 Hz scan out on independent clocks unless the driver locks them.

**On one GPU.** NVIDIA's internal framelock or Synchronized Mosaic "will ensure no tearing across monitors". Mosaic across GPUs that share only a PCIe bus "is not synchronized" ([RTX PRO Sync guide](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)).

**Across GPUs and machines.** The only shipping mechanism on Windows is **NVIDIA RTX PRO Sync**, the April 2025 rebrand of Quadro Sync II. One card serves up to 4 GPUs and a system takes 2 cards, for 8 GPUs and 32 displays. It accepts house sync in TTL, bi-level or tri-level form and can multiply or divide it from 1 to 8, so 120 Hz outputs run on 60 Hz house sync. Machines are joined by a CAT-5 daisy chain that must never touch a network switch, and display timings must agree within **±50 ppm** ([NVIDIA](https://www.nvidia.com/en-us/design-visualization/solutions/rtx-pro-sync/); [user guide](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)).

Applications join through NvAPI's D3D12 present barrier. It is six calls, with a sync mode that reports not joined, client, system or cluster, plus frame statistics. "GeForce is NOT supported" ([NVIDIA](https://developer.nvidia.com/blog/synchronizing-present-calls-between-applications-on-distributed-systems-with-directx-12/); [nvpro-samples](https://github.com/nvpro-samples/dx12_present_barrier)). The barrier engages only full-screen, with no borders, desktop scaling or taskbar composition. Those are the same conditions Independent Flip needs, so one presentation discipline serves both.

**AMD.** AMD's PRO driver states that "Framelock/Genlock is no longer supported" from 23.Q1 ([AMD](https://www.amd.com/en/resources/support-articles/release-notes/RN-PRO-WIN-23-Q1.html)), and the RDNA 3 W7900 lists no sync feature ([AMD W7900](https://www.amd.com/en/products/graphics/workstations/radeon-pro/w7900.html)). Only disguise's vendor-pinned AMD driver on its older VX 4 hardware still genlocks ([disguise](https://help.disguise.one/designer/configuration/genlock-configuration)).

**Software sync has a hard ceiling.** Dataton explains that NTP aligns clocks "to within about a millisecond, but it does not align GPU output", so outputs sit "a fraction of a frame apart". On genlocked LED processors "even a sub-millisecond offset can shift the output by a frame and tear between panels" ([Watchout](https://docs.dataton.com/guide/watchout/network-setup/time-synchronization.html)). Epic reports that genlock alone "has not proven to be 100% reliable", and that Ethernet sync can still tear "among the displays because of Windows DWM" ([Unreal nDisplay](https://docs.unrealengine.com/4.27/en-US/WorkingWithMedia/IntegratingMedia/nDisplay/Synchronization/)). Windows has had a PTP client since 1809 and NIC hardware timestamps on Windows 11 ([W32Time](https://github.com/microsoft/W32Time?tab=readme-ov-file); [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/iphlp/packet-timestamping)). PTP sharpens the *measurement* of phase but cannot *move* it.

PlayMap's software sync group is therefore state of the art for content. Without hardware, its honest verdict is "same frame, phase offset up to one refresh", and STATE must report measured phase, never "locked". One design inference follows: wherever topology allows, keep blend zones and LED seams on outputs of a single framelocked GPU. A seam that crosses machines without sync hardware will tear on fast motion.

**Barriers are all-or-nothing.** TouchDesigner warns that "Frame Lock is not fault tolerance" ([Derivative](https://docs.derivative.ca/Hardware_Frame_Lock)). In Watchout, a node whose sync is invalid stalls the barrier and stops presenting, and the sync board's 24-bit frame counter wraps about every three days at 60 fps ([Watchout](https://docs.dataton.com/guide/watchout/working-with-shows/show-properties.html)). PlayMap's hardware anchor must therefore be wrap-aware, and its existing "falls out" rule must become a governed "leave the barrier and free-run" path with a recorded cause. During a running show, degrading one node beats Epic's fail-closed startup policy.

**Identical timings are a precondition.** disguise outputs "cannot genlock if their resolutions match but their EDIDs differ" ([disguise](https://help.disguise.one/designer/feed-outputs/head-configuration)), and Pixera calls the same EDID on all outputs "mandatory" ([Pixera](https://help.pixera.one/synchronize-outputs-genlock-framelock-setup)). The presentation layer should own EDIDs and custom timings, and STATE should expose each output's pixel clock and totals so that a refused lock can name its cause.

**SDI and ST 2110 outputs genlock on the I/O card, not the GPU.** DeckLink reports its reference-lock status ([Blackmagic](https://sdk-doc.blackmagicdesign.com/decklink-sdk/DeckLinkAPI/enums/bmdreferencestatus.html)). Rivermax on Windows needs a BlueField DPU for PTP ([NVIDIA](https://developer.nvidia.com/networking/rivermax/faq)). Both want a presenter type whose vblank truth comes from the card, plus a shared house reference into the Sync card's BNC input.

**Warp and blend at scanout.** On RTX PRO, the driver applies warp and blend "before the final scanout" with "no incremental latency" ([NVIDIA](https://developer.nvidia.com/warp-and-blend)). GeForce returns `NVAPI_NOT_SUPPORTED` ([NVIDIA forum](https://forums.developer.nvidia.com/t/rtx-warp-and-blend-api/249199)). It is an optional tier behind PlayMap's own shader warp, which stays the reference.

| Scope | What removes tearing | Hardware and OS | How PlayMap proves it |
|---|---|---|---|
| Inside one output | Flip-model swap chain on vblank, Independent Flip, mode-matched, VRR off | Any D3D12 GPU, Windows 11 | PresentMon mode, DXGI statistics continuity, present ledger |
| Several outputs on one GPU | Internal framelock or Synchronized Mosaic | RTX PRO (consumer cards free-run) | Phase fit for each output |
| Several GPUs or machines | RTX PRO Sync plus D3D12 present barrier | RTX PRO 4000-class or above, Sync card, CAT-5 chain | Barrier sync mode, in-sync present/flip counts |
| Locked to house or broadcast sync | House sync into the Sync card; SDI genlock on the I/O card; ST 2110 via PTP | Sync card; DeckLink/AJA; BlueField for 2110 on Windows | Reference status from the card |
| No sync hardware | Content alignment only (leader time, NTP/PTP); phase offset up to one refresh | Any | Report measured phase, never "locked" |

### One queued frame is the tear-free latency floor

With the waitable object at maximum latency 1 in Independent Flip, latency gets "down to 1 frame". `ALLOW_TEARING` goes lower only by permitting tears ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)). Beam racing reaches below one frame, but it needs vsync off and tearline steering ([Blur Busters](https://blurbusters.com/blur-busters-lagless-raster-follower-algorithm-for-emulator-developers/)), and on a GeForce RTX under Windows 11 a tearline will not even appear in the first ~30 scanlines ([VOGONS](https://www.vogons.org/viewtopic.php?t=95018)). That makes it incompatible with locks and useful only for single-output loops such as camera-to-projector scanning.

The remaining lever is just-in-time work. Wait on the waitable object, then sample leader time and the newest live input, then record the frame. This is the pattern behind NVIDIA Reflex and AMD Anti-Lag 2. Reflex is documented for GeForce 900 and newer; support on RTX PRO drivers is not stated ([Streamline](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideReflex.md); [GPUOpen](https://gpuopen.com/anti-lag-2/)).

Photon latency needs a sensor. A photodiode rig costing under €25 measured with 116.5 µs internal error. Because scanout takes **16.67 ms from top to bottom at 60 Hz**, the sensor's position must be fixed and reported ([Uni Regensburg](https://epub.uni-regensburg.de/45570/1/yet-another-latency-measuring-device.pdf)).

## Windows 11 throttles an unclaimed engine, so claim QoS, timers and cores

Windows 11's defaults now work against a show engine that is partly hidden or unattended. The scheduler assigns quality of service from window state: in focus is High, visible is Medium, minimised or fully occluded is Low ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)). Timer requests changed too. Since Windows 10 2004, `timeBeginPeriod` no longer sets a global resolution, and Windows 11 stops guaranteeing it for processes whose windows are "fully occluded, minimized, or otherwise invisible or inaudible" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)).

An engine whose output window sits behind the desk is exactly that process. It must opt out explicitly. One `SetProcessInformation(ProcessPowerThrottling)` call does it: put both the execution-speed and ignore-timer-resolution flags in the control mask and leave the state mask at zero. That forces HighQoS and "Always honor Timer Resolution Requests" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)). The user-inactivity QoS drop needs its own registry switch, and Microsoft notes that automated tests without input can trigger it ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)).

**Timing.** Sleeps should use `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION` (Windows 10 1803 and later) ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw)). Time stamps come from QPC, which is what `Stopwatch` uses. `GetSystemTimePreciseAsFileTime` serves cross-machine wall-clock stamps ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)).

**Priority.** The engine process belongs in `HIGH_PRIORITY_CLASS`, not realtime, which "you should almost never use" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities)). Deadline threads join MMCSS (the Multimedia Class Scheduler Service). The Pro Audio task runs at priority 23–26, MMCSS threads enter the Media and Deadline QoS levels, and MMCSS's "GPU Priority" value "is not yet used" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)).

**Core placement.** Placement should be soft. CPU Sets cooperate with power management, while a hard affinity mask overrides them ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/procthread/cpu-sets)). Intel says that on hybrid chips "software should avoid setting affinity", that scheduling "is QoS and then priority-driven" ([Intel](https://cdrdv2-public.intel.com/685869/optimizing%20_software_for_performance_hybrid_architecture.pdf)), and that critical-path threads should be separated from background pools, with the background pools pushed to efficient cores through EcoQoS ([Intel](https://www.intel.com/content/www/us/en/developer/articles/technical/optimizing-threading-for-gaming-performance.html)).

AMD's dual-CCD X3D parts are a known conflict. The V-Cache optimiser parks the second CCD only when Game Mode identifies a game, and it expects the Balanced power plan ([FPSHQ](https://fpshq.com/en/wiki/core-parking/); [VideoCardz](https://videocardz.com/newz/amd-confirms-chipset-driver-updates-and-new-features-for-ryzen-9-9950x3d-9900x3d)). Pro-audio guidance demands High Performance instead ([Universal Audio](https://help.uaudio.com/hc/en-us/articles/27247945568788-Optimizing-Windows-for-UA-Devices)). PlayMap will not be recognised as a game, so restricting its critical pool to the V-Cache CCD needs measurement on real 9950X3D hardware. The AMD evidence here comes from press and enthusiast sources, not an AMD whitepaper.

**GPU priority is also claimable.** A D3D12 queue at `GLOBAL_REALTIME` needs a "sufficiently privileged" process and fails rather than silently downgrading ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ne-d3d12-d3d12_command_queue_priority)). The Xenia emulator enables `SeIncreaseBasePriorityPrivilege` before creating such a queue and falls back to HIGH ([Xenia](https://github.com/xenia-project/xenia/blob/master/src/xenia/ui/d3d12/d3d12_provider.cc)). That is the right pattern for PlayMap: the installer grants the privilege, the engine never runs as administrator, and realtime GPU priority is turned on only after measurement.

**HAGS.** Hardware-accelerated GPU scheduling should be recorded in STATE, not forced. It is now required for some features, such as DLSS frame generation and the hardware flip queue ([XDA](https://www.xda-developers.com/gpu-scheduling-toggle-pointless-2020-growing-list-windows-features-need/)). Puget measured "little to no impact" in content-creation apps and reported instability with high-VRAM workloads ([Puget](https://www.pugetsystems.com/labs/articles/impact-of-hardware-accelerated-gpu-scheduling-on-content-creation-performance/)).

**Memory.** For a renderer, the GC strategy that matters is not allocating on the hot path. Use workstation concurrent GC with `SustainedLowLatency` while a show is armed. Microsoft lists "applications that render animations" as the intended case, at the cost of a larger, uncompacted heap ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/latency)). Server GC and DATAS (the GC's dynamic heap-sizing mode) optimise throughput and heap size, not pauses ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/datas)). Frame pools belong in unmanaged memory allocated once at start-up. Large pages need `SeLockMemoryPrivilege`, and Microsoft's advice is to "allocate all large pages one time, at startup" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/memory/large-page-support)).

**CPU features in .NET 10.** Vector code should target `Vector128/256/512` behind `IsHardwareAccelerated` guards. AVX10.2 ships disabled by default ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/runtime)). Hybrid Intel parts expose only the instruction set common to their P- and E-cores, so 512-bit paths will mostly light up on Zen 4/5 and workstation silicon. One community report, not yet confirmed by Microsoft, shows explicit `Vector256` code regressing 71–73% on .NET 10.0.5 on an AVX-512 CPU ([dotnet/runtime #126250](https://github.com/dotnet/runtime/issues/126250)), so hot kernels need benchmarks on the actual show CPUs.

**Start-up compilation.** Tiered compilation runs unoptimised code on first calls ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/compilation)). The repo enables `TieredPGO` globally ([Directory.Build.props](/home/user/mapper/Directory.Build.props)), so the engine should pre-roll every path it runs each frame before declaring itself ready. NativeAOT removes the JIT, but it has "no built-in COM" on Windows, which DXGI and D3D interop must work around ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)). Microsoft's game guidance adds that "NativeAOT does not remove the garbage collector" ([Microsoft Learn](https://learn.microsoft.com/en-us/gaming/gdk/docs/gdk-dev/pc-dev/tutorials/get-started-with-custom-engine/native-aot-for-gaming?view=gdk-2604)). The choice between ReadyToRun plus pre-roll and NativeAOT should follow a measured p99.9 frame time over the first ten minutes of a show.

None of MMCSS, QoS, CPU Sets, high-resolution waitable timers or GPU priority exists in .NET 10's base library, so all of them belong in one small `PlayMap.Platform.Windows` seam built on `LibraryImport`.

## RTX PRO unlocks the mapping stack; Radeon brings media but no sync

### NVIDIA: the media stack is on every RTX, the projection stack is pro-only

NVIDIA divides its stack cleanly. The **projection-specific** features are RTX PRO only, as Watchout's requirements confirm ([Dataton](https://docs.dataton.com/guide/watchout/getting-started/system-requirements.html)): warp and blend at scanout, Mosaic, framelock and the present barrier, EDID management, and GPUDirect for Video.

The **media** features work on consumer RTX too. NVENC and NVDEC are there, though encoding is capped at **12 concurrent sessions per system** on non-qualified GPUs ([NVIDIA](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/nvenc-application-note/index.html)) and 4:2:2 encode and decode arrived only with Blackwell ([NVIDIA](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/read-me/index.html)). The RTX Video SDK does AI upscaling and SDR→HDR on D3D11, D3D12 and Vulkan ([NVIDIA](https://developer.nvidia.com/blog/enhancing-low-resolution-sdr-video-with-the-nvidia-rtx-video-sdk/)), and the VFX SDK's TrueHDR turns 8-bit SDR into 10-bit PQ ([NGC](https://catalog.ngc.nvidia.com/orgs/nvidia/maxine/collections/nvvfxtruehdr/-)). Aftermath crash dumps work on consumer cards but must be enabled before any device is created ([NVIDIA](https://docs.nvidia.com/nsight-aftermath/SDK/index.html)). OptiX ray tracing, useful for projection planning, is free for commercial use once NVIDIA has been notified ([NVIDIA](https://developer.nvidia.com/designworks/optix/download)). Windows ML's TensorRT-for-RTX provider runs inference "over 50% faster" than DirectML, by Microsoft's account ([Windows blog](https://blogs.windows.com/windowsdeveloper/2025/09/23/windows-ml-is-generally-available-empowering-developers-to-scale-local-ai-across-windows-devices/)).

DLSS frame generation is the exception worth refusing: it inserts synthesised frames under its own pacing, which contradicts content as a pure function of show time.

### AMD and Intel

AMD offers permissively licensed media and system SDKs, but no warp/blend API and no current sync. AGS 6.3.1 (MIT) detects GPUs and adds debug markers, but its D3D12 extensions require creating the device through `agsDriverExtensionsDX12_CreateDevice` instead of `D3D12CreateDevice` ([AGS](https://github.com/GPUOpen-LibrariesAndSDKs/AGS_SDK/blob/master/README.md)). ADLX controls FreeSync, colour depth, custom resolutions, 3D LUTs and Eyefinity ([ADLX](https://gpuopen.com/manuals/adlx/adlx-sdk-references/adlx-interfaces/display/)), which is enough to force FreeSync off and full-range 10-bit on projector outputs. AMF 1.5.3 (MIT) is the media framework ([AMF](https://gpuopen.com/advanced-media-framework/)), but **every AMD hardware codec is 4:2:0 only** through RDNA 4 ([AMF wiki](https://github.com/GPUOpen-LibrariesAndSDKs/AMF/wiki/GPU-and-APU-HW-Features-and-Support)).

Intel's VPL (MIT) is the broadest decoder and adds VVC ([Intel](https://github.com/intel/libvpl/)). Intel is best treated as a baseline tier plus a spare decode engine on the iGPU.

### Support tiers, probing and fallback

Peer products already tier their hardware support. Smode says AMD GPUs "are no longer validated" ([Smode](https://doc.smode.io/userGuide/tutorialsAndHow-Tos/gettingStarted/requirements/)). Notch warns of AMD "show-stopping driver bugs" ([Notch](https://manual.notch.one/2026.2/en/docs/workflows/working-with-media-servers/blocks/using-notch-in-d3/)). Watchout says AMD cards "require additional testing before deployment" ([Dataton](https://docs.dataton.com/guide/watchout/getting-started/system-requirements.html)). PlayMap should publish the same three tiers: **NVIDIA RTX and RTX PRO as tier 1, AMD RDNA 3/4 validated for each driver as tier 2, and Intel Arc B as best effort**.

| Feature tier | NVIDIA | AMD | Intel | Baseline that keeps PlayMap correct |
|---|---|---|---|---|
| 0: any D3D12 GPU | — | — | — | Shader warp, blend and masks; D3D12 Video or FFmpeg decode; software sync; FP16 or HDR10 output; Windows ML on CPU or DirectML |
| 1: consumer, probe then enable | NVENC/NVDEC, RTX Video, TrueHDR, Optical Flow, Aftermath, CUDA interop, TensorRT-RTX | AMF, AGS, ADLX display control, RGD, MIGraphX | VPL, OpenVINO | Tier 0 |
| 2: pro only, probe and never assume | Scanout warp/blend, Mosaic, RTX PRO Sync plus present barrier, EDID management, GPUDirect, Rivermax | None current | None | Tier 0 plus honest phase reporting |

Every feature in these tiers has a run-time probe, and the probe is the contract. The engine enumerates DXGI adapters by LUID (the adapter's locally unique ID) and binds each vendor library to its adapter by that LUID. It records each feature's result (supported, reason, driver version) in an immutable capability snapshot that STATE and the context publish, and it refuses any verb that needs an absent feature with the probe's reason. Where a feature can be set yet silently not applied, the engine must read back observed state before reporting "applied". Two known cases: a present barrier that stays pending, and scanout warp that reportedly returned success but did nothing on GeForce under newer drivers ([NVIDIA forum](https://forums.developer.nvidia.com/t/rtx-warp-and-blend-api/249199)). The device and swap-chain factories are the critical seam, because AGS replaces device creation, Aftermath must hook in before it, and the present barrier wraps the swap chain. Vendor code lives in edge modules, as the module rules require.

### Licensing

Licensing blocks nothing for a closed commercial product. NVAPI ([NVIDIA](https://github.com/NVIDIA/nvapi/blob/main/License.txt)), AGS and AMF are MIT-licensed. The Video Codec SDK allows object-code redistribution for use with NVIDIA GPUs only ([NVIDIA](https://developer.nvidia.com/nvidia-video-codec-sdk-license-agreement)). NVIDIA's RTX SDK licence requires notifying NVIDIA before a commercial release that uses DLSS or Reflex ([NVIDIA](https://github.com/NVIDIA-RTX/RTXCR/blob/main/License.txt)). AMD's EULA forbids redistributing driver components, so the ADLX and AMF runtimes are never bundled ([AMD](https://www.amd.com/en/resources/support-articles/amd-software-eula.html)). If PlayMap's source is ever opened, the proprietary NVIDIA SDKs must move into separately distributed, dynamically loaded modules. Their terms forbid use that would make them "subject to an open source software license" ([NVIDIA](https://github.com/NVIDIA/nvcomp/blob/main/LICENSE)).

## OS edition, not the installer, decides what a show node can do

### Installer and process layout

The installer is the easy part. Use a per-machine MSI built with **WiX v7** (released April 6, 2026), whose Open Source Maintenance Fee applies to organisations above $10,000 in annual revenue ([FireGiant](https://docs.firegiant.com/wix/whatsnew/releasenotes/); [OSMF](https://docs.firegiant.com/wix/osmf/)). The alternative is Velopack's `--msi --instLocation PerMachine`. Velopack installs per-user to LocalAppData by default ([Velopack](https://docs.velopack.io/packaging/operating-systems/windows)), and its MSI work does not add system services ([Velopack #606](https://github.com/velopack/velopack/pull/606)). MSIX now supports services and firewall rules, but it forbids drivers and virtualises writes to HKLM and AppData ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/msix/packaging-tool/know-your-installer)). That is awkward for machine-wide privilege grants and dump folders.

The installer should do every machine-level action once, so that the engine never needs administrator rights at run time. It writes the firewall rules and the WER (Windows Error Reporting) dump settings, grants privileges to the engine's account, and places an Agility SDK `D3D12Core.dll` beside the exe, since Windows loads the newer of the app's copy and System32's ([DirectX blog](https://devblogs.microsoft.com/directx/gettingstarted-dx12agility/)).

**The engine must not be a Windows service.** Services run in session 0, where functions that touch display devices "receive errors" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct2d/server-side-rendering-overview); [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)). It runs instead in an auto-logged-on show user's session, supervised by a small service or a scheduled task. On Enterprise, Education or IoT Enterprise, Shell Launcher can run it as the shell itself ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/configuration/shell-launcher/browser-support)).

### Choosing the OS edition

The edition choice carries more weight than it first appears. Windows 10 reached end of support on October 14, 2025 ([Microsoft](https://learn.microsoft.com/en-us/lifecycle/products/windows-10-home-and-pro)), and AMD's drivers have listed only Windows 11 since 25.10.2 ([AMD](https://www.amd.com/en/resources/support-articles/release-notes/RN-RAD-WIN-25-10-2.html)). **Windows 11 IoT Enterprise LTSC 2024** is build 26100, equivalent to 24H2, and is supported until **October 10, 2034** with no feature updates ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/iot/iot-enterprise/whats-new/windows-11-iot-enterprise-ltsc-2024)).

Three things make it the natural OS for fixed show nodes. It meets every feature floor in this report: build 24H2 is the minimum for GPU upload heaps (26080 or later), D3D12 AV1 encode and Advanced Shader Delivery (26100.1000) ([sample readme](https://github.com/microsoft/DirectX-Graphics-Samples/blob/master/Samples/Desktop/D3D12AdvancedShaderDelivery/readme.md)), and the LTSC build satisfies all of them. Its edition unlocks two features PlayMap wants, because Shell Launcher and specialized displays are both available on IoT Enterprise and neither is on Pro. And D3D12 stays current without feature updates, because the Agility SDK lets an LTSC node run a new D3D12 runtime while the OS stays frozen. The general channel moves on beneath desk machines: 23H2 ends November 11, 2026 ([Microsoft](https://learn.microsoft.com/en-us/lifecycle/products/windows-11-iot-enterprise)).

### Updates and signing

On general-channel machines, Windows Update policies defer feature updates up to 365 days and quality updates up to 30 ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/deployment/update/windows-update-client-policies)). PlayMap's own updater must refuse, with the reason, while a show is armed. A pending reboot or pending update should appear as a preflight fact.

**Signing** should use Azure Artifact Signing, from $9.99 a month with keys held in an HSM (a hardware security module) ([Azure](https://azure.microsoft.com/en-us/products/artifact-signing)). EV certificates stopped bypassing SmartScreen in 2024. Eligibility is limited: organisations in the USA, Canada, EU and UK, but individuals only in the USA and Canada ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)). Every release channel should be signed with one identity, so that SmartScreen reputation accrues to it.

### Crash dumps, device loss and preflight

A handful of settings keep a show node running and honest. WER LocalDumps should be configured for the PlayMap exe, with a bounded count, in a PlayMap-owned folder; the feature does not support apps that do their own crash reporting ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/wer/collecting-user-mode-dumps)). Full dumps stay on the machine, while anything shared off the node should be .NET's Triage dump type, which strips paths and passwords ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/collect-dumps-crash)). That reconciles full-dump forensics with the rule that secrets ride in no line. TDR registry keys are never shipped changed, because "Applications shouldn't manipulate these registry keys" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-registry-keys)); long GPU work is split instead. Device removal must be recoverable, since a driver update installed overnight removes the device and Microsoft calls that "normal" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/uwp/gaming/handling-device-lost-scenarios)). And `ES_DISPLAY_REQUIRED` keeps the display on but "does not stop the screen saver" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate)), so the screen saver needs its own preflight check. Power plan, USB selective suspend, PCIe power management, notifications, HAGS and driver version all belong in preflight as reported facts, never silent changes.

## One git-derived version must satisfy every format that reads it

Today every PlayMap project inherits a hard-coded `<Version>0.1.0</Version>` ([Directory.Build.props](/home/user/mapper/Directory.Build.props)). That number cannot tell two builds apart, cannot order CI builds, and cannot map a crash dump to a commit.

The consumers of a version disagree on its shape. SemVer requires that build metadata "MUST be ignored when determining version precedence" ([semver.org](https://semver.org/)). MSI reads only `major.minor.build`, with major and minor capped at **255** and build at 65,535 ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/msi/productversion)). MSIX uses four 16-bit parts, and the Store wants the fourth to be zero ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/package-version-numbering?pivots=store-installer-msix)). Velopack accepts only three-part SemVer ([Velopack](https://docs.velopack.io/troubleshooting/faq)). Two rules follow. Calendar majors such as `2026.x` cannot be used with MSI, and a CI run number must never sit in a 16-bit field, where it eventually overflows.

**Nerdbank.GitVersioning** fits best. Major and minor live in a reviewed `version.json`. The third component is the git height, so every commit is unique and ordered. It also generates a `ThisAssembly` class that Core can read ([NB.GV](https://dotnet.github.io/Nerdbank.GitVersioning/docs/ecosystems/dotnet.html)). Its default fourth FileVersion part is derived from the commit hash and breaks installers that expect `.0`; the maintainer documents an override ([NB.GV #444](https://github.com/dotnet/Nerdbank.GitVersioning/issues/444)). MinVer is the tag-driven alternative, and it already emits `Major.Minor.Patch.0` ([MinVer](https://github.com/adamralph/minver)).

Since the .NET 8 SDK, InformationalVersion automatically carries the commit ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/8.0/source-link)). Whether that doubles the hash when combined with NB.GV is unverified and should be checked on the first build. CI needs a full-history checkout so that height can be computed.

| Consumer | Format | Example |
|---|---|---|
| About box, wire hello, STATE, MCP context, journal header, dump names, Velopack | SemVer 2 with commit | `1.4.0-beta.37+g1a2b3c4d5e` |
| Windows FileVersion (Explorer, WER) | four 16-bit parts, fourth fixed at 0 | `1.4.37.0` |
| MSI ProductVersion | major.minor.build, major and minor ≤255 | `1.4.37` |
| MSIX, if ever used | four 16-bit parts, fourth 0 | `1.4.37.0` |
| AssemblyVersion | binding only | `1.4.0.0` |

The version should be read once in Core from `AssemblyInformationalVersionAttribute`. Every surface then reports the same string, and Patterns and Stagewatch can compare nodes by the SemVer core and catch mismatched builds by the commit.

A show node's identity is larger than PlayMap's own build, though. The GPU driver, Agility SDK, FFmpeg build and Sync firmware all change behaviour. Smode pins NVIDIA driver 582.16 and Sync firmware 3.06 for a release ([Smode](https://doc.smode.io/userGuide/tutorialsAndHow-Tos/gettingStarted/requirements/)), and a driver install clears the shader cache ([Epic](https://www.unrealengine.com/en-US/tech-blog/game-engines-and-shader-stuttering-unreal-engines-solution-to-the-problem)). STATE should carry a node-identity record holding both the build version and these versions. Preflight should warn when a node drifts from the driver set locked for the show.

## Games teach speed: the render thread only walks a precompiled plan

### Compile the render graph when the show changes, not every frame

Every major engine now builds a declarative frame graph and compiles it: culling unused passes, computing lifetimes, aliasing transient memory, and placing barriers and cross-queue fences ([Frostbite](https://www.slideshare.net/slideshow/framegraph-extensible-rendering-architecture-in-frostbite/72795495); [Unreal RDG](https://dev.epicgames.com/documentation/unreal-engine/render-dependency-graph-in-unreal-engine?lang=en-US); [Unity](https://docs.unity3d.com/Manual/urp/render-graph-introduction.html)). The refactor cut Frostbite's world renderer from **15K to 5K lines** ([Frostbite slides](https://en.ppt-online.org/1673409)).

PlayMap's topology of outputs × surfaces × passes changes only when the configuration does. So the graph should be compiled on the lane when the show changes, and the result published as an immutable plan that the render thread merely walks. Frostbite's one-frame lifetime rule means delay rings and history buffers must be imported, never aliased. Unreal's debug switches, which force-initialise resources and extend lifetimes, suggest a cheap fixture: run the golden-image tests with aliasing on and off. Any difference proves a missing barrier.

### Use frame data blocks, pipes and dedicated workers

Naughty Dog ran 800–1000 jobs per frame on six workers locked to cores. Each frame had a `FrameParams` block carrying per-stage time stamps, and a tagged block allocator needed "no locks … for 99.9% of memory allocations" ([Gyrling, GDC 2015](https://media.gdcvault.com/gdc2015/presentations/Gyrling_Christian_Parallelizing_The_Naughty.pdf)). Unreal's pipes replace mutexes with serialised task chains ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/tasks-systems-in-unreal-engine)).

PlayMap already has these patterns under other names: its lanes are pipes, and its snapshots are `FrameParams`. What remains is to make the per-frame block an explicit ring, sized to frames in flight plus one. Each block carries the frame's show time, its target vblank and stage stamps feeding the present ledger, and is backed by a native arena reset when the frame's fence signals. Render-critical work belongs on dedicated pinned threads, not the shared ThreadPool. Fibers are not practical in .NET.

### Drive every stage from a predicted display time

Modern latency engineering sleeps *before* sampling time or input. NVIDIA Reflex paces the CPU so that it submits "just in time", where the API would normally let it run two frames ahead ([NVIDIA](https://www.nvidia.com/en-us/geforce/news/reflex-low-latency-platform/)). AMD reports native latency of 3–5 frames falling to 1–2 with Anti-Lag 2 ([GPUOpen](https://gpuopen.com/learn/integrating-amd-radeon-anti-lag-2-sdk-in-your-game/)). OpenXR states the governing rule: "Every stage in the engine pipeline should use the exact same display time" ([Khronos](https://registry.khronos.org/OpenXR/specs/1.1/man/html/xrWaitFrame.html)). Valve's "running start" begins submission about 2 ms before vsync ([Valve, GDC 2015](https://media.steampowered.com/apps/valve/2015/Alex_Vlachos_Advanced_VR_Rendering_GDC2015.pdf)).

For PlayMap, frames in flight should be a policy for each output, not a global constant. Use 1 for outputs that carry live inputs such as IMAG (the live camera image of performers) and tracking. Use 2 for heavy generative layers, where the extra latency is invisible because content is a function of time.

### Never compile a pipeline on the render thread

Shader and pipeline (PSO) compilation is games' best-documented stutter. A first-use compile can take "tens of milliseconds or more" ([Epic](https://www.unrealengine.com/en-US/tech-blog/game-engines-and-shader-stuttering-unreal-engines-solution-to-the-problem)). Fortnite compiles about 30,000 PSOs per match, and installing a driver clears the cache ([PC Gamer](https://www.pcgamer.com/hardware/graphics-cards/epic-talks-shop-about-stuttering-in-games-that-use-its-unreal-engine-and-offers-solutions-to-the-problem/)). Unreal counts any compile above 20 ms as a hitch, and one capture showed 117 ms ([Epic](https://dev.epicgames.com/documentation/en-us/unreal-engine/pso-precaching-for-unreal-engine)). DOOM Eternal ran on about 500 PSOs in total ([Coenen](https://simoncoenen.com/blog/programming/graphics/DoomEternalStudy)).

PlayMap's pipeline space is closed and small, so the whole space can be handled before the show. Enumerate every PSO when a show is armed and assert "all compiled" in preflight. If one is still missing at air time, hold the layer and record the fact rather than stall. Key the cache by adapter, device and driver, so that it re-warms automatically after a driver update. Microsoft's Advanced Shader Delivery is aimed at storefronts. Whether it is available to non-store apps is unconfirmed.

### Bindless records, measured queues and decode lanes that never block

**Bindless and GPU-driven rendering.** Ubisoft reported "1-2 orders of magnitude less drawcalls" ([SIGGRAPH 2015](https://advances.realtimerendering.com/s2015/aaltonenhaar%5Fsiggraph2015%5Fcombined%5Ffinal%5Ffooter%5F220dpi.pdf)), and id reported up to 5 ms of GPU savings in DOOM Eternal using only three indexable resource layouts in the whole game ([SIGGRAPH 2020](https://advances.realtimerendering.com/s2020/RenderingDoomEternal.pdf)). For PlayMap the gain is a render thread whose work does not grow with surface count. That requires descriptor lifetimes tied to fences: "premature release of objects in-flight is one of the top causes" of device removal ([DRED spec](https://microsoft.github.io/DirectX-Specs/d3d/DeviceRemovedExtendedData.html)).

**Queues.** AMD's guidance is to use the copy queue for uploads from system memory to VRAM, started several frames early, and to double-buffer those uploads, which in one example saved almost 10% of frame time ([AMD](https://gpuopen.com/learn/concurrent-execution-asynchronous-queues/)). Async compute can lose performance, so every async pass keeps a serial fallback and synchronises through a fixed handshake, because repeatable timing matters more to a show than peak throughput ([AMD](https://gpuopen.com/download/GDC2017-Asynchronous-Compute-Deep-Dive.pdf)).

**Video decode.** Decode lanes should run ahead of the predicted display time into a fenced ring. The render thread takes the newest ready frame and holds the last valid one, as TiXL does in C# ([TiXL](https://github.com/tixl3d/tixl/blob/main/Video/VideoPlaybackController.cs)). DirectStorage GPU decompression TDRs on corrupt data ([DirectX blog](https://devblogs.microsoft.com/directx/directstorage-1-3-is-now-available/)), so media hashes must be checked at ingest.

**Allocation discipline.** In managed code this discipline needs a fence of its own: a CI test asserting that `GC.GetAllocatedBytesForCurrentThread` is unchanged across N warm frames. One conflict needs a decision. Microsoft's game guidance recommends forcing collection on load screens ([Microsoft Learn](https://learn.microsoft.com/en-us/gaming/gdk/docs/gdk-dev/pc-dev/tutorials/get-started-with-custom-engine/native-aot-for-gaming?view=gdk-2604)), but `GC.Collect` is banned in `src/`. Any exception for show-arm needs a measured cause and a deterministic test.

## Medical devices teach stability: prove the frame the audience saw

### Prove what was displayed, not just what was presented

Medical display practice treats a frozen screen as the most dangerous failure, because it looks normal. One patent describes vital-sign frames that carry an advancing counter. A separate monitor reads the frame actually in the display buffer and alerts or blanks the screen when the counter is stale, because the operator "will not notice this situation immediately" ([US 10,383,581](https://exa.ai/library/legal/patent/51s97407qh8)). The FDA's MAUDE database records an operating-room monitor where "the screen is frozen" ([FDA MAUDE](https://www.accessdata.fda.gov/scripts/cdrh/cfdocs/cfmaude/detail.cfm?mdrfoi__id=19221498&pc=MHX)). Monitors also label an *intentional* freeze on screen ([Contec manual](https://www.scribd.com/document/362534289/Monitor-Contec-CMS8000-Service-Manual-v1-0)).

PlayMap's present ledger proves a frame was shown *according to the driver*. The missing step is "observed". Each output should carry a per-frame counter or time code in a masked, overscan or off-canvas region. An independent observer reads it back: a capture card on a loop-through, the LED processor's monitor output, or the scan camera PlayMap already drives. The observer then flags frames that are stale, torn (two codes in one capture), wrong (a code that does not match leader time) or late. That completes the doctrine's chain of sent → accepted → applied → observed for pixels. FREEZE and BLACKOUT must also be distinct states in STATE and on the desk, so that neither the observer nor the operator mistakes a deliberate hold for a fault.

### Keep the safety monitor independent of the engine

The safety architecture behind this separates an operational subsystem from a safety subsystem running on separate resources. The safety side uses thread heartbeats rather than watchdog timers, because "watchdog timers too often have been reset inappropriately" ([AAMI BI&T 2017](https://array.aami.org/doi/full/10.2345/0899-8205-51.5.380)), and it is kept "as simple as possible … functionally independent" ([MDDI](https://www.mddionline.com/design-engineering/medical-device-safety-system-design-a-systematic-approach)). Software faults are systematic, so redundancy must be *diverse* or it duplicates the bug ([Johner Institute](https://blog.johner-institute.com/systems-engineering/functional-safety/)).

Two changes follow for PlayMap. Its watchdog heartbeat should be the present ledger's shown-frame counter advancing, not a thread's tick, because a thread can tick while the picture is frozen. And the monitor should be a minimal process outside the engine.

### Treat device loss as a rehearsed event with evidence

Microsoft wants one rebuild path "similar, if not identical" to start-up, and provides a forced TDR for testing ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/uwp/gaming/handling-device-lost-scenarios)). CI should force a TDR and assert the time to the first good frame.

DRED should be on by default. It must be armed before device creation, and it tracks breadcrumbs and recently freed objects ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3d12/use-dred)). Microsoft's debugger extension then names "the first outstanding operation" as the strongest suspect ([DirectX blog](https://devblogs.microsoft.com/directx/debugger-extension-for-dred/)).

CPU crashes are best captured out of process, which also survives heap corruption and fast-fail ([Sentry](https://docs.sentry.io/platforms/native/advanced-usage/backend-tradeoffs/)). Minidumps can carry secrets ([Sentry](https://docs.sentry.io/platforms/unreal/configuration/crash-reporter/crash-reporter-client/)), which is why the dump policy above keeps full dumps local.

### Degrade gracefully when a frame is missing

Games and VR rank the fallbacks the same way. Valve calls reprojection "a last-resort safety net": its render thread resubmits the last frame's work with updated poses ([Valve, GDC 2016](https://media.steampowered.com/apps/valve/2016/Alex_Vlachos_Advanced_VR_Rendering_Performance_GDC2016.pdf)). Meta's compositor "always has the most recently submitted frame available" and counts stale frames ([Meta](https://developers.meta.com/vr/documentation/native/android/os-missed-frames/)).

PlayMap can do better than both, because content is a function of time. When a frame is missing, the engine first resubmits the last frame's GPU work at the new time, holds the last frame if that fails, and only then switches to the backup. Black appears only when show policy says so. Adaptive resolution should be refused, because it breaks blend seams.

### Borrow medical risk mechanisms, not the paperwork

What transfers from medical regulation is the *mechanisms*, not the certification. IEC 62304, the medical-device software lifecycle standard, states that software failure probability "shall be assumed to be 1", and only controls external to the software lower the risk class ([Kelsey](https://kelseyqms.com/crosswalk/iec-62304/req-iec62304-4-3)). It requires segregation between parts of the software to be designed and verified rather than asserted, and SOUP (software of unknown provenance) to be identified by exact version with its published anomaly lists reviewed ([CASRAI](https://www.casrai.org/guides/iec-62304)).

ISO 14971, the risk-management standard, fixes the order of controls: inherently safe design, then protective measures, then information. It also warns that a bottom-up FMEA "rarely" suffices alone ([spilma](https://www.spilma.com/en/guides/risk-management-iso-14971-iec-31010-fmea-fta)). Controls need verification of both implementation and *effectiveness* ([MedTechLearning](https://medtechlearning.com/learning/medical-device-risk-management.html)). The FDA expects traceability from hazard to test ([FDA](https://www.fda.gov/media/153781/download)) and an SBOM for cybersecurity ([FDA](https://www.fda.gov/regulatory-information/search-fda-guidance-documents/cybersecurity-medical-devices-quality-management-system-considerations-and-content-premarket)).

For PlayMap the translation is direct. Classify by harm to the air: render, present, sync, the show gate and PANIC get the highest rigour, while the desk, assistant and scan tools get less, which is justified only because the engine stands independent of the desk. List the air hazards (black, frozen, torn, wrong cue, a visible seam, desync, a brightness jump, a photosensitive flash, a projector misfire, a stale timecode chase, a crash) and trace each to a fault-injection test that asserts the air stayed within policy. Keep a SOUP list with locked driver and firmware versions. No source shows an entertainment vendor applying these standards formally, so this is a design tool, not a compliance claim.

### Test latency with a step signal, and switch over on observed faults

Two adjacent fields supply ready-made tests. **Flight simulation** caps transport delay at 100 ms for instrument and motion response and **120 ms for visual response** ([FAA](https://www.faa.gov/sites/faa.gov/files/2022-11/Final%20Rule%20%2014%20CFR%20part%2060-Flight%20Simulation%20Training%20Device.pdf)). It measures delay with a step signal through every module, and the higher simulator levels require automated test drivers ([FAA](https://www.faa.gov/documentLibrary/media/Advisory_Circular/Appx_1-2.pdf); [eCFR](https://www.ecfr.gov/current/title-14/chapter-I/subchapter-D/part-60/appendix-Appendix%20A%20to%20Part%2060)). That maps onto a built-in step-test verb that measures glass-to-glass latency for each output in preflight.

**Broadcast changeover** switches on detected black, freeze or loss, with hysteresis, and keeps a hardware bypass that works "even if the changeover server is powered off" ([SkyLark](https://skylark.tv/products/software-new/transmission-telecom-operators/sl-neo-changeover/)). That argues for LED-processor dual inputs or relay routers, so the failsafe does not depend on a working PC.

### Budget latency and colour like a medical display

**Latency.** Surgical studies found "significant deterioration … at 105 ms added latency" ([Kumcu et al.](https://doi.org/10.1002/rcs.1758)). One glass-to-glass test measured 41.61 ms with an exclusive display against 49.62 ms under a display manager ([RidgeRun](https://www.ridgerun.com/post/glass-to-glass-assessment-of-the-holoscan-sensor-bridge-on-a-nvidia-agx-orin)). Together these put a budget near 100 ms on IMAG and tracking, and show that bypassing the compositor is measurable.

**Colour.** DICOM's display standard calibrates to one standard curve in measured luminance, ambient light included. It warns that levels "too far apart" show contours at 8 or 10 bits ([DICOM](https://dicom.nema.org/medical/dicom/current/output/chtml/part14/chapter_A.html)). That argues for 10-bit outputs and a declared, measured reference for every projector and LED processor.

## The desk keeps Avalonia and borrows the lighting console's discipline

### Keep Avalonia

Avalonia remains the right desk framework. It is current: version 12 shipped in April 2026, 12.1 in July with far fewer compositor allocations and faster hit-testing, and the desk already runs 12.1.4 ([Avalonia 12.1](https://avaloniaui.net/blog/release-12-1); [PlayMap.App.csproj](/home/user/mapper/src/PlayMap.App/PlayMap.App.csproj)). It also offers a low-latency DXGI swap-chain mode ([Avalonia docs](https://docs.avaloniaui.net/docs/platform-specific-guides/windows)).

The alternatives are weaker for this desk. WinUI 3 has one unique asset, `SetSwapChainHandle`, which passes a swap chain from one process into another ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/windows.ui.xaml.media.dxinterop/nf-windows-ui-xaml-media-dxinterop-iswapchainpanelnative2-setswapchainhandle)). But Microsoft says its launch time and RAM use are still worse than UWP's ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/migrate-to-windows-app-sdk/what-is-supported)), and moving to it means rewriting every view. WPF hosts only Direct3D 9 surfaces, copied on every Unlock ([Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/system.windows.interop.d3dimage?view=windowsdesktop-10.0)). Dear ImGui does not support accessibility ([Dear ImGui](https://github.com/ocornut/imgui?tab=readme-ov-file)), and Qt's C# bridge is still a beta ([Qt](https://www.qt.io/blog/qt-bridges-csharp-0.3.0-beta-released)).

### Replace the preview copies with shared textures

The biggest desk win is in previews. Today a preview travels from GPU to a shared-memory ring, then into a `byte[]`, then into a `WriteableBitmap`, then back to the GPU ([PreviewSource.cs](/home/user/mapper/src/PlayMap.App/Controls/PreviewSource.cs)). That is about **2 GB/s of memory traffic per 1080p60 view and about 8 GB/s at 4K60** (computed from frame size × rate × four passes).

Avalonia's GPU interop already imports D3D11 NT-handle textures and D3D12 fence NT handles ([Avalonia API](https://docs.avaloniaui.net/api/avalonia/rendering/composition/icompositiongpuinterop); [source](https://github.com/AvaloniaUI/Avalonia/blob/main/src/Avalonia.Base/Platform/PlatformGraphicsExternalMemory.cs)). On the new path, the engine renders each preview at its displayed size into two or three shared textures with a shared fence. The desk imports each texture once, and the engine never waits on the desk. If the desk compositor's LUID differs from the engine's adapter, the desk falls back to the existing CPU ring. Whether Avalonia's ANGLE backend advertises the D3D12 fence type at run time is unverified, and should be tested first.

### Borrow the consoles' safety patterns

The best show consoles converge on a few patterns. QLab protects GO by drawing a red border while its double-GO guard is active and flashing when a GO is refused, and Esc is always panic and double-Esc always a hard stop, a binding that "cannot be changed" ([QLab](https://qlab.app/docs/v5/fundamentals/workspace-settings/); [QLab shortcuts](https://qlab.app/docs/v5/general/keyboard-shortcuts/)). ETC Eos makes blind editing unmistakable by turning the background grey and putting "Blind" on every display ([ETC](https://www.etcconnect.com/uploadedFiles/Main_Site/Documents/Public/Video_Tutorial/Eos_Family_L3_Intermediate_v3.2.pdf)). grandMA3 treats undo as a history in its Oops menu ([MA Lighting](https://help.malighting.com/grandMA3/2.3/HTML/ws_oops_overlay.html)) and, from version 2.5, dims unselected UI for dark control rooms while highlighting what is selected ([MA Lighting](https://help.malighting.com/grandMA3/2.5/HTML/rn_features-2-5.html)). Resolume and Millumin highlight every control that can be mapped to a key, MIDI or OSC ([Resolume](https://resolume.com/support/en/keyboard-shortcuts); [Millumin](https://help.millumin.com/docs/connect/interactions/)).

Vendors' own release notes show what operators hate. disguise's r30 notes fixed "small hangs while editing", slow transport response when out of focus, and flashes to black on timeline jumps ([disguise](https://help.disguise.one/designer/release-notes/r30)).

### Apply human-factors rules to every status and alarm

The desk should be treated like safety-related equipment. Status must never rely on colour alone ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)), and nothing may flash more than three times a second ([W3C](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)). Confirmations belong only on serious or irreversible actions, backed by going "to great lengths to provide undo" ([NN/g](https://www.nngroup.com/articles/confirmation-dialog/)). Hazard-related use scenarios, such as GO on the wrong output or blind mistaken for live, should run through formative and then summative evaluation with real operators, as IEC 62366-1's process lays out ([ISO](https://www.iso.org/standard/63179.html)). Responsiveness has a measured threshold: users notice drag latency at about 11 ms and tap latency at about 69 ms ([Deber et al.](https://dl.acm.org/doi/10.1145/2702123.2702300)). So STATE updates should coalesce to at most one apply per UI frame, every list should be virtualised, and every preview should show its age, greying out when stale.

## Conclusion

The API decision is really a decision about vocabulary. On Windows, the decoder, the encoder, Spout, DirectStorage, the crash tools and the desk's compositor all speak in DXGI handles and fences. An engine that speaks the same language shares frames across all of them without a single copy. A Vulkan engine spends its life translating. The less obvious decision is the operating system edition. **Windows 11 IoT Enterprise LTSC 2024** clears every 24H2 feature floor in this report and unlocks Shell Launcher and DWM-free specialized displays. Paired with the Agility SDK's app-local runtime, it gives a decade-long platform that still receives new D3D12 features. That makes the OS edition part of the renderer design, not an IT afterthought.

The second shift is in what PlayMap can honestly claim. Tearing inside an output is a solved software problem. Tearing between outputs and machines is a property of the hardware tier, and only RTX PRO cards with RTX PRO Sync remove it on Windows today. The product should therefore sell "tear-free across machines" only with that hardware, and report measured phase everywhere else. The same honesty extends the doctrine itself: the present ledger already proves "applied", and the in-picture counter read by an independent observer is the missing "observed" rung. The first measurements should run before any rewrite commits. Compare D3D12 and GL latency through the present ledger on the same show hardware. Confirm Avalonia's import of a D3D12 fence. Test the composition swapchain with D3D12 buffers. And exercise the present barrier with several swap chains on a real Sync wall. Those four results decide the schedule more than any further reading.
