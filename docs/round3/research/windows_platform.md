# Windows platform, CPU features, packaging and build versioning for an installed real-time .NET 10 media server / projection-mapping renderer (state as of October 2026)

Scope note: PlayMap today is a portable self-contained .NET exe with two processes (desk = Avalonia UI; engine = playback, FFmpeg decode, GPU render, network control, video I/O). These notes cover what an installed, Windows 11 x64-only build should use. Everything below is sourced; inferences are kept separate and marked. Where a source is a forum, vendor blog or community post rather than Microsoft/Intel/AMD primary documentation, that is stated.

---

## 1. Scheduling and timing (MMCSS, priorities, CPU Sets, QoS/EcoQoS, hybrid and X3D CPUs, power throttling, timers, GPU priority, HAGS, power plans, what .NET offers)

### Takeaway
Windows 11 gives a real-time renderer four independent levers that must all be set explicitly, because the defaults now actively work against an unattended or partly-occluded app: (1) CPU priority (process class + per-thread priority, or MMCSS tasks for the deadline threads), (2) Quality of Service / power throttling (explicitly opt the engine into HighQoS and "always honor timer resolution", otherwise Windows 11 downgrades QoS and ignores timer requests for minimized/occluded/inaudible windows), (3) soft core placement via CPU Sets rather than hard affinity (Intel and Microsoft both say avoid affinity on hybrid parts), and (4) GPU scheduling priority (D3D12 queue priority / DXGI GPU thread priority / D3DKMT process class; the realtime tiers need SeIncreaseBasePriorityPrivilege, i.e. an elevated or specially-privileged process). Timing should be measured with QPC (Stopwatch) and slept with high-resolution waitable timers, not with `timeBeginPeriod` + `Sleep`. .NET 10 exposes only process priority class, thread priority and hard affinity; MMCSS, QoS, CPU Sets, high-resolution waitable timers and GPU priority all need P/Invoke.

### Cited Findings

**Timer resolution (timeBeginPeriod) — behaviour changed; old guidance no longer applies**
- Before Windows 10 2004, `timeBeginPeriod` changed a global setting (lowest value requested by any process won). Since Windows 10 2004 it "no longer affects global timer resolution"; only processes that call it get the higher resolution, and processes that have not called it get no guarantee beyond the default system resolution. — [timeBeginPeriod (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)
- Starting with Windows 11, if a window-owning process becomes "fully occluded, minimized, or otherwise invisible or inaudible to the end user", Windows does not guarantee a higher resolution than the default. Higher resolution "does not improve the accuracy of the high-resolution performance counter" and can prevent CPU power-saving states. — [timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)
- The Windows 11 occlusion behaviour can be overridden: `SetProcessInformation(ProcessPowerThrottling)` with `ControlMask = PROCESS_POWER_THROTTLING_IGNORE_TIMER_RESOLUTION` and `StateMask = 0` means "Always honor Timer Resolution Requests"; setting both masks to that flag makes Windows ignore the process's timer requests. — [SetProcessInformation (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)

**High-resolution waitable timers and QPC**
- `CreateWaitableTimerExW(..., CREATE_WAITABLE_TIMER_HIGH_RESOLUTION (0x2), ...)` "Creates a high resolution timer. Use this value for time-critical situations when short expiration delays on the order of a few milliseconds are unacceptable." Supported from Windows 10 1803. — [CreateWaitableTimerExW (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createwaitabletimerexw)
- QPC is the primary API for high-resolution time stamps; `System.Diagnostics.Stopwatch` uses QPC. QPC is not synchronized to any external reference; for cross-machine time-of-day stamps (with NTP/PTP), use `GetSystemTimePreciseAsFileTime`. QPC is preferred over reading the TSC directly. — [Acquiring high-resolution time stamps (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/sysinfo/acquiring-high-resolution-time-stamps)

**QoS levels, EcoQoS and power throttling**
- Windows QoS levels: High (foreground/in-focus, audible, or explicitly tagged via SetProcessInformation/SetThreadInformation), Medium (visible but not in focus; also foreground app after user inactivity on battery, feature "Ge 2025.05"), Low (not visible or audible), Utility (background services, Windows 11 22H2), Eco (explicit opt-in), Media (MMCSS batch buffering threads, Windows 10 2004), Deadline (MMCSS audio threads that must meet deadlines, 2004). On heterogeneous CPUs, QoS "may restrict scheduling to a subset of processors". — [Quality of Service (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Window state drives QoS for window-owning processes: In Focus → High, Visible → Medium, Minimized/Fully occluded → Low. Processes not classified by these sources get a heuristic level, where "threads running with reduced thread priority can imply a lower QoS level". — [Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- The user-inactivity QoS reduction can be disabled with `HKLM\SYSTEM\CurrentControlSet\Control\Power\PowerThrottling\DisableUserPresenceQos = 1` (REG_DWORD). Microsoft notes automated tests without input can trigger it and skew results. — [Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- Opting into `PROCESS_POWER_THROTTLING_EXECUTION_SPEED` classifies the process as EcoQoS (lower frequency, efficient cores); "EcoQoS should not be used for performance critical or foreground user experiences". To force HighQoS: `ControlMask = PROCESS_POWER_THROTTLING_EXECUTION_SPEED`, `StateMask = 0`. If the app sets nothing, "the system will use its own heuristics". Per-thread equivalent: `SetThreadInformation(ThreadPowerThrottling)` with `THREAD_POWER_THROTTLING_EXECUTION_SPEED`. — [SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation); [Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)
- `ProcessMemoryPriority` (MEMORY_PRIORITY_INFORMATION) lowers the memory priority of pages so they are trimmed first; recommended for background/indexing work, not for hot data. — [SetProcessInformation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-setprocessinformation)

**MMCSS**
- Threads join an MMCSS task with `AvSetMmThreadCharacteristics` / `AvSetMmMaxThreadCharacteristics`. Default tasks: Audio, Capture, Distribution, Games, Playback, Pro Audio, Window Manager (registry `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Multimedia\SystemProfile\Tasks`). — [MMCSS (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)
- Scheduling categories: High = priority 23–26 ("lower than only certain system-level tasks… designed for Pro Audio"); Medium = 16–22 (foreground app); Low = 8–15; 1–7 once quota is used. `SystemResponsiveness` sets the % of CPU reserved for low-priority tasks (rounded down to multiples of 10; <10 or >100 clamp to 20; 100 disables MMCSS). The per-task "GPU Priority" value "is not yet used"; "Clock Rate" guarantee was removed in Windows 7; "SFIO Priority" is not used. — [MMCSS](https://learn.microsoft.com/en-us/windows/win32/procthread/multimedia-class-scheduler-service)
- MMCSS-tagged threads are placed in the Media and Deadline QoS levels (since Windows 10 2004). — [Quality of Service](https://learn.microsoft.com/en-us/windows/win32/procthread/quality-of-service)

**Process/thread priority classes**
- Base priorities are 0–31; `REALTIME_PRIORITY_CLASS` "interrupts system threads that manage mouse input, keyboard input, and background disk flushing" and "you should almost never use" it; `HIGH_PRIORITY_CLASS` should be reserved for threads that run briefly for time-critical events; a common pattern is a high-priority process whose threads are mostly blocked. — [Scheduling Priorities (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities)
- Setting a process to Realtime requires `SeIncreaseBasePriorityPrivilege`; without it the highest settable class is High. — [Win32_Process.SetPriority (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/setpriority-method-in-class-win32-process)

**CPU Sets, hybrid (Intel P/E) and affinity**
- CPU Sets declare "soft" affinity "compatible with OS power management"; Process Default CPU Sets can re-home all non-assigned threads of the process (to keep them off cores reserved for critical threads); some Windows versions support Core Reservation (exclusive CPU Sets for one app); a restrictive hard affinity mask overrides CPU Sets. APIs: `GetSystemCpuSetInformation`, `SetProcessDefaultCpuSets(/Masks)`, `SetThreadSelectedCpuSets(/Masks)`. — [CPU Sets (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/procthread/cpu-sets)
- Intel: group logical processors by `EfficiencyClass` (from `GetSystemCpuSetInformation` or `GetLogicalProcessorInformationEx`), not by CPUID core type; `SetThreadSelectedCpuSets` can exceed the 64-LP limit of `SetThreadAffinityMask`. Control strength ranges from weak hints (`SetThreadIdealProcessor`, `SetThreadPriority`) through `SetThreadInformation` and CPU Sets to hard `SetThreadAffinityMask`. Thread Director requires Windows 11. — [Intel Game Dev Guide for 12th Gen hybrid](https://www.intel.com/content/www/us/en/developer/articles/guide/12th-gen-intel-core-processor-gamedev-guide.html)
- Intel hybrid scheduling on Windows "is QoS and then priority-driven"; "In general, software should avoid setting affinity"; if affinity is needed use CPU Sets. If apps do not use the power-throttling APIs, Windows' automatic classification may misplace threads. Hybrid P/E cores have symmetric ISA ("converged to a common baseline"). — [Intel: Optimizing Software for Performance Hybrid Architecture (PDF)](https://cdrdv2-public.intel.com/685869/optimizing%20_software_for_performance_hybrid_architecture.pdf)
- Intel 2024 threading guidance: separate critical-path (per-frame) and background thread pools; bump critical-path threads to ABOVE_NORMAL or "2 above general workers" only if they are a small subset of work; soft-affinitize background work to lower-performance cores (EcoQoS or `SetThreadIdealProcessor`); "only use hard affinity if work must never migrate"; filter out the low-power E-cores (e.g. Core Ultra LP E-cores) using relative performance + cache hierarchy; do not mix SIMD-heavy and scalar work on the same thread because Thread Director classifies per thread; "Windows uses priority to sort which threads get executed, not necessarily where they get run". — [Intel: Optimizing Threading for Gaming Performance](https://www.intel.com/content/www/us/en/developer/articles/technical/optimizing-threading-for-gaming-performance.html)
- Windows core parking parameters (CPMinCores, CPMaxCores, CPIncreaseTime, CPDecreaseTime, CPHeadroom) govern unparking; long-running/high-priority/focus-app threads get favored-core priority. — [Intel GameDev 2023 "Programming for Hybrid" slides (PDF)](https://game.intel.com/wp-content/uploads/2024/02/GameDev2023_Hybrid_Profiling-2023_v1.pdf)

**AMD dual-CCD X3D (7950X3D/7900X3D/9950X3D/9900X3D)**
- Only one CCD carries 3D V-Cache; while a "game" runs, the AMD 3D V-Cache Performance Optimizer (chipset driver) parks the other CCD. Detection relies on Windows Game Mode + Xbox Game Bar ("Remember this is a game"); recommended setup is the Balanced power plan (not High/Ultimate), Game Mode on, BIOS "CPPC Dynamic Preferred Cores = Driver"; alternatives are BIOS "Cache" preference. — [FPSHQ wiki (secondary, enthusiast)](https://fpshq.com/en/wiki/core-parking/); corroborated by users on [AMD community forum (2025)](https://pcforum.amd.com/s/question/0D5KZ000016mPti0AE/more-aggressive-core-parking-on-9950x3d)
- For 9950X3D/9900X3D AMD updated the chipset driver: Provisioning Packages Service now re-detects the CPU each boot (no Windows reinstall after CPU swap), the V-Cache Optimizer works with VBS on Windows 10, and a new Application Compatibility Database "reduces the thread pool size" for a fixed list of titles. Software not identified as a game may not trigger parking. — [VideoCardz (2025)](https://videocardz.com/newz/amd-confirms-chipset-driver-updates-and-new-features-for-ryzen-9-9950x3d-9900x3d); [Neowin (2025-03-11)](https://www.neowin.net/news/amd-makes-cpu-changing-easy-as-you-wont-need-to-reinstall-windows-1110-any-more/); [PC Perspective review (2025-03-11)](https://pcper.com/2025/03/amd-ryzen-9-9950x3d-processor-first-look-review/)

**GPU scheduling priority**
- `D3DKMTSetProcessSchedulingPriorityClass(hProcess, D3DKMT_SCHEDULINGPRIORITYCLASS)` (gdi32.dll) sets a process's GPU scheduling class: IDLE, BELOW_NORMAL, NORMAL, ABOVE_NORMAL, HIGH, REALTIME. — [D3DKMTSetProcessSchedulingPriorityClass](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/nf-d3dkmthk-d3dkmtsetprocessschedulingpriorityclass); [D3DKMT_SCHEDULINGPRIORITYCLASS](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmthk/ne-d3dkmthk-_d3dkmt_schedulingpriorityclass)
- `IDXGIDevice::SetGPUThreadPriority`: relative mode −7…+7 (0 normal); absolute mode (bit 30, Windows 10+): 0 idle, 1 normal, 16–29 "Soft Realtime — preempts lower priorities and periodically yields", 30 "Hard Realtime — … does not yield to lower priorities", 31 internal. Microsoft warns it "can impede rendering speed"; profile first. — [IDXGIDevice::SetGPUThreadPriority](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgidevice-setgputhreadpriority)
- D3D12: `D3D12_COMMAND_QUEUE_PRIORITY_NORMAL (0)`, `HIGH (100)`, `GLOBAL_REALTIME (10000)`; GLOBAL_REALTIME requires the app to be "sufficiently privileged" and adapter/driver preemption support, and creation fails rather than silently downgrading. — [D3D12_COMMAND_QUEUE_PRIORITY](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ne-d3d12-d3d12_command_queue_priority)
- Newer D3D12 dynamic priority (`D3D12_COMMAND_QUEUE_FLAG_ALLOW_DYNAMIC_PRIORITY`, `ID3D12CommandQueue1::SetGlobalPriority/SetProcessPriority`) maps GLOBAL_REALTIME to `GLOBAL_PRIORITY_HARD_REALTIME` and adds SOFT_REALTIME_0…13 levels. — [DirectX-Specs: CommandQueue Dynamic Priority](https://microsoft.github.io/DirectX-Specs/d3d/D3D12_CommandQueue_Dynamic_Priority.html)
- Practical example: Xenia enables `SeIncreaseBasePriorityPrivilege` via `AdjustTokenPrivileges` before creating a GLOBAL_REALTIME queue and falls back to HIGH with the message "try launching … as administrator". — [Xenia d3d12_provider.cc (GitHub)](https://github.com/xenia-project/xenia/blob/master/src/xenia/ui/d3d12/d3d12_provider.cc)

**HAGS**
- Hardware-accelerated GPU scheduling arrived in Windows 10 2004 (May 2020) as an opt-in, off-by-default option needing supporting GPUs + WDDM 2.7 drivers; it offloads quanta management and context switching to a GPU scheduling processor while Windows keeps control of prioritization. Toggle: Settings → System → Display → Graphics. — [DirectX Dev Blog: Hardware Accelerated GPU Scheduling (2020-06-30)](https://devblogs.microsoft.com/directx/hardware-accelerated-gpu-scheduling/)

**Power plans**
- Ultimate Performance (Windows 10 1803+) is "designed to reduce micro-latencies", shown by default only on Pro for Workstations, not available on battery-powered systems, and exposed elsewhere by `powercfg -duplicatescheme e9a42b02-d5df-448d-aa00-03f14749eb61` (generates a new per-machine GUID; then `powercfg -setactive`). — [Winaero (2018)](https://winaero.com/enable-ultimate-performance-power-plan-in-windows-10/); [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/3808904/ultra-performance-mode); [Atera guide (deployment script, GPO note)](https://www.atera.com/blog/how-to-enable-ultimate-performance-power-plan-in-windows-11/)
- Pro audio vendor guidance (Universal Audio): High performance plan; PCI Express Link State Power Management Off; Minimum/Maximum processor state 100%; USB selective suspend Disabled; sleep/hibernate/display/disk never. — [UA: Optimizing Windows for UA Devices](https://help.uaudio.com/hc/en-us/articles/27247945568788-Optimizing-Windows-for-UA-Devices)
- Conflict: on dual-CCD X3D CPUs the AMD parking mechanism expects the Balanced plan; High/Ultimate Performance plans defeat it. — [FPSHQ (secondary)](https://fpshq.com/en/wiki/core-parking/)

### Inferences
- Engine process at startup (all P/Invoke, none exist in .NET 10's BCL): `SetPriorityClass(HIGH_PRIORITY_CLASS)` (not REALTIME); `SetProcessInformation(ProcessPowerThrottling)` with EXECUTION_SPEED and IGNORE_TIMER_RESOLUTION both in ControlMask and StateMask = 0 (explicit HighQoS and always-honor timers — the engine owns a fullscreen output window that may be occluded by the desk or vice versa); `D3DKMTSetProcessSchedulingPriorityClass(HIGH)` (REALTIME only if the engine runs with SeIncreaseBasePriorityPrivilege, and only after measurement — "measured, then governed").
- Thread roles: present/vsync-pacing thread → MMCSS "Games" or "Playback" (category Medium/High) or "Pro Audio" (High, 23–26) only for the audio/timecode clock thread; decode workers → ABOVE_NORMAL or NORMAL on P-cores via CPU Sets; network/control threads → NORMAL; background (thumbnailing, media scan, upload) → EcoQoS per thread. Use `AvRevertMmThreadCharacteristics` on shutdown (owned resource).
- Prefer CPU Sets (soft) + EfficiencyClass grouping over `Process.ProcessorAffinity` (hard, ≤64 LPs). On dual-CCD X3D, the engine will not be recognised as a game by default; options are to document "mark PlayMap as a game in Game Bar", set BIOS CPPC to Cache, or have the engine itself restrict its critical pool to the CCD whose LPs share the largest L3 (derivable from GetLogicalProcessorInformationEx cache relationships). This needs measurement on real 9950X3D hardware.
- Frame pacing: "frame = f(leader time at vblank)" fits naturally with QPC timestamps + DXGI waitable swap chain / vblank waits; any software sleeps should use a HIGH_RESOLUTION waitable timer, never `Thread.Sleep` (already banned in src/) or `Task.Delay` (thread-pool timer granularity).
- What .NET 10 offers: `Process.PriorityClass`, `Thread.Priority` (maps to SetThreadPriority levels), `Process.ProcessorAffinity`, `Stopwatch` (QPC). What it lacks (no managed wrapper found in the .NET 10 what's-new or BCL docs consulted): MMCSS, QoS/power throttling, CPU Sets, high-resolution waitable timers, GPU scheduling priority, `SetThreadExecutionState`. A small `PlayMap.Platform.Windows` seam with LibraryImport bindings is the natural home. (Inference from absence; not an explicit Microsoft statement.)
- HAGS should be treated as a machine-profile variable to record in STATE/health (on/off), not something the installer flips; measured A/B on the target GPU decides.

### Gaps
- Whether HAGS is now on by default on fresh Windows 11 24H2/25H2 installs with current NVIDIA/AMD drivers, and current pro-AV vendor (disguise/Pixera/Resolume) recommendations on HAGS: not found in primary sources.
- Exact privilege required by `D3DKMTSetProcessSchedulingPriorityClass(REALTIME)` is not stated on its doc page; the D3D12 page only says "sufficiently privileged" (Xenia's code implies SeIncreaseBasePriorityPrivilege/admin).
- Microsoft documentation of Game Mode's effect on non-game apps (beyond the AMD parking trigger) was not found.
- No primary AMD whitepaper for the 3D V-Cache Optimizer was retrieved; the AMD findings above are from press and enthusiast sources.
- Windows 11 "Core Reservation" CPU Set policy: which editions expose it and how an app requests it was not documented in the pages read.

## 2. Memory and I/O (large pages, working set, GC modes for low latency, unmanaged frame buffers, DirectStorage, unbuffered/overlapped I/O, NVMe)

### Takeaway
For a render/decode engine, the GC strategy that matters is "don't allocate on the hot path" plus Workstation concurrent GC with `SustainedLowLatency` during shows; Server GC/DATAS optimise throughput and heap size, not pause latency. Frame buffers belong in unmanaged, pre-allocated (optionally large-page) memory allocated once at startup. DirectStorage 1.3 is a GPU-asset streaming API (NVMe → GPU buffers/textures with GDeflate) — useful only for GPU-native, chunk-compressed frame formats (image sequences / texture-codec frames), not for FFmpeg bitstreams.

### Cited Findings
**Large pages and memory locking**
- Large pages require `SeLockMemoryPrivilege` (AdjustTokenPrivileges), size/alignment multiples of `GetLargePageMinimum()`, `VirtualAlloc(MEM_RESERVE|MEM_COMMIT|MEM_LARGE_PAGES)` reserved and committed in one call; memory is nonpageable, counted in private bytes but not the working set; allocations become hard to obtain after long uptime due to fragmentation, so "allocate all large pages one time, at startup". — [Large-Page Support (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/memory/large-page-support)
- .NET GC large pages: `DOTNET_GCLargePages=1` (.NET 6+), used together with a heap hard limit; the docs list no runtimeconfig.json name, while the runtime source declares a public name `System.GC.LargePages` (values: 1 = real large pages, 2 = emulation). — [GC config settings (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector); [gcconfig.h (dotnet/runtime)](https://github.com/dotnet/runtime/blob/bbdd508a/src/coreclr/gc/gcconfig.h). The GC must commit the whole reserve up front and the process needs SeLockMemoryPrivilege; TLB-miss gains quoted at "a few percent to 20%". — [dotnet/runtime#10476](https://github.com/dotnet/runtime/issues/10476)

**GC modes**
- Workstation vs Server: `System.GC.Server` / `ServerGarbageCollection` (default Workstation); background GC `System.GC.Concurrent` (default true). Settings are read only at GC init. — [GC config settings](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector)
- Since .NET 9, environment variables take precedence over MSBuild properties and runtimeconfig.json. — [.NET runtime config options (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/)
- DATAS (opt-in in .NET 8, default in .NET 9+) adapts heap size to long-lived data, starts with one heap and grows/shrinks heap count, does more Gen0/Gen1 GCs; TechEmpower showed 2–3% lower max RPS for >80% working-set reduction; Server GC by contrast "treats the process as the dominant one on the machine". — [DATAS (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/datas)
- `GCLatencyMode.LowLatency` (workstation only) suppresses gen2 for short periods; `SustainedLowLatency` suppresses foreground (blocking) gen2 and allows background gen2, usable for long periods on workstation or server GC, requires background GC, grows the heap and does not compact (fragmentation). Scenarios explicitly include "applications that render animations". Gen2 still occurs on OS low-memory notification or explicit `GC.Collect(2)`. — [Latency Modes (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/latency)
- `System.GC.ConserveMemory` / `DOTNET_GCConserveMemory` 0–9 (.NET 6+): trades more frequent GCs and possibly longer pauses for a smaller heap; non-zero auto-compacts a fragmented LOH. — [GC config settings](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector)
- Other relevant knobs: `System.GC.LOHThreshold` (default 85,000 bytes), `System.GC.HeapHardLimit(Percent)`, `System.GC.RetainVM`, `GCHeapCount`, `GCNoAffinitize`; runtime has `GCEnabledInstructionSets` for AVX2/AVX-512 in GC. — [GC config settings](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/garbage-collector); [gcconfig.h](https://github.com/dotnet/runtime/blob/bbdd508a/src/coreclr/gc/gcconfig.h)

**DirectStorage**
- DirectStorage 1.3 released 2025-07-01 (NuGet `Microsoft.Direct3D.DirectStorage`): new `IDStorageQueue3::EnqueueRequests` batches requests and synchronizes them with a D3D12 fence; new `DSTORAGE_DESTINATION_MULTIPLE_SUBRESOURCES_RANGE`. GPU decompression of corrupted GDeflate data causes a driver TDR (CPU path now fails cleanly). — [DirectStorage 1.3 is now available (DirectX blog)](https://devblogs.microsoft.com/directx/directstorage-1-3-is-now-available/); [NuGet changelog](https://www.nuget.org/packages/Microsoft.Direct3D.DirectStorage/)
- Earlier versions added GDeflate GPU decompression (1.1), buffered file IO option for HDDs, `GetCompressionSupport`, and a `.winmd` "to ease generation of non-C++ bindings". — [NuGet changelog](https://www.nuget.org/packages/Microsoft.Direct3D.DirectStorage/)
- Each request's data must be independently decompressible (compress per chunk, not per file); requests must fit the staging buffer (`SetStagingBufferSize`); Enqueue blocks when the queue is full (size queues ~2× the expected maximum); BypassIO can be forced off for testing. — [DirectStorage Developer Guidance (GitHub)](https://github.com/microsoft/DirectStorage/blob/main/Docs/DeveloperGuidance.md)
- NVIDIA: raise the 32 MB default staging buffer to ~128 MB with GPU decompression; keep DirectStorage-read files separate from files accessed by other I/O APIs or lose BypassIO gains; on Windows 11, overlap of DirectStorage and app queues is expected — throttle reads if it hurts the app. — [NVIDIA Technical Blog (2022)](https://developer.nvidia.com/blog/accelerating-load-times-for-directx-games-and-apps-with-gdeflate-for-directstorage/)
- The DirectStorage SDK downloads page also lists Zstd support, Game Asset Conditioning Library and D3D12 CreatorID support, suggesting a release newer than 1.3 exists; version/date not confirmed. — [DirectStorage SDK & API (DirectX blog)](https://devblogs.microsoft.com/directx/directstorage-api-downloads/)

### Inferences
- Engine GC profile: Workstation + Concurrent (default), `GCSettings.LatencyMode = SustainedLowLatency` while SHOW is live (revert when idle), no Server GC/DATAS for the engine (multi-heap Server GC adds GC threads competing with render/decode threads and grows heap aggressively). Gate this with a measured pause histogram (e.g. EventPipe GC events) before/after — the doctrine's "measured, then governed".
- Frame/plane pools: allocate once at startup via `NativeMemory.AlignedAlloc` or `VirtualAlloc` (large pages where SeLockMemoryPrivilege is granted by the installer to the engine's account — privilege grant is a per-machine install action), wrap in `SafeHandle`/owned pool types (the analyzers require disposing what you own). GC large pages are less attractive than unmanaged large-page pools because they require a hard heap limit and commit the whole range.
- DirectStorage is relevant only if PlayMap adds a GPU-native frame format (e.g. per-frame GDeflate-compressed BCn textures or image sequences); FFmpeg-decoded H.264/HEVC/ProRes still go through CPU/hardware decoders. It is D3D12-only, so it fits the D3D12 render path, not GL.
- Media read path today: sequential, large reads with `FileOptions.SequentialScan` + async I/O; unbuffered I/O (`FILE_FLAG_NO_BUFFERING`, sector-aligned buffers) only if measured page-cache pressure appears on multi-stream 8K playback.

### Gaps
- Primary documentation for `FILE_FLAG_NO_BUFFERING` alignment rules and .NET's lack of a `FileOptions.NoBuffering` value was not retrieved.
- `VirtualLock` / `SetProcessWorkingSetSizeEx` (working-set locking) semantics and quotas not retrieved.
- `GC.TryStartNoGCRegion` limits (size cap relative to segment/region size in .NET 7+ regions GC) not retrieved.
- Whether DATAS applies only under Server GC is implied but not stated verbatim in the DATAS page read.
- No benchmark data found comparing Workstation vs Server vs DATAS GC pause times for a real-time render workload.

## 3. CPU features in .NET 10 (intrinsics, AVX2/AVX-512/AVX10, Vector128–512, TensorPrimitives, NativeAOT vs JIT/PGO/R2R, tiering stalls)

### Takeaway
Write vector code against `Vector128/256/512` with `IsHardwareAccelerated` guards (JIT-time constants) and prefer `TensorPrimitives` for bulk math; AVX10.2 exists in .NET 10 but is disabled by default. Tiered compilation means the first calls into render/decode paths run unoptimised tier-0 code and then swap; for a show engine either pre-warm before going live, publish ReadyToRun, disable tiering for the engine, or move to NativeAOT — but NativeAOT forbids built-in COM interop, which matters for DXGI/D3D/MF unless the interop is source-generated.

### Cited Findings
- .NET 10 adds `System.Runtime.Intrinsics.X86.Avx10v2`; "Because AVX10.2-enabled hardware isn't yet available, the JIT's support for AVX10.2 is currently disabled by default." .NET 10 JIT also improves struct-argument promotion, loop inversion, array-interface devirtualization, 3-opt block layout, and stack allocation of small arrays/delegates (fewer GC allocations). — [What's new in .NET 10 runtime (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/runtime)
- In .NET 10 the JIT treats AVX-512 F+BW+CD+DQ+VL as a single ISA and, per Intel's spec change, "AVX10 is now a strict superset of AVX512 and requires V512 support". — [dotnet/runtime PR #115983 (2025-05)](https://github.com/dotnet/runtime/pull/115983)
- Microsoft's SIMD guidance: start with `Vector128`, add wider widths only for measured hot paths; `IsHardwareAccelerated`, `IsSupported` and `Count` are JIT constants (don't cache them); `TensorPrimitives` gives ready-made vectorized span math. Diagnostics knobs: `DOTNET_EnableAVX512`, `DOTNET_EnableAVX10v1`, `DOTNET_EnableAVX10v2` (default 0), `DOTNET_PreferredVectorBitWidth` (e.g. 256 makes `Vector512.IsHardwareAccelerated` false), `DOTNET_MaxVectorTBitWidth` (`Vector<T>` may stay 256-bit even when 512 is accelerated). The page notes knob names were reconfigured across releases and lists the .NET 11 set. — [Use SIMD and hardware intrinsics in .NET (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/standard/simd)
- `TensorPrimitives` gained Half vectorization for dozens of operators (e.g. Add 800 elements: 5,119 ns → 897 ns on AVX2). — [dotnet/runtime PR #116934](https://github.com/dotnet/runtime/pull/116934)
- Community report (not yet a confirmed Microsoft finding): explicit `Vector256` code regressed ~71–73% on .NET 10.0.5 vs .NET 8 on AVX-512 Tiger Lake due to EVEX register allocation (ymm16+) and a longer `Sum()` lowering; `Vector<T>` improved 3–6%. — [dotnet/runtime#126250](https://github.com/dotnet/runtime/issues/126250)
- Tiered compilation (default on since .NET Core 3.0): tier 0 = quick JIT or ReadyToRun code, tier 1 = optimized JIT in the background; `TieredCompilation=false` disables; `TieredCompilationQuickJit=false` makes non-R2R methods compile fully optimized on first call; `TieredPGO` enables Dynamic PGO (instrumentation during tier 0). The doc states omitting `QuickJitForLoops` means loops are not quick-jitted. — [Compilation config settings (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/core/runtime-config/compilation)
- .NET 10 JIT inlining uses profile data more aggressively (larger size tolerance for hot callees). — [What's new in .NET 10 runtime](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-10/runtime); see also [Performance Improvements in .NET 10 (2025-09-10)](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-10/)
- NativeAOT: no JIT at runtime, faster startup, smaller footprint, but: no `Assembly.LoadFile`, no `Reflection.Emit`, no C++/CLI, "Windows: No built-in COM", trimming required, single-file implied, LINQ Expressions interpreted, all generic instantiations pre-generated (size growth); supported on Windows x64/Arm64/x86 (.NET 9+); debug info in a separate .pdb. `IsAotCompatible` metadata introduced in .NET 10; `VerifyReferenceAotCompatibility` warns (IL3058) on unannotated references. — [Native AOT deployment overview (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)
- Single-file and NativeAOT apps only support full dumps for .NET's crash-dump feature. — [Collect dumps on crash (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/collect-dumps-crash)
- Intel hybrid client parts expose a symmetric ISA common to P- and E-cores. — [Intel hybrid optimization PDF](https://cdrdv2-public.intel.com/685869/optimizing%20_software_for_performance_hybrid_architecture.pdf)

### Inferences
- Because hybrid Intel client CPUs expose only the ISA common to P- and E-cores, AVX-512 paths will mostly light up on AMD Zen 4/5 and Intel workstation/server parts; code must remain correct and fast at 256-bit. Benchmark explicit `Vector256` vs `Vector<T>` vs `TensorPrimitives` on the actual show-machine CPUs given the .NET 10 regression report.
- Tiering stalls on the render thread: (a) publish the engine ReadyToRun (removes most first-call JIT, but R2R code is later re-jitted at tier 1 in the background and generic instantiations across assemblies may still JIT); (b) run a "pre-roll" that exercises every per-frame path (all shaders/passes, decode, blend, output) before the node reports itself ready on the wire; (c) for maximum determinism, set `TieredCompilation=false` for the engine only (fully-optimized first JIT, loses Dynamic PGO) or `TieredPGO=false`; (d) NativeAOT eliminates JIT entirely but requires source-generated COM (`ComWrappers`/`[GeneratedComInterface]`) for DXGI/D3D11/D3D12/Media Foundation and AOT-safe Avalonia/serialization — a large migration to scope separately. A measured comparison (frame-time p99.9 over first 10 minutes) should pick between (b)+(a) and (d).
- The desk (Avalonia UI) benefits from R2R/startup work; the engine benefits from no-JIT determinism. They can use different publish modes since they are separate processes.

### Gaps
- Conflict to verify: the compilation-config doc says loops are not quick-jitted when `QuickJitForLoops` is omitted, whereas .NET 7+ release material (not retrieved here) describes QuickJitForLoops + OSR as on by default on x64. Verify against .NET 10 behaviour before relying on either.
- NativeAOT instruction-set targeting (`IlcInstructionSet`, e.g. x86-x64-v3) documentation could not be fetched (network/DNS failure on the optimizing page).
- No source found on whether Avalonia 12 is fully NativeAOT/trim-compatible.
- Status of dotnet/runtime#126250 (fixed in a .NET 10 servicing release or not) unknown.

## 4. Packaging and install (MSIX vs MSI/WiX vs Velopack vs Inno; per-machine; service vs user process; firewall; mDNS; kiosk/auto-start; update policy; signing; SmartScreen; redistributables)

### Takeaway
For a per-machine show-node install, an MSI (WiX v7) or Velopack's MSI (`--instLocation PerMachine`) is the pragmatic choice; MSIX now supports packaged services and firewall rules but forbids drivers, virtualizes HKLM/AppData writes, and its version rules differ. The engine must not be a Session-0 service if it drives displays (services cannot reach the interactive desktop); run it in an auto-logged-on user session (Shell Launcher on Enterprise/IoT, or auto-logon + startup task), optionally supervised by a small service. Sign with Azure Artifact Signing (formerly Trusted Signing); since 2024 EV certificates no longer bypass SmartScreen.

### Cited Findings
**MSI / WiX**
- WiX v7.0.0 released 2026-04-06 (v6.0.0 2025-04-07, v6.0.2 2025-08-28); delivered as MSBuild SDK (`WixToolset.Sdk`) and .NET tool (`dotnet tool install --global wix --version 7.0.0`). — [WiX release notes (FireGiant)](https://docs.firegiant.com/wix/whatsnew/releasenotes/); [NuGet: wix 7.0.0](https://www.nuget.org/packages/WiX/)
- WiX binaries are under the Open Source Maintenance Fee: organisations with >$10,000 annual revenue must sponsor `wixtoolset` on GitHub; v7 enforces EULA acceptance (EULA ID `wix7`, via an MSBuild property for CI); the fee is per entity, not per product. — [OSMF (FireGiant docs)](https://docs.firegiant.com/wix/osmf/); [wixtoolset/issues#8974](https://github.com/wixtoolset/issues/issues/8974)
- MSI `ProductVersion` is `major.minor.build` with major ≤255, minor ≤255, build ≤65,535; Windows Installer ignores a fourth field; at least one of the three fields must change for a major upgrade. — [ProductVersion property (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/msi/productversion)

**Velopack**
- `Setup.exe` is per-user, installs to `%LocalAppData%\{packId}` without elevation (`--installto` overrides). The `--msi` option produces a true MSI with `--instLocation PerUser|PerMachine|Either`; PerMachine installs to `Program Files\{publisher}\{packTitle}` (HKLM, elevation); admins can override with `VELOPACK_INSTALLDIR`; `--msiVersion` must be a valid MSI version. — [Velopack: Windows overview](https://docs.velopack.io/packaging/operating-systems/windows); [Velopack: Installers](https://docs.velopack.io/packaging/installer)
- Velopack supports only SemVer2 three-part versions with tags/metadata (e.g. `1.0.0-build.23+metadata`), not 4-part versions; suggests nbgv for git-based versioning. — [Velopack FAQ](https://docs.velopack.io/troubleshooting/faq); [Velopack packaging overview](https://docs.velopack.io/packaging/overview)
- Velopack's MSI work brings elevated hooks for all-users installs but "does not add support for system services" (roadmap, no ETA at the time). — [velopack PR #606](https://github.com/velopack/velopack/pull/606); earlier rejection of Squirrel's "machine-wide" hack: [velopack#32](https://github.com/velopack/velopack/issues/32)

**MSIX**
- MSIX supports per-machine (session-0) services under LocalSystem/LocalService/NetworkService (`desktop6:Service`, restricted capability `packagedServices` or `localSystemServices`), Windows 10 2004+, admin required to install; no per-user services; no drivers; HKLM writes go to an isolated per-app hive and AppData is redirected to a private store. — [Know your installer (MSIX)](https://learn.microsoft.com/en-us/windows/msix/packaging-tool/know-your-installer); [desktop6:Service schema](https://learn.microsoft.com/en-us/uwp/schemas/appxpackage/uapmanifestschema/element-desktop6-service); [MSIX deployment targets](https://learn.microsoft.com/en-us/windows/msix/desktop/managing-your-msix-deployment-targetdevices); [Prepare to package (msix-docs)](https://github.com/microsoftdocs/msix-docs/blob/main/msix-src/desktop/desktop-to-uwp-prepare.md)
- MSIX can declare firewall exceptions with `desktop2:Extension Category="windows.firewallRules"` (Direction, IPProtocol, port ranges, Profile); requires the full-trust restricted capability. — [Desktop app extensions (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/desktop-to-uwp-extensions)

**Service vs user process (session 0)**
- Since Vista, services cannot directly interact with a user; all services run in session 0; `NoInteractiveServices` defaults to 1. — [Interactive Services (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)
- Under WDDM session-0 isolation "a Direct3D 9 HAL device is never available from a Windows service"; Microsoft's (D3D9/10-era) table shows only WARP10 available in a service. — [XPDM vs WDDM (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/direct3d9/xpdm-vs-wddm)
- Session 0 "only supports non-interactive functionality"; functions that interact with display devices "receive errors" (Direct2D server-side rendering guidance). — [Direct2D server-side rendering (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/direct2d/server-side-rendering-overview)

**Kiosk / unattended start / OS channel**
- Single-app kiosk: Assigned Access runs a UWP app or Edge above the lock screen (auto-restarts if closed, applies lockdown policies automatically); Shell Launcher runs a Win32 desktop app as the shell instead of explorer.exe (no default lockdown policies, not above the lock screen). Assigned Access: Pro, Enterprise, Education; Shell Launcher: Enterprise and Education only; the two cannot be combined. — [Kiosk overview (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/configuration/shell-launcher/browser-support)
- Shell Launcher is enabled with `Dism /online /Enable-Feature /all /FeatureName:Client-EmbeddedShellLauncher` on IoT Enterprise. — [Configure Shell Launcher or Assigned Access (IoT)](https://learn.microsoft.com/en-us/windows/iot/iot-enterprise/commercialization/iot-ent-shell-launcher-app-launcher)
- Windows 11 IoT Enterprise LTSC 2024 (build 26100, 24H2-equivalent) is supported to 2034-10-10 (10 years, monthly quality updates, no feature updates); Windows 11 Enterprise LTSC 2024 has a 5-year lifecycle; LTSC is for special-purpose devices. — [What's new in IoT Enterprise LTSC 2024](https://learn.microsoft.com/en-us/windows/iot/iot-enterprise/whats-new/windows-11-iot-enterprise-ltsc-2024); [Enterprise LTSC 2024](https://learn.microsoft.com/en-us/windows/whats-new/ltsc/whats-new-windows-11-2024)
- Windows 11 general channel: 23H2 ends 2026-11-11, 24H2 ends 2027-10-13, 25H2 ends 2028-10-11, 26H2 started 2026-09-29 (IoT Enterprise listing). — [Windows 11 IoT Enterprise lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/windows-11-iot-enterprise)
- Windows 10 reached end of support on 2025-10-14; 22H2 is the final version (LTSC releases continue per their own lifecycles). — [Windows 10 Home and Pro lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/windows-10-home-and-pro)

**Update policy for show machines**
- Windows Update client policies (formerly "Windows Update for Business"): defer feature updates up to 365 days, quality updates up to 30 days; pause either for up to 35 days from a set start date (then a scan is forced before re-pausing); active hours default max range 18 hours; compliance deadlines 2–30 days with a 0–7 day grace period. — [Windows Update client policies](https://learn.microsoft.com/en-us/windows/deployment/update/windows-update-client-policies); [Configure Windows Update client policies](https://learn.microsoft.com/en-us/windows/deployment/update/waas-configure-wufb); [Update Policy CSP](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-update); [Intune update ring settings](https://learn.microsoft.com/en-us/intune/device-updates/windows/ref-update-ring-settings)
- Conflict: one registry table lists `DeferQualityUpdatesPeriodInDays` as 0–35 while the policy pages say 30 days maximum. — [waas-configure-wufb](https://learn.microsoft.com/en-us/windows/deployment/update/waas-configure-wufb) vs [windows-update-client-policies](https://learn.microsoft.com/en-us/windows/deployment/update/windows-update-client-policies)
- Microsoft recommends staying on a Windows version with ≥3 months of support remaining; users can pause 7 days via UI unless `SetDisablePauseUXAccess` is applied. — [Windows Update via CSP/MDM](https://learn.microsoft.com/en-us/windows/deployment/update/waas-wufb-csp-mdm)
- Pro-AV practice: Dataton's WATCHOUT guide (Windows 10 Enterprise, 2018 — older guidance) sets "Configure Automatic Updates = Disabled" and "Do not connect to any Windows Update Internet locations = Enabled", and installs updates manually from the Update Catalog. — [WATCHOUT Windows 10 tweaking guide (PDF)](https://cdn.dataton.com/Files-PDF-etc/content_offers/WATCHOUT-Windows_10_Enterprise_Tweaking_Guide.pdf?mtime=20180615134405). Signage vendor Broox warns not to leave machines permanently unpatched and to schedule updates in maintenance windows. — [Broox Windows kiosk preparation](https://dev-broox.github.io/support/technical/windows/)

**Code signing and SmartScreen**
- Azure Artifact Signing (renamed from Trusted Signing; functionally identical): Basic $9.99/month for 5,000 signatures, Premium $99.99/month for 100,000, $0.005 per extra; HSM-held keys (FIPS 140-2 L3); integrates with SignTool, GitHub Actions, Azure DevOps; supports public, private, VBS-enclave and test trust. — [Azure Artifact Signing product page](https://azure.microsoft.com/en-us/products/artifact-signing)
- Eligibility: organisations in USA, Canada, EU, UK; individuals USA and Canada only; requires a paid Azure subscription; does not issue EV certificates. Reputation still builds over time — "initial warnings expected". — [Code signing options for Windows app developers (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options); [Artifact Signing FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)
- EV certificates "previously bypassed SmartScreen… That behavior was removed in 2024"; EV is "no longer recommended specifically for SmartScreen bypass". — [Code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)
- History: preview onboarding was restricted on 2025-04-02 to US/Canada organisations with ≥3 years of history. — [Trusted Signing public preview update](https://techcommunity.microsoft.com/blog/microsoft-security-blog/trusted-signing-public-preview-update/4399713); certificates are short-lived and managed by the service. — [InfoQ (2024-05)](https://www.infoq.com/news/2024/05/microsoft-trusted-signing/)

**Redistributables / DirectX Agility SDK**
- The Agility SDK splits `D3D12.dll` (thin loader in System32) from `D3D12Core.dll`; an app can ship a newer `D3D12Core.dll` beside itself (exporting the SDK version/path) and the OS loads the newer of app vs System32 copies; requires Windows 10 1909+ (with specific KB revisions) or later. — [Getting Started with the Agility SDK (DirectX blog)](https://devblogs.microsoft.com/directx/gettingstarted-dx12agility/)

**mDNS / DNS-SD**
- `DnsServiceRegister` / `DnsServiceBrowse` (windns.h, dnsapi.dll) are built into Windows 10+; registration is tied to the calling process's lifetime; `unicastEnabled=false` uses mDNS. — [DnsServiceRegister (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/api/windns/nf-windns-dnsserviceregister)
- Developers have reported the browse API as hard to use and unreliable for add events (2020 thread; Microsoft asked for repros). — [WindowsAppSDK#281](https://github.com/microsoft/WindowsAppSDK/issues/281)

### Inferences
- Recommended shape: one per-machine MSI (WiX v7, or Velopack `--msi --instLocation PerMachine` if Velopack's delta-update channel is wanted) installing to Program Files; the installer (elevated) does all machine-level actions once: firewall rules for the engine exe (TCP control/web ports, UDP for Show Bus/sync/mDNS), WER LocalDumps key, Event Log source registration, granting SeLockMemoryPrivilege / SeIncreaseBasePriorityPrivilege to the engine's run-as account if those features are enabled, and optionally the Ultimate Performance plan and DisableUserPresenceQos. The engine itself then never needs admin at runtime ("fail closed").
- Engine placement: run the engine as a normal process in the auto-logged-on show user's session (it owns displays and GPU outputs). A tiny LocalSystem watchdog service (or Task Scheduler "at logon" + restart-on-failure) can supervise it; a service that must relaunch the engine into the interactive session would use the session APIs (WTSQueryUserToken/CreateProcessAsUser — not sourced here). On Enterprise/IoT Enterprise, Shell Launcher with the engine (or a PlayMap launcher) as the shell gives restart-on-exit; on Pro, auto-logon + startup task.
- Recommend Windows 11 IoT Enterprise LTSC 2024 for fixed show nodes (10-year servicing, no feature updates) and Windows 11 Pro/Enterprise 24H2/25H2 for desk/programming machines; drop Windows 10 support entirely (EOS 2025-10-14).
- "Never update mid-show": PlayMap's own updater must be gated by STATE.show (refuse with reason while a show is armed — matches the doctrine "a verb that would change nothing is refused with the reason"); Windows updates: defer + active hours + no auto-restart, applied in a maintenance window that PlayMap can surface in preflight (pending reboot / pending update as preflight warnings).
- Version constraints from installer tech propagate into the versioning scheme (see §6): MSI major/minor ≤255 rules out year-based majors like 2026.x for MSI; Velopack rules out 4-part versions.
- Signing: Artifact Signing for all exe/dll/msi in CI; SmartScreen reputation accrues to a stable publisher identity across releases, so sign every build channel with the same profile.

### Gaps
- Inno Setup (current version, per-machine/service support) was not researched.
- WiX v7 Firewall/Util extension specifics (FirewallException, ServiceConfig recovery) not retrieved.
- URL ACLs (`netsh http add urlacl`) only matter for HTTP.sys/HttpListener hosting; whether PlayMap's web/control endpoints use Kestrel (no URL ACL) was not checked here.
- Microsoft guidance on Defender exclusions for media folders/processes (and their security trade-off) not retrieved.
- VC++ runtime needs of the FFmpeg 9.0 shared builds PlayMap uses (static vs dynamic CRT) not checked.
- Auto-logon mechanics on Windows 11 (registry `AutoAdminLogon` vs Sysinternals Autologon LSA secret, and interaction with Windows Hello/passwordless defaults) not retrieved from primary sources.
- Whether hardware D3D11/D3D12 *compute* works from a session-0 service on WDDM 2.x (modern GPU compute services suggest yes) — Microsoft's only table found is D3D9/10-era and says only WARP.
- MSIX + Shell Launcher/Assigned Access interplay and MSIX's suitability for unattended per-machine provisioning not researched.

## 5. Reliability and diagnostics (WER/minidumps, .NET crash handling, ETW/EventPipe, Event Log, watchdogs/restart, TDR and device-removed recovery, update deferral, notifications, display/screen-saver suppression, USB selective suspend)

### Takeaway
Configure WER LocalDumps per-exe at install time (full dumps, bounded count) and keep .NET's own dump env vars as a fallback; use EventPipe (no admin) for in-field GPU/GC/JIT traces and ETW (admin) for kernel-level investigations; supervise the engine with restart policies that also fire on non-crash failures; never ship TDR registry changes — instead implement full device-removed recovery, which Microsoft treats as a normal event (driver updates, TDRs). Keep the display awake with `SetThreadExecutionState(ES_CONTINUOUS | ES_DISPLAY_REQUIRED | ES_SYSTEM_REQUIRED)` — it does not stop the screen saver, which must be disabled separately.

### Cited Findings
**Crash dumps**
- WER LocalDumps: `HKLM\SOFTWARE\Microsoft\Windows\Windows Error Reporting\LocalDumps[\PlayMap.exe]` with `DumpFolder` (default `%LOCALAPPDATA%\CrashDumps`; services write to service-profile folders), `DumpCount` (default 10, oldest replaced), `DumpType` (0 custom, 1 mini (default), 2 full), `CustomDumpFlags`; requires admin to configure; works even if WER reporting is disabled; "Applications that do their own custom crash reporting are not supported by this feature"; no dump if automatic debugging is set. — [Collecting User-Mode Dumps (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/wer/collecting-user-mode-dumps)
- .NET crash dumps: `DOTNET_DbgEnableMiniDump=1`, `DOTNET_DbgMiniDumpType` (1 Mini, 2 Heap default, 3 Triage — strips paths/passwords, 4 Full), `DOTNET_DbgMiniDumpName` with `%p %e %h %t` templates; `DOTNET_EnableCrashReport` JSON report not supported on Windows; single-file and NativeAOT only support full dumps; `.NET 11+` adds `DOTNET_DbgCreateDumpToolPath` for NativeAOT. — [Collect dumps on crash (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/collect-dumps-crash)

**Tracing**
- EventPipe is built into the runtime, collects runtime (JIT, GC) and EventSource events into `.nettrace`, needs no admin (same user), but only managed frames and no kernel events; ETW requires admin but gives kernel events and native stacks. Start via `dotnet-trace`/`Microsoft.Diagnostics.NETCore.Client` or `DOTNET_EnableEventPipe` + `DOTNET_EventPipeConfig`. — [EventPipe overview (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/eventpipe)
- Each .NET process exposes a diagnostic port at `\\.\pipe\dotnet-diagnostic-{pid}`; `DOTNET_DiagnosticPorts` adds custom ports (connect/listen, suspend on startup) for tracing from startup. — [Diagnostic port (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/diagnostic-port); [dotnet-trace](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-trace)
- `EventSource` is the built-in structured logging mechanism; on .NET (Core) it feeds EventPipe and ETW. — [EventSource (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/eventsource)

**Restart policies**
- `SERVICE_FAILURE_ACTIONS_FLAG.fFailureActionsOnNonCrashFailures = TRUE` makes recovery actions fire also when the service stops with a non-zero exit code (otherwise only when it dies without reporting SERVICE_STOPPED). — [SERVICE_FAILURE_ACTIONS_FLAG (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/ns-winsvc-service_failure_actions_flag)
- Microsoft's guideline for critical services: Restart/60000/Restart/120000/Reboot/60000, reset after 300 s; non-critical: Restart/120000/Restart/300000/None, reset 900 s (`ChangeServiceConfig2`). — [Guidelines for services (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/rstmgr/guidelines-for-services); `sc failure <svc> reset= N actions= restart/5000/...` syntax — [sc failure (Microsoft Learn)](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2012-r2-and-2012/cc742019(v=ws.11))

**GPU TDR and device removal**
- TDR registry keys under `HKLM\System\CurrentControlSet\Control\GraphicsDrivers`: `TdrLevel` (3 = recover, default), `TdrDelay` (default 2 s — effectively the timeout), `TdrDdiDelay` (default 5 s, then bugcheck 0x116), `TdrLimitCount` (default 5) within `TdrLimitTime` (default 60 s) before the machine crashes. Microsoft: "End users shouldn't manipulate these registry keys. Applications shouldn't manipulate these registry keys outside of targeted testing or debugging during driver development." — [TDR registry keys (Microsoft Learn)](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/tdr-registry-keys)
- Device removed handling: check `Present`/`ResizeBuffers` for `DXGI_ERROR_DEVICE_REMOVED`/`DXGI_ERROR_DEVICE_RESET`, call `GetDeviceRemovedReason` before release, release every device resource and the swap chain, recreate device + resources. `DEVICE_REMOVED` (physical removal or driver upgrade) "happens occasionally and is normal". `dxcap -forcetdr` forces a TDR for testing. — [Handle device removed scenarios in Direct3D 11 (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/uwp/gaming/handling-device-lost-scenarios). The same pattern applies to D3D12; a common cause in the field is Windows Update installing a driver overnight. — [GameDev StackExchange answer by Chuck Walbourn](https://gamedev.stackexchange.com/questions/126534/dx11-handle-device-removed)
- DirectStorage GPU decompression of corrupt GDeflate data causes a TDR. — [DirectStorage 1.3 blog](https://devblogs.microsoft.com/directx/directstorage-1-3-is-now-available/)

**Display, notifications, USB, power**
- `SetThreadExecutionState(ES_CONTINUOUS | ES_DISPLAY_REQUIRED)` keeps the display on (video players "must use ES_DISPLAY_REQUIRED"); `ES_SYSTEM_REQUIRED` keeps the system awake; "This function does not stop the screen saver"; it cannot prevent user-initiated sleep (lid/power button). — [SetThreadExecutionState (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate)
- Kiosk/signage practice: `powercfg /x -monitor-timeout-ac 0` (and standby/hibernate/disk), `ScreenSaveActive=0`, `NoLockScreen=1`, `DisableNotificationCenter=1`, `ToastEnabled=0`, Windows Update notification levels, `CrashControl\DisplayDisabled=1`. — [Broox Windows kiosk preparation](https://dev-broox.github.io/support/technical/windows/)

### Inferences
- Install-time: per-exe LocalDumps for `PlayMap.exe` (engine + desk are the same exe → one key) with DumpType 2 (full) and DumpCount ~5 to a PlayMap-owned folder; the dump file name and the engine's journal should both carry the full InformationalVersion so a dump maps to a commit (see §6). Do not also install an in-process crash reporter that intercepts unhandled exceptions, since WER LocalDumps does not support apps doing their own crash reporting.
- Runtime: the engine subscribes to `AppDomain.UnhandledException` only to flush the journal and write a STATE "crashed" line, then lets the process die so WER dumps it and the watchdog restarts it; recovery goes back to "content is a pure function of show time", so a restarted engine rejoins at the leader's time.
- Device-removed is an "observed" fact for STATE/health: count TDRs, record `GetDeviceRemovedReason`, and expose a verb to force a re-init. Shipping a raised `TdrDelay` contradicts Microsoft's guidance; long-running GPU work should be split instead.
- Preflight checks worth adding (machine profile): power plan, USB selective suspend, PCIe ASPM, display/sleep timeouts, screen saver, notifications/DND, pending Windows Update reboot, WU deferral policy, HAGS state, timer-resolution honour flag, GPU driver version — each reported as a fact, not changed silently.
- Watchdog: Task Scheduler / service recovery for the supervisor; the supervisor restarts the engine on exit or on a missed heartbeat on the existing wire (HEALTH), with a backoff and a "too many restarts" stop state surfaced to Patterns/Stagewatch.

## 6. Build versioning (Version/AssemblyVersion/FileVersion/InformationalVersion, SourceLink SHA, NB.GV vs MinVer vs GitVersion vs CI numbers, SemVer 2.0, 4-part 65535 limits, MSIX/MSI rules, where to show the version, reproducible builds)

### Takeaway
Use one source of truth (git: `version.json` with Nerdbank.GitVersioning, or tags with MinVer) and derive every representation from it: SemVer2 `Version`/`InformationalVersion` with `+<sha>` for humans, logs, hello and dumps; a 4-part `FileVersion` whose parts each fit 16 bits; an installer version that satisfies the installer's own rules (MSI: major/minor ≤255, only 3 fields count; MSIX: 4 parts ≤65535, Store wants 4th = 0 and 1st ≠ 0; Velopack: SemVer2 3-part only). Build metadata never orders versions (SemVer §10), so ordering must be carried by major.minor.patch(.height).

### Cited Findings
- SemVer 2.0: `MAJOR.MINOR.PATCH[-pre][+build]`; pre-release has lower precedence; build metadata "MUST be ignored when determining version precedence"; identifiers `[0-9A-Za-z-]`, numeric pre-release identifiers without leading zeros. — [semver.org](https://semver.org/)
- .NET versions: `AssemblyVersion` used for binding (consider major-only, don't keep fixed); `FileVersion` shown in Explorer, format `Major.Minor.Build.Revision`, "consider including a continuous integration build number as the … revision"; `InformationalVersion` free text — avoid setting it yourself; Source Link sets it to package version + commit (e.g. `1.0.0-beta1+204ff0a`). — [Versioning and .NET libraries (Microsoft Learn)](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/versioning)
- Since the .NET 8 SDK, Source Link is in the SDK and `InformationalVersion` always includes `SourceRevisionId` (the commit hash); opt out with `IncludeSourceRevisionInInformationalVersion=false`. — [Breaking change: Source Link included in the .NET SDK](https://learn.microsoft.com/en-us/dotnet/core/compatibility/sdk/8.0/source-link); [MSBuild properties: SourceRevisionId](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props)
- Nerdbank.GitVersioning: major.minor from `version.json`; third component = git height (commits since the version was set; minimum 1); fourth = first two bytes of the commit id as an integer ("not useful in sorting", distinguishes same height on different branches); e.g. `AssemblyVersion("1.0")`, `AssemblyFileVersion("1.0.24.15136")`, `AssemblyInformationalVersion("1.0.24-alpha+g9a7eb6c819")`; generates a `ThisAssembly` class with these constants; `version.json` supports x.y.z (height becomes 4th), `-beta.{height}`, `assemblyVersion.precision`, cloud build number options. — [NB.GV .NET docs](https://dotnet.github.io/Nerdbank.GitVersioning/docs/ecosystems/dotnet.html); [NB.GV FAQ](https://dotnet.github.io/Nerdbank.GitVersioning/docs/faq.html); [version.json reference](https://dotnet.github.io/Nerdbank.GitVersioning/docs/versionJson.html); `GetTruncatedCommitIdAsUInt16` in [NB.GV source](https://github.com/dotnet/Nerdbank.GitVersioning/blob/ce50e213/src/NerdBank.GitVersioning/Managed/GitExtensions.cs)
- NB.GV's commit-derived 4th FileVersion part can break installers/inventory that need `major.minor.build.0`; the maintainer suggests raising `AssemblyVersion` precision or overriding `AssemblyFileVersion` with `$(BuildVersionSimple)`. — [NB.GV#444](https://github.com/dotnet/Nerdbank.GitVersioning/issues/444)
- MinVer: version from the latest SemVer tag; untagged commits get `{next patch}-alpha.0.{height}`; sets `AssemblyVersion={Major}.0.0.0`, `FileVersion={Major}.{Minor}.{Patch}.0`, `InformationalVersion={full SemVer}`; requires .NET SDK 8+; CI must fetch tags/history; options `MinVerTagPrefix`, `MinVerBuildMetadata`, `MinVerMinimumMajorMinor`, etc. — [MinVer README](https://github.com/adamralph/minver)
- MSIX identity Version is a DotQuad `0.0.0.0`–`65535.65535.65535.65535`, must increase with updates; for Store packages the 4th part "is reserved for Store use and must be left as 0" and the 1st part cannot be 0. — [Package identity overview](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/package-identity-overview); [Package version numbering](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/package-version-numbering?pivots=store-installer-msix)
- Microsoft's own MSIX CI example sets `major.minor.build.$(counter)` in the manifest from an Azure Pipelines counter (sideload scenario). — [MSIX + Azure DevOps (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/msix/desktop/azure-dev-ops)
- Windows App SDK maps SemVer `1.3.5` to MSIX `1.3.5.0` and reserves Revision for servicing (a team convention, not a platform rule). — [WindowsAppSDK MSIX versioning spec](https://github.com/microsoft/WindowsAppSDK/blob/main/specs/Deployment/MSIXPackageVersioning.md); [WindowsAppSDK discussion #3747](https://github.com/microsoft/WindowsAppSDK/discussions/3747)
- MSI ProductVersion: major ≤255, minor ≤255, build ≤65,535; 4th field ignored. — [ProductVersion (Microsoft Learn)](https://learn.microsoft.com/en-us/windows/win32/msi/productversion)
- Velopack: SemVer2 3-part only (`--packVersion 1.0.0-build.23+metadata`); separate `--msiVersion` for its MSI. — [Velopack FAQ](https://docs.velopack.io/troubleshooting/faq); [Velopack installers](https://docs.velopack.io/packaging/installer)

### Inferences
- A scheme that satisfies every consumer: `version.json` = `"1.4-beta.{height}"` (or tag `v1.4.0` with MinVer). Derived:
  - SemVer2 / product version: `1.4.0-beta.37+g1a2b3c4d5e` (UI "About", logs header, network hello `ver`, STATE `version`, crash dump folder/name, Velopack `--packVersion`, installer file name `PlayMap-1.4.0-beta.37-win-x64.msi`).
  - FileVersion: `1.4.37.0` (major.minor.height.0 — keeps every part ≤65535 and sortable; avoid NB.GV's commit-derived 4th part or CI run numbers that will exceed 65535 over the project's life).
  - MSI ProductVersion: `1.4.37` (major, minor ≤255 — so no `2026.x` calendar majors for MSI).
  - MSIX (if ever): `1.4.37.0`.
  - AssemblyVersion: `1.0.0.0` or `1.4.0.0` (binding only).
- Read the version in code from `AssemblyInformationalVersionAttribute` (or NB.GV's `ThisAssembly.AssemblyInformationalVersion`) in Core, so engine, desk, wire hello, STATE, MCP context and journal all report the same string; Patterns/Stagewatch can compare nodes by the SemVer core and detect mismatched builds by the `+sha`.
- CI: full-history checkout (`fetch-depth: 0`) so git height/tags are computable; never derive ordering from build metadata. Tag releases; CI builds from untagged commits are pre-releases.
- If PlayMap must also show "build N" for support, put the CI run number only in build metadata (`+ci.1234.g<sha>`), never in a 16-bit field.
