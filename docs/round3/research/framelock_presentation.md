# Framelock, genlock and tear-free, low-latency presentation on Windows (state as of October 2026)

Scope: every mechanism that removes tearing and aligns frames across outputs, GPUs and machines for a Windows 11 x64 media server / projection-mapping renderer on NVIDIA RTX (consumer and RTX PRO) and AMD Radeon (consumer and Radeon PRO), across D3D12, Vulkan and OpenGL 4.6. Context: PlayMap today presents through GL (GLFW, swap interval, optional `swapGroup`/`swapBarrier` settings) and an experimental D3D11 DXGI `FLIP_DISCARD` waitable path that reads `GetFrameStatistics` into a per-output vblank fit (`docs/OUTPUT.md`, `docs/SYNC.md`).

## 1. Hardware framelock / genlock: what exists in 2026, for which cards and APIs, and what the products use

### Takeaway
In 2026 hardware framelock/genlock on Windows is effectively an NVIDIA-professional-only capability: the NVIDIA RTX PRO Sync card (the April 2025 rebrand of Quadro Sync II) plus an RTX PRO / RTX Ada / RTX A / Quadro RTX GPU, exposed to applications as swap groups/barriers (OpenGL `WGL_NV_swap_group`, NvAPI for D3D) and, for D3D12 and Vulkan, the higher-level "present barrier" (`NvAPI_D3D12_*PresentBarrier*`, `VK_NV_present_barrier`). AMD removed Framelock/Genlock from its public PRO Edition driver in 23.Q1 and no RDNA3/RDNA4 Radeon PRO lists it; GeForce has no hardware sync. Every major media server (disguise, Pixera, WATCHOUT 7, TouchDesigner, Unreal nDisplay) uses the NVIDIA sync card for multi-machine lock and falls back to network time (NTP/software barriers) without it.

### Cited Findings

**NVIDIA RTX PRO Sync (formerly Quadro Sync II) — hardware**

- The user guide (DU-08348-001_v09, March 10 2026) says: synchronizes up to eight GPUs with two cards; external sync up to 1000 Hz; generates a sync output for other systems; enables Synchronized Mosaic; "sync multiply and divide"; sync different resolutions with the same refresh. Requirements: "Pascal-series graphics boards and later, 4000-class and above"; Windows 10/11 64-bit and Linux; "R440 branch and newer display drivers support NVIDIA RTX PRO Sync with Mosaic topologies"; a free PCIe slot (mechanical only, "does not use any electrical or data connection through the PCIe bus") and 6-pin PCIe or SATA power. — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- "The NVIDIA RTX PRO Sync card is a rebranding of the Quadro Sync II card that was aligned with the launch of the NVIDIA RTX PRO Blackwell cards. Both cards offer equivalent features." Revision 08 (April 16 2025) is the rebrand; it lists "New features highlighted, including Variable Refresh Rate", but the v09 body contains no VRR section (see Gaps). — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- Not compatible with Maxwell (Quadro M) or Kepler GPUs; the fifth connector links a second Sync card, not a fifth GPU. — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- Cluster wiring: CAT-5 daisy chain between Sync cards' RJ45 ports, never to a switch ("not compatible with TCP/IP protocols, and the card will not operate if it is connected to networking equipment"). NVIDIA recommends the timing server in the middle of the chain and two chains for large clusters. "The Swap Barrier signal is sent over the RJ45 connector, so applications using this capability require this connection." — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- House sync input (BNC): TTL 3.3 V; bi-level composite (NTSC/PAL) 75 Ω; tri-level composite (HDTV, SMPTE 240) 75 Ω. Settings: trigger edge for TTL, interlace detection, Sync Interval (divide incoming pulses), and a start Sync Delay in µs between external and internal pulses. The BNC can instead output TTL sync locked to the framelock signal (~200 ns pulse at 60 Hz). — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- Tolerance: "can align displays and sync sources up to ±50 ppm difference in the display timings" (e.g. 60 Hz: 59.9988–60.0012 Hz). Firmware 2.18+: sync multiply/divide 1–8 (e.g. 120 Hz displays on a 60 Hz house sync, `configureSync.exe enable server source=HOUSESYNC multiplier=2 display=0,0`), and up to two different resolutions per system at the same refresh. — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- Setup order matters: disable G-SYNC, set stereo, configure Mosaic, then enable framelock (server first, then clients). Re-syncing a cluster "can take many minutes". — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- NVLink carries some sync signals, but only for an NVLink pair in Mosaic, and that pair cannot lock to external sync. Mosaic across GPUs that are only on PCIe "is not synchronized"; it is synchronized when the GPUs are wired to a Sync card. Remote configuration and Sync event monitoring go through NVWMI. — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- Windows automation is the Sync Utility `configureSync.exe` (previously `configureQsync`/QSync Utility, renamed in the rebrand). — [NVIDIA Sync Utility](https://www.nvidia.com/en-us/drivers/sync-utility/); [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- Sync firmware 3.06 fixes framelock setup and also updates Quadro Sync II boards. The Linux package's minimum driver is 535.154.05. — [NVIDIA Sync Firmware 3.06 (Linux)](https://www.nvidia.com/en-us/drivers/firmware/3_06/nv-quadro-sync-linux-64bit-update-3-06-driver/); [Windows](https://www.nvidia.com/en-us/drivers/firmware/3_06/nv-quadro-sync-windows-update-3-06-driver/)
- Linux driver 595.x README: "Frame Lock is supported across an arbitrary number of RTX PRO Sync systems", with no mixing of Sync generations and "identical mode timings". The OpenGL path there is `GLX_NV_swap_group`. — [NVIDIA Linux driver README, Ch. 32](https://download.nvidia.com/XFree86/Linux-x86_64/595.91.07/README/framelock.html)

**NVIDIA application-level mechanisms (by API)**
- **OpenGL — `WGL_NV_swap_group`** ("Shipping since 2003 on Quadro GPUs with framelock support"): `wglJoinSwapGroupNV`, `wglBindSwapBarrierNV`, `wglQueryFrameCountNV`, `wglResetFrameCountNV`. Swaps in a group happen together. Swaps across groups bound to a barrier are concurrent "if and only if the vertical retraces of the screens of all the groups are synchronized". The implementation provides "a universal counter, the so called frame counter, among all systems that are locked together", and reset succeeds only on the framelock master. The spec warns the window-system state can restrict swap groups; "one fullscreen sized window per windows desktop" is the typical working case. — [WGL_NV_swap_group spec](https://registry.khronos.org/OpenGL/extensions/NV/WGL_NV_swap_group.txt)
- **D3D (NvAPI swap groups/barriers)**: swap groups and barriers "were later extended through public NvAPI interfaces and supported in DirectX 9 through 12". — [NVIDIA Technical Blog, 2022-07-26](https://developer.nvidia.com/blog/synchronizing-present-calls-between-applications-on-distributed-systems-with-directx-12/)
- **D3D12 — present barrier**: it "combine[s] swap groups and swap barriers". Six functions: `NvAPI_D3D12_QueryPresentBarrierSupport`, `NvAPI_D3D12_CreatePresentBarrierClient(device, swapChain)`, `NvAPI_D3D12_RegisterPresentBarrierResources(client, fence, backBuffers, n)` (the barrier increments the fence; the app may wait on it but must not signal it; re-register when buffers change), `NvAPI_JoinPresentBarrier`, `NvAPI_LeavePresentBarrier`, `NvAPI_QueryPresentBarrierFrameStatistics`. `SyncMode` reports `NOT_JOINED` / `SYNC_CLIENT` / `SYNC_SYSTEM` / `SYNC_CLUSTER`. — [NVIDIA Technical Blog](https://developer.nvidia.com/blog/synchronizing-present-calls-between-applications-on-distributed-systems-with-directx-12/)
- Present barrier conditions: "only effective when an application is in a full-screen state with no window borders, as well as no desktop scaling or taskbar composition. If at least one of these requirements is not met, the present barrier disengages and reverts to a pending state." Displays need the same timing, synchronized via the Sync card or a Mosaic surface (or NVLink). — [NVIDIA Technical Blog](https://developer.nvidia.com/blog/synchronizing-present-calls-between-applications-on-distributed-systems-with-directx-12/)
- NVAPI also has `NvAPI_D3D12_CreateDDisplayPresentBarrierClient(device, sourceId, …)`, a present barrier for a dedicated display that is not a DXGI swap chain. — [NVAPI reference (DX group)](https://archive.docs.nvidia.com/gameworks/content/gameworkslibrary/coresdk/nvapi/group__dx.html)
- Sample requirements: "NVIDIA RTX / Quadro series card (GeForce is NOT supported)", driver 472.12+, NVAPI R470+. Its overlay is red (not in sync), yellow (in sync with local clients) or green (in sync across systems through framelock), and its stats include `PresentInSyncCount` and `FlipInSyncCount`. — [nvpro-samples/dx12_present_barrier](https://github.com/nvpro-samples/dx12_present_barrier)
- **Vulkan — `VK_NV_present_barrier`** (published in Vulkan 1.3.230, 2022) adds `VkPhysicalDevicePresentBarrierFeaturesNV`, `VkSurfaceCapabilitiesPresentBarrierNV` and `VkSwapchainPresentBarrierCreateInfoNV`. There is no query of whether a swapchain is in the barrier; "if the required hardware is presented in the system, and all settings for the physical synchronization with other systems are set up, an implementation manages the configuration automatically when creating a swapchain." — [Vulkan refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VK_NV_present_barrier.html); [Phoronix, Vulkan 1.3.230](https://www.phoronix.com/news/Vulkan-1.3.230-Released)
- NVIDIA's `configureDriver.exe` has an option "Enable the SwapGroupPresentIndicator for OpenGL and Vulkan", an on-screen indicator for swap-group state. — [TouchDesigner: Hardware Frame Lock](https://docs.derivative.ca/Hardware_Frame_Lock)
- **NVAPI warp and blend**: `NvAPI_GPU_SetScanoutWarping` / `NvAPI_GPU_SetScanoutIntensity` apply warp and intensity/black-level "in the display pipeline before the pixels get scanned out", with "minimal performance impact and no incremental latency". Quadro/RTX-professional only; works with Mosaic and the Sync card ("up to 16 displays"). — [NVIDIA Warp and Blend](https://developer.nvidia.com/warp-and-blend); [SIGGRAPH talk](https://www.nvidia.com/content/siggraph/Nash_Seamless_Display.pdf)
- The NVAPI display-control reference is at Release 590 (Feb 19 2026). It includes custom timing types (`NV_TIMING_OVERRIDE_CVT_RB`, `_CUST`, `_SDI`, …) and `NV_GET_VRR_INFO`. — [NVAPI Display Control](https://docs.nvidia.com/nvapi/group__dispcontrol.html)

### Inferences
- For PlayMap the hardware-lock path is NVIDIA-only. On D3D12 the natural primitive is the NvAPI present barrier (one join call, frame statistics with `SyncMode`). On Vulkan it is `VK_NV_present_barrier` (a swapchain create flag; no per-frame confirmation, so lock state must be read elsewhere, e.g. NVAPI/NVWMI). On GL it stays `WGL_NV_swap_group`. AMD nodes have to be treated as "software sync only" unless a vendor-pinned partner driver is in play, as at disguise.
- The swap-group frame counter (`wglQueryFrameCountNV`, reset only on the master) and WATCHOUT's use of the sync boards' 24-bit counter suggest PlayMap's leader "counter anchor" can be the hardware frame counter. It must be wrap-aware: 2^24 frames ≈ 3.2 days at 60 Hz.
- Present-barrier and swap-barrier semantics are all-or-nothing: a stalled node stalls the wall (WATCHOUT, TouchDesigner). The presentation layer therefore needs a governed "leave barrier / fall back to free-run" path with a measured cause, which matches PlayMap's `fell-out` state.
- Hardware warp/blend at scanout (NVAPI) is an option for edge-blend/keystone at zero added latency, but only on RTX-professional cards. Mesh warps from PlayMap's 3D pipeline still belong in the renderer.

### Gaps
- The RTX PRO Sync revision 08 changelog advertises "Variable Refresh Rate" support, but the v09 body describes no VRR mode and still says to disable G-SYNC before framelock. I found no NVIDIA document explaining VRR with RTX PRO Sync.
- Whether `VK_NV_present_barrier` works on Windows with the same requirements as the D3D12 barrier (borderless fullscreen, no DWM composition) is not stated in the extension text I read.
- The Unreal 5.7 nDisplay pages are client-rendered and could not be read. The official 5.x docs on the Present Barrier policy and on retiring the DX11 swap-lock path are not captured.
- I found no AMD statement on any successor to the S400, any ADLX/ADL/AGS framelock API for RDNA3/RDNA4, or the current state of Eyefinity display groups for tear-free spanning. The terms of disguise's AMD partner driver are not public.
- Whether the Reflex SDK and the present barrier can be combined was not found.

## 2. Single-machine tear-free presentation: DXGI, Vulkan and OpenGL on Windows 11

### Takeaway
On Windows 11 the tear-free, low-latency path is a flip-model swap chain (`FLIP_DISCARD`/`FLIP_SEQUENTIAL`) in a borderless window that covers the output, which the OS promotes to DirectFlip / Independent Flip (the same efficiency as legacy exclusive fullscreen, and D3D12 has no true exclusive fullscreen anyway). Add a frame-latency waitable object (down to 1 frame queued) and read `GetFrameStatistics` for vblank truth. Vulkan gets explicit pacing through `VK_KHR_present_wait2`/`present_id2` (Vulkan 1.4.317, June 2025) and time-targeted presents through `VK_EXT_present_timing` (Vulkan 1.4.335, Nov 2025; NVIDIA driver first). OpenGL on Windows depends on the vendor driver's presenter (NVIDIA's "Vulkan/OpenGL present method" layering onto DXGI) and has no standard frame statistics.

### Cited Findings
- Flip model "will give better performance, lower power usage, and provide a richer set of features" and makes "windowed mode effectively equivalent or better when compared to the classic 'fullscreen exclusive' mode". — [MS Learn: For best performance, use DXGI flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)
- DirectFlip variants: (1) swap-chain buffers match the screen and the window covers it; (2) DirectFlip with panel fitters (buffers within e.g. 0.25x–4x of the screen); (3) DirectFlip with multi-plane overlay (MPO). Once DirectFlipped, "the DWM can go to sleep … Your application frames are sent directly to the screen, independently, with the same efficiency as fullscreen exclusive. This is 'Independent Flip'". Overlapping content makes DWM recompose, "reverse compose" or use MPO. — [MS Learn flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model); [DirectX Dev Blog 2018](https://devblogs.microsoft.com/directx/dxgi-flip-model/)
- Latency: with `DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT` "When in Independent Flip mode, you can get down to 1 frame of latency" (the 2-frame minimum bug was fixed in the Fall Creators Update). `ALLOW_TEARING` "can enable even lower latency than the waitable object, even in a window on systems with multi-plane overlay support". — [MS Learn flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)
- `IDXGIOutput6::CheckHardwareCompositionSupport` reports which DirectFlip scaling scenarios the hardware supports. — [MS Learn flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)
- D3D12 supports only `FLIP_SEQUENTIAL`/`FLIP_DISCARD`. "Direct3D 12 doesn't support full-screen exclusive mode (FSE)"; the OS uses full-screen optimisations (FSO). `SetFullscreenState` on D3D12 only changes resolution/refresh. Without frame-flight limiting "Present can succeed immediately … allowing the CPU to queue frames unboundedly". — [MS Learn: D3D12 Swap Chains](https://learn.microsoft.com/en-us/windows/win32/direct3d12/swap-chains)
- NVIDIA guidance: by default DXGI blocks on the 4th Present (3 queued frames per swap chain). Set `FRAME_LATENCY_WAITABLE_OBJECT` plus `SetMaximumFrameLatency` and use 1–2 more buffers than queued frames. "True immediate independent flip" for unlimited-rate tearing on D3D12 needs `SetFullScreenState(TRUE)`, a borderless fullscreen window and a non-windowed flip swap chain. VRR displays need both `ALLOW_TEARING` flags. In windowed mode, sync interval 0 shows "the most recent frame available" at the next composition (which happens at VSYNC). — [NVIDIA Advanced API Performance: Swap Chains (2023)](https://developer.nvidia.com/blog/advanced-api-performance-swap-chains/)
- DXGI best practice: if the refresh rate passed to `ResizeTarget` does not match an enumerated mode (e.g. 60 vs 60000/1001), "DXGI is forced to perform a blit in full-screen mode instead of a flip". For multiple monitors, "create all swap chains as windowed, and then … set them to full-screen". — [MS Learn: DXGI Best Practices](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/dxgi-best-practices)
- `DXGI_FRAME_STATISTICS` = {`PresentCount`, `PresentRefreshCount`, `SyncRefreshCount`, `SyncQPCTime` (a QPC value), `SyncGPUTime` (reserved, always 0)}. Swap-chain statistics are available only for flip-model or fullscreen swap chains; windowed counts start at swap-chain creation. — [MS Learn: DXGI_FRAME_STATISTICS](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/ns-dxgi-dxgi_frame_statistics)
- `GetFrameStatistics` returns `DXGI_ERROR_FRAME_STATISTICS_DISJOINT` on the first call and after mode changes. Flip model recommends `BufferCount` 2–16 and formats FP16, BGRA8 or RGBA8, without MSAA; use one flip swap chain per HWND and no GDI on that HWND. — [MS Learn: DXGI flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-flip-model)
- Windows 11 "Optimizations for windowed games" moves DX10/DX11 blt-model games to flip model; it is required for Auto HDR and enables VRR in windowed mode. — [Microsoft Support](https://support.microsoft.com/en-us/windows/hardware/display-graphics/optimizations-for-windowed-games-in-windows-11)
- **Composition swapchain API (Windows 11)**: presents can carry a target time (`IPresentationManager::SetTargetTime`, system interrupt time in 100 ns units, derivable from QPC), "whereas DXGI doesn't". Presents are processed in queue order. Its "initial version" focuses on media frameworks (Media Foundation). Requirements: WDDM 2.0 and Windows 11 build 10.0.22000.194+; direct scanout/iflip need WDDM 3.0 and displayable allocations. — [MS Learn: Composition swapchain overview](https://learn.microsoft.com/en-us/windows/win32/comp_swapchain/comp-swapchain-portal); [SetTargetTime](https://learn.microsoft.com/en-us/windows/win32/api/presentation/nf-presentation-ipresentationmanager-settargettime); [examples](https://learn.microsoft.com/en-us/windows/win32/comp_swapchain/comp-swapchain-examples); [comp-swapchain.md (requirements)](https://github.com/MicrosoftDocs/win32/blob/docs/desktop-src/comp_swapchain/comp-swapchain.md)
- **Vulkan present wait**: `VK_KHR_present_id2` and `VK_KHR_present_wait2` shipped in Vulkan 1.4.317 (June 6 2025). They replace `present_id`/`present_wait` with per-surface capability queries. The wait-finish wording is "implementation-dependent" ("time to light"/"first pixel" semantics deferred to a future extension). — [Vulkan-Docs 1.4.317 changelog](https://github.com/KhronosGroup/Vulkan-Docs/commit/1228b2beff1a664da6dabea122f49f9818ecda8a); [VK_KHR_present_wait2 proposal](https://github.khronos.org/Vulkan-Site/features/latest/features/proposals/VK_KHR_present_wait2.html); [refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_present_wait2.html)
- **`VK_EXT_present_timing`**: merged Nov 26 2025 and published in Vulkan 1.4.335 after 5 years (NVIDIA-led, with Google, AMD, Collabora, Samsung, Unity, Red Hat). It gives present-engine timing (refresh duration, VRR indicator), per-present stage timestamps (`vkGetPastPresentationTimingEXT`), and "schedule a present to happen no earlier than a desired time". Present at absolute or relative time; `PRESENT_AT_NEAREST_REFRESH_CYCLE` snaps to refresh boundaries; swapchain-local time domains or calibrated domains. Depends on `present_id2`, `get_surface_capabilities2` and `calibrated_timestamps`. — [Khronos blog, 2025-12-04](https://www.khronos.org/blog/vk-ext-present-timing-the-journey-to-state-of-the-art-frame-pacing-in-vulkan); [Phoronix 1.4.335](https://www.phoronix.com/news/Vulkan-1.4.335-Released); [proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_present_timing.html); [refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_present_timing.html); [Khronos sample](https://github.khronos.org/Vulkan-Site/samples/latest/samples/api/swapchain_present_timing/README.html)
- Driver status of present timing: "NVIDIA developer drivers—available now" (Dec 2025). Mesa merged it for 26.1 (RADV, ANV, NVK, Turnip, PanVK; X11/Wayland, i.e. Linux). Khronos says the EXT prefix means "not all platforms yet support the extension, and some use cases—such as driving complex display topologies—are not yet possible". — [Khronos blog](https://www.khronos.org/blog/vk-ext-present-timing-the-journey-to-state-of-the-art-frame-pacing-in-vulkan); [Phoronix: Mesa 26.1](https://www.phoronix.com/news/Mesa-Merges-Present-Timing)
- **`VK_EXT_full_screen_exclusive`** (Windows-only): DEFAULT / ALLOWED / DISALLOWED / APPLICATION_CONTROLLED (`vkAcquireFullScreenExclusiveModeEXT`), and `VK_ERROR_FULL_SCREEN_EXCLUSIVE_MODE_LOST_EXT` when lost. Khronos' sample frames it as a fix "applicable on Windows prior to version 11". — [refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_full_screen_exclusive.html); [Khronos sample](https://docs.vulkan.org/samples/latest/samples/extensions/full_screen_exclusive/README.html)
- `VK_EXT_swapchain_maintenance1` (`VkSwapchainPresentModesCreateInfoEXT`) switches between compatible present modes at present time without recreating the swapchain. — [Khronos WSI blog, 2022](https://www.khronos.org/blog/resolving-longstanding-issues-with-wsi)
- An NVIDIA Windows Vulkan surface (driver 526.47, X-Plane log) exposed MAILBOX, IMMEDIATE, FIFO and FIFO_RELAXED. — [X-Plane.org forum log (user report)](https://forums.x-plane.org/forums/topic/276396-xp12-dxgi-swap-chain-openglvulkan-in-nvidia-52647/)
- **OpenGL/Vulkan on NVIDIA Windows**: the "Vulkan/OpenGL present method" driver setting (`OGL_CPL_PREFER_DXPRESENT`: PREFER_DISABLED / PREFER_ENABLED / AUTO, default AUTO). — [NVAPI driver settings](https://docs.nvidia.com/nvapi/NvApiDriverSettings_8h.html)
- User reports on that setting (not vendor documentation): with AUTO/"Prefer native", a GL borderless window at native resolution "enters exclusive fullscreen"; "Prefer layered on DXGI swapchain" gives the expected borderless flip behaviour, G-SYNC in windowed GL/Vulkan and flip-model optimisations. The setting reportedly appeared around driver 526.47 (Oct 2022). — [MonoGame issue #8629](https://github.com/MonoGame/MonoGame/issues/8629); [X-Plane.org forum](https://forums.x-plane.org/forums/topic/276396-xp12-dxgi-swap-chain-openglvulkan-in-nvidia-52647/); [DXVK issue #5171](https://github.com/doitsujin/dxvk/issues/5171)
- **Verification (PresentMon)**: `PresentMode` values are Hardware: Legacy Flip; Hardware: Legacy Copy to front buffer; Hardware: Independent Flip; Composed: Flip; Hardware Composed: Independent Flip (MPO plane). There is also an `AllowsTearing` column. — [PresentMon console README](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md)

### Inferences
- PlayMap's experimental D3D11 path (waitable `FLIP_DISCARD`, latency 1, `Present1(1, …)`, `GetFrameStatistics` feeding a vblank fit) is the documented best practice. Promoting it, or a D3D12 equivalent, to the default on Windows is supported by every source here. The required invariant is "this output is in Independent Flip", checked by PresentMon or by statistics continuity, not assumed.
- D3D12 gives no "exclusive" mode to fall back to. Tear-free plus low-latency means borderless window = output size, matching format/refresh, nothing overlapping. Note the borderless, no-scaling, no-taskbar-composition conditions are the same ones that NVIDIA's present barrier needs.
- For Vulkan on Windows, present timing support beyond NVIDIA's driver (i.e. AMD Windows) is unconfirmed. A Vulkan presentation layer should treat `present_wait2` as the portable baseline and present timing as an NVIDIA-first enhancement.
- For a GL-on-Windows build, the presenter behaviour is a per-driver setting outside the app. That argues for moving presentation to DXGI (GL→D3D interop, or ANGLE as PlayMap already does) or to Vulkan/D3D12, rather than relying on the GL swap path.

### Gaps
- I found no Microsoft document listing the exact Windows 11 24H2/25H2 conditions under which a flip swap chain is denied independent flip (e.g. HDR mismatch, rotation, cursor, overlays). PresentMon remains the empirical check.
- AMD's Windows Vulkan driver support for `VK_EXT_present_timing`, `VK_KHR_present_wait2` and `VK_EXT_full_screen_exclusive` as of late 2026 was not found.
- The `VkPresentModeKHR` definitions (FIFO = queue on vblank, no tearing; FIFO_RELAXED = tears if late; MAILBOX = replace queued image, no tearing; IMMEDIATE = may tear) are standard spec text I did not re-fetch this session ([refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VkPresentModeKHR.html)).

## 3. Multi-output on one GPU and across GPUs; DWM, display ownership, EDID/timings

### Takeaway
Outputs on one GPU are not phase-aligned unless the driver locks them: internal framelock on a professional card, Mosaic, or a Sync card for several GPUs. Mosaic across GPUs on PCIe alone is explicitly unsynchronized. Composed (DWM) presentation follows one compositor cadence (the primary display's for DXGI). Independent Flip, or taking displays away from the desktop ("specialized displays" plus `Windows.Devices.Display.Core`, NVIDIA's DDisplay / `VK_KHR_display`), removes DWM from the path. Framelock requires identical timings within ±50 ppm, so identical EDIDs/custom timings are a precondition.

### Cited Findings
- Synchronized Mosaic "will ensure no tearing across monitors". For two or more GPUs a Sync card is needed. "Even though Mosaic mode can be enabled when GPUs are connected through the PCIe bus, it is not synchronized." — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- The D3D12 present barrier "works correctly only when displays are attached to the same GPU and set to the same timing", unless synchronized by the Sync card, NVLink or Mosaic. — [NVIDIA Technical Blog](https://developer.nvidia.com/blog/synchronizing-present-calls-between-applications-on-distributed-systems-with-directx-12/)
- disguise: framelock "keeps individual outputs of the same server in sync". Internal framelock is configured in the NVIDIA/AMD panel by selecting a timing-server display and ticking the others. — [disguise Genlock Configuration](https://help.disguise.one/designer/configuration/genlock-configuration)
- disguise recommends "all output heads … identical refresh rate and resolution". "Outputs cannot genlock if their resolutions match but their EDIDs differ." — [disguise Head Configuration](https://help.disguise.one/designer/feed-outputs/head-configuration)
- Pixera: "For syncing outputs on the internal timing it is mandatory to use the same EDID on all outputs." Sync must be re-applied whenever displays, resolution or refresh change. — [Pixera Sync](https://help.pixera.one/synchronize-outputs-genlock-framelock-setup)
- Mixed rates under lock: Sync card multiply/divide 1–8 (firmware 2.18+), and up to two resolutions per system at the same refresh (±50 ppm). — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- DWM cadence: "the DXGI swapchain API always uses the cadence of the primary monitor, regardless of what window the application is displayed on". The compositor clock API (`DCompositionGetTargetStatistics`, per-target statistics) replaces `WaitForVBlank` for multi-monitor heartbeats but gives "incomplete information on frames that are not composed, such as in iflip". — [MS Learn: Compositor clock](https://learn.microsoft.com/en-us/windows/win32/directcomp/compositor-clock/compositor-clock)
- Windows 11 (Insider build 25915, July 2023) changed the logic "to allow different refresh rates on different monitors, depending on the refresh rate for each monitor and content shown". — [Tom's Hardware](https://www.tomshardware.com/news/windows-11-refresh-rate-multi-monitors)
- **Specialized displays**: only custom compositors can address them; DWM ignores them (no desktop, no auto power-on, no touch/mouse). Designation is by the Microsoft EDID VSDB (version 0x3 for non-HMD specialized displays, Windows 10 1903+) or by the user toggle ("Remove display from desktop"). "Displays may not be designated as HMDs or specialized displays by overriding the EDID in software." Available from Windows 10 2004, and "require Windows 10 Enterprise, Windows 10 Pro for Workstations, or Windows 10 IoT Enterprise". The API is `DisplayManager.Create(EnforceSourceOwnership)`, `TryAcquireTarget(s)…`, `DisplayState.TryApply` (set modes), then create scanout resources and schedule presents. — [MS Learn: Custom compositor for specialized monitors](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/specialized-monitors-compositor); [MS Learn: EDID extension](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/specialized-monitors-edid-extension); [DisplayManager class](https://learn.microsoft.com/en-us/uwp/api/windows.devices.display.core.displaymanager?view=winrt-28000); [specialized-monitors.md](https://github.com/MicrosoftDocs/windows-driver-docs/blob/staging/windows-driver-docs-pr/display/specialized-monitors.md)
- Without the EDID extension, third-party compositors "must use HWND-based or CoreWindow-based presentation APIs, which don't allow for exclusive access" and the desktop compositor "can incur extra nondeterministic latency in some scenarios". — [MS Learn: EDID extension](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/specialized-monitors-edid-extension)
- NVIDIA `configureDdisplay.exe` removes and returns displays to the desktop compositor. A removed display can then be acquired via a `VK_KHR_display` swapchain, `Windows.Devices.Display.Core`, or `NvAPI_DISP_AcquireDedicatedDisplay`. — [NVIDIA Configure DDisplay Utility](https://www.nvidia.com/en-us/drivers/ddisplay-utility/)
- `VK_NV_acquire_winrt_display` takes exclusive control of a display not held by another compositor; releasing it from the desktop "must be performed outside of Vulkan" (Settings, Windows 10 2004+). — [VK_NV_acquire_winrt_display refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VK_NV_acquire_winrt_display.html)
- TouchDesigner's Direct Display Out uses this route, which "avoids a lot of the issues caused by the Windows Compositor" and keeps other windows and the cursor off the output. It is limited to 3 outputs and needs a workstation NVIDIA GPU ("Geforce will not be able to remove displays … using configureDdisplay.exe"). — [TD Direct Display Out TOP](https://docs.derivative.ca/Direct_Display_Out_TOP)
- The NVAPI display-control API exposes custom timing types (CVT, CVT-RB, DMT, EIA-861, SDI, custom) and EDID data. — [NVAPI Display Control (R590)](https://docs.nvidia.com/nvapi/group__dispcontrol.html)

### Inferences
- For PlayMap's "outputs on one machine share one vblank", the strongest single-GPU option short of a Sync card is NVIDIA internal framelock (Synchronize Displays, timing server = one output) on a professional card, or Mosaic. On GeForce and AMD consumer cards, outputs free-run at independent phases even at identical nominal refresh. PlayMap's per-output vblank fit should report that as phase drift rather than claim a lock.
- Specialized-display ownership is the route to deterministic, cursor-free, DWM-free outputs. It is vendor-neutral at the WinRT level, but needs Windows Enterprise / Pro for Workstations / IoT Enterprise and either a user toggle or an EDID VSDB, so it is an installation-time requirement for a media-server SKU. NVIDIA additionally ties the DDisplay present barrier to this route.
- The ±50 ppm framelock tolerance plus "same EDID" rules mean the presentation layer should own EDID/custom-timing management (emulated EDIDs, exact pixel clocks), and STATE should expose each output's exact timing (pixel clock, totals) so a lock refusal can name its cause.

### Gaps
- Whether AMD's Windows driver supports `Windows.Devices.Display.Core` scanout (and any AMD equivalent of `VK_KHR_display` on Windows) for removed displays was not confirmed.
- No source found on how many simultaneous independent-flip outputs one GPU sustains, or on MPO plane counts per output for current RTX/Radeon.
- No authoritative source on whether outputs of one consumer GPU at identical timing are phase-locked by default; the sources only say framelock/Mosaic are required.

## 4. Variable refresh (G-SYNC/FreeSync/Adaptive-Sync) and HDR/10-bit

### Takeaway
VRR is incompatible with genlock/framelock as documented: NVIDIA's sync setup says disable G-SYNC first, and projectors/LED processors downstream of genlock want fixed timing. VRR is useful for single-display, single-machine low-latency playback and, in principle, for software phase steering, because a present starts a refresh cycle. HDR needs flip model. DWM composes in FP16 scRGB when Advanced Color is on, and a full-screen HDR10 (R10G10B10A2 + PQ) swap chain can avoid the FP16 path.

### Cited Findings
- Cluster setup: "If you are using a G-SYNC display, disable G-SYNC" before enabling framelock, on server and clients. — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- RTX PRO Sync revision 08 (Apr 2025) mentions "New features highlighted, including Variable Refresh Rate" but documents nothing about it (see Gaps). — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)
- VRR with DXGI needs `DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING` and `DXGI_PRESENT_ALLOW_TEARING` for proper unlimited-rate support. — [NVIDIA Advanced API Performance: Swap Chains](https://developer.nvidia.com/blog/advanced-api-performance-swap-chains/)
- On a VRR display "the API call to deliver a frame, simply begins a new refresh cycle if the display isn't already in the middle of a refresh cycle. The display waits for your software"; the horizontal scan rate stays fixed and only the blanking interval varies. — [Blur Busters / WinUAE beam racing issue](http://github.com/tonioni/WinUAE/issues/133)
- `VK_EXT_present_timing` exposes a VRR indicator and multiple durations to describe VRR. — [VK_EXT_present_timing proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_present_timing.html)
- NVIDIA's LDAT guide claims "G-SYNC adds no latency". — [LDAT v2 User Guide (hosted copy)](https://filedn.com/lFoqnw8IpRE8IK7xJUtGgB5/LDAT%20v2%20User%20Guide%202.1.pdf)
- HDR: "When Advanced Color is enabled, the DWM performs its composition using IEEE half-precision floating point (FP16)" in scRGB (CCCS); flip model is required for Advanced Color. Option 1: FP16 `R16G16B16A16_FLOAT` (scRGB). Option 2: `R10G10B10A2_UNORM` with `SetColorSpace1(DXGI_COLOR_SPACE_RGB_FULL_G2084_NONE_P2020)`, which may perform better for HDR10 video or fullscreen use. Windows downconverts (clips) to what the display supports. — [MS Learn: Advanced Color](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range)
- The W7900 supports 10- and 12-bit display output. The FirePro W7000 datasheet (legacy) advertised a 30-bit display pipeline. — [AMD W7900](https://www.amd.com/en/products/graphics/workstations/radeon-pro/w7900.html); [W7000 datasheet](https://static6.arrow.com/aropdfconversion/8f3c2f247b6040afc403b88b6b5f06b3eccb8841/2793_w7000_datasheet_r4.pdf)

### Inferences
- Media-server presentation should treat VRR as OFF for any output that participates in a lock group or feeds genlocked LED/projectors. VRR is an opt-in per output for single-machine, single-display latency-critical cases.
- Without sync cards, VRR is a possible way to steer phase in software, because a present starts the refresh cycle. In theory nodes with VRR-capable displays could align refresh starts to a network-shared time with `VK_EXT_present_timing` or the composition swapchain's target time. I found no product or paper doing this for multi-machine walls, and projectors and LED processors are rarely VRR sinks; this is speculative.
- HDR output should keep the swap chain in a format that permits independent flip on the target display (HDR10 10-bit for a fullscreen HDR output), so DWM's FP16 composition is not forced into the path.

### Gaps
- No NVIDIA documentation found on what "Variable Refresh Rate" means for RTX PRO Sync (e.g. framelocked VRR across a cluster).
- No data found on whether an HDR10 flip swap chain stays in Independent Flip on current Windows 11 builds with mixed SDR/HDR monitors, or on latency differences between FP16 and HDR10 swap chains.
- AMD FreeSync interaction with Radeon PRO multi-display sync was not researched (no AMD framelock remains).

## 5. Latency: measuring and minimising photon latency

### Takeaway
On Windows the low-latency chain is: flip model in Independent Flip; a frame-latency waitable with max latency 1; just-in-time CPU start via vendor SDKs (NVIDIA Reflex: `NvAPI_D3D_SetSleepMode`/`Sleep`/markers, or `VK_NV_low_latency2`; AMD Anti-Lag 2 SDK for D3D11/D3D12 and `VK_AMD_anti_lag`); and present-time targeting (`VK_EXT_present_timing`, the composition swapchain). Beam racing / front-buffer rendering can go below a frame but needs tearing (VSYNC OFF) and is incompatible with locks. Verify with PresentMon (present mode, MsUntilDisplayed, MsPCLatency, MsAnimationError) and a photodiode (NVIDIA LDAT, AMD Frame Latency Meter, or a microcontroller rig).

### Cited Findings
- In Independent Flip with the waitable object, latency gets "down to 1 frame". `ALLOW_TEARING` goes lower still. — [MS Learn flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)
- **NVIDIA Reflex** (via Streamline 2.12): Reflex Low Latency on "GeForce 900 Series and newer", driver 456.38+. The frame-rate limiter works on all hardware; PC Latency (PCL) stats are vendor-agnostic. The NVAPI calls are `NvAPI_D3D_SetSleepMode`, `NvAPI_D3D_Sleep`, `NvAPI_D3D_SetLatencyMarker` and `NvAPI_D3D_GetLatency`. The QA checklist accepts up to a 4% FPS hit with Reflex On. — [Streamline Reflex Programming Guide](https://github.com/NVIDIA-RTX/Streamline/blob/main/docs/ProgrammingGuideReflex.md)
- **AMD Anti-Lag 2 SDK**: call `Update()` just before input polling, with an optional frame limiter. Driver support: Adrenalin 24.6.1+ (DX11), 24.7.1+ (DX12), 24.9.1+ (Vulkan). — [GPUOpen Anti-Lag 2](https://gpuopen.com/anti-lag-2/); [AntiLag2-SDK](https://github.com/GPUOpen-LibrariesAndSDKs/AntiLag2-SDK)
- `VK_AMD_anti_lag` "automatically paces the CPU to make sure it does not get too far ahead of the GPU", and the app can tell the driver when input processing begins. — [VK_AMD_anti_lag refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VK_AMD_anti_lag.html)
- An open-source Vulkan layer implements both `VK_NV_low_latency2` and `VK_AMD_anti_lag` hardware-agnostically, so the two extensions map onto the same pacing model. — [Korthos low_latency_layer](https://github.com/Korthos-Software/low_latency_layer/)
- **PresentMon**: v2.x metrics include `MsUntilDisplayed` (formerly DisplayLatency), `MsBetweenDisplayChange`, `MsPCLatency`, `MsAnimationError` (the gap between CPU delta and display delta), `AnimationTime` and `MsClickToPhotonLatency`. CSV headers changed in v2.3.1. v2.3.0 (Dec 2024) added "Instrumented Latency" from driver markers. — [PresentMon README](https://github.com/GameTechDev/PresentMon/blob/main/README-ConsoleApplication.md); [v2.3.0 release](https://github.com/GameTechDev/PresentMon/releases/tag/v2.3.0); [issue #468](https://github.com/GameTechDev/PresentMon/issues/468)
- **LDAT**: a luminance sensor measures from mouse-switch closure to a ≥6% luminance rise. It also measures display latency (scanout start to screen response) and GtG, and "works with GPUs from all vendors". — [NVIDIA LDAT](https://developer.nvidia.com/nvidia-latency-display-analysis-tool); [NVIDIA Reviewer Toolkit](https://www.nvidia.com/en-us/geforce/news/nvidia-reviewer-toolkit/)
- AMD's **Frame Latency Meter** validates Anti-Lag 2 integration (source on GitHub). — [AntiLag2-SDK](https://github.com/GPUOpen-LibrariesAndSDKs/AntiLag2-SDK)
- DIY photodiode rig: under €25, 116.5 µs internal error. Sensor position matters: at 60 Hz the top-to-bottom latency difference is 16.67 ms because of scanout. — [Uni Regensburg, "Yet Another Latency Measuring Device"](https://epub.uni-regensburg.de/45570/1/yet-another-latency-measuring-device.pdf)
- **Beam racing**: steer tearlines with `D3DKMTGetScanLine()` or `RasterStatus.ScanLine`, or by time offsets from a vsync timestamp, with VSYNC OFF ("software-based tearline-steering accuracy can be <0.1ms"). `QueryDisplayConfig()` gives the horizontal scan rate and vertical total, hence the exact blanking-interval time. — [Blur Busters](https://blurbusters.com/blur-busters-lagless-raster-follower-algorithm-for-emulator-developers/)
- Beam-racing caveats on Windows: "you typically need full screen exclusive + VSYNC OFF" for intentional tearing; "I can't ever get a tearline to appear in the first ~30 scanlines of my GeForce RTX on Windows 11"; always flush after present. — [VOGONS HOWTO (Blur Busters author)](https://www.vogons.org/viewtopic.php?t=95018)
- Vulkan front-buffer: `VK_KHR_shared_presentable_image` lets the app render while the presentation engine reads the image ("beam chasing" via strip rendering). — [VK_KHR_shared_presentable_image](https://registry.khronos.org/vulkan/specs/1.2-extensions/man/html/VK_KHR_shared_presentable_image.html)
- NVAPI warp/blend at scanout claims "no incremental latency" compared with external warp boxes. — [NVIDIA Warp and Blend](https://developer.nvidia.com/warp-and-blend)
- Hardware frame lock "reduces overall render performance due to the overhead it requires" (TouchDesigner), and a barrier makes every node wait for the slowest. — [TD Hardware Frame Lock](https://docs.derivative.ca/Hardware_Frame_Lock)

### Inferences
- PlayMap's doctrine "frame = f(leader time at vblank)" maps directly onto time-targeted presentation. The leader time for a frame is the target vblank's QPC/present-stage time: `SyncQPCTime` plus the period fit on DXGI, `VK_EXT_present_timing` stage times on Vulkan/NVIDIA, the composition swapchain's target time on Windows 11. Reflex/Anti-Lag are for game input loops; for a show-clock player the equivalent is starting CPU/GPU work just in time before the target vblank (waitable object + measured GPU time).
- Beam racing conflicts with framelock and with tear-free output across a wall. It is only relevant for a single output where sub-frame latency matters (e.g. camera-to-projector loops in scanning), and it needs tearing permitted.
- Photon latency must be measured at a fixed screen position (top/centre). PlayMap's "air latency" model should report the display's own latency separately, as LDAT does.

### Gaps
- Whether Reflex works on RTX PRO (workstation) drivers is not stated (the table says "GeForce 900 Series and newer"). Whether Anti-Lag 2 works on Radeon PRO PRO-Edition drivers is not stated (requirements are given as Adrenalin versions).
- No published numbers found for the latency added by the NvAPI present barrier or the swap barrier itself, beyond "performance overhead".
- No Windows API found for a sub-vblank scanline wait with D3D12 flip model apart from `D3DKMTGetScanLine`/`D3DKMTWaitForVerticalBlankEvent` (kernel-thunk APIs) and `IDXGIOutput::WaitForVBlank`.

## 6. Software sync across machines without sync cards (PTP/NTP, network vblank alignment)

### Takeaway
Software can align content (which frame is drawn) across machines to well under a frame. Windows NTP is supported to ~1 ms; Windows has a PTPv2 client since 1809 with NIC hardware timestamping APIs on Windows 11. Software cannot align GPU scanout phase, so without sync hardware displays on different machines refresh up to one frame apart, and tearing appears across LED/projector seams with fast motion. All products layer it the same way: network time for content, sync cards for phase and swap.

### Cited Findings
- WATCHOUT 7: NTP aligns system clocks "to within about a millisecond, but it does not align GPU output. Each node's GPU scans out on its own clock. The outputs between nodes therefore sit in different phases — a fraction of a frame apart". "Different Windows versions and GPU vendors also implement Full Screen Optimizations (FSO) differently, which changes GPU latency and widens the gap." On genlocked LED processors "even a sub-millisecond offset can shift the output by a frame and tear between panels". — [WATCHOUT 7 Time Synchronization](https://docs.dataton.com/guide/watchout/network-setup/time-synchronization.html); [Show Properties](https://docs.dataton.com/guide/watchout/working-with-shows/show-properties.html)
- TouchDesigner: "Even if the computers are generating content in perfect sync, displaying the images may introduce up to 1 frame of sync errors … the time when each display starts doing it's refresh may be offset by up to 16.6ms". Sync In/Out CHOPs keep timelines "within a single frame" (the clients pause until all have cooked). OSC multicast sync is "usually within 1-3 frames". Levels: weak (Touch In/Out), medium (OSC), tight (Sync In/Out), tight plus hardware (plus Quadro Sync frame lock). — [TD Syncing Multiple Computers](https://docs.derivative.ca/Syncing_Multiple_Computers); [TD Sync](https://docs.derivative.ca/Sync); [Sync In CHOP](https://derivative.ca/UserGuide/Sync_In_CHOP)
- disguise checks multi-machine sync with a readout that compares `tRender`, `tRunning`, `deltaTime` and `frameTime` across machines; `timerMode` must be Network, and `frameTime` "should always be in sync when Genlocked". — [disguise Output Sync Test](https://help.disguise.one/designer/networking/output-sync-test)
- nDisplay's Ethernet policy (software barrier plus VSync) avoids tearing within an output, but "tearing can still be possible among the displays because of Windows DWM". — [UE 4.27 nDisplay Synchronization](https://docs.unrealengine.com/4.27/en-US/WorkingWithMedia/IntegratingMedia/nDisplay/Synchronization/)
- Windows time: "Under reasonable operating conditions, systems can be configured to maintain 1 ms (millisecond) accuracy or better (with respect to UTC)" (Windows 10 1607+/Server 2016+, with support-boundary requirements on topology and latency). — [MS Learn: Configuring systems for high accuracy](https://learn.microsoft.com/en-us/windows-server/networking/windows-time-service/configuring-systems-for-high-accuracy?tabs=MaxPollInterval)
- Windows includes a PTPv2 (IEEE 1588v2) subordinate from Windows 10 October 2018 Update and Server 2019. — [microsoft/W32Time](https://github.com/microsoft/W32Time?tab=readme-ov-file)
- Windows packet timestamping: hardware NIC timestamps (NDIS 6.82+) or software (QPC) timestamps, but "having both hardware and software timestamps enabled together isn't supported". Scope is "PTPv2 over User Datagram Protocol (UDP). PTP over raw ethernet isn't supported." Winsock `SIO_TIMESTAMPING` delivers RX/TX timestamps; `CaptureInterfaceHardwareCrossTimestamp` relates the NIC clock to QPC. — [MS Learn: Packet timestamping](https://learn.microsoft.com/en-us/windows/win32/iphlp/packet-timestamping); [Winsock timestamping](https://learn.microsoft.com/en-us/windows/win32/winsock/winsock-timestamping); [NDIS timestamping overview](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/overview-of-ndis-packet-timestamping)
- `OID_TIMESTAMP_GET_CROSSTIMESTAMP`: minimum client Windows 11, server Windows Server 2022. — [MS Learn OID](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/oid-timestamp-get-crosstimestamp)
- NVIDIA Rivermax on Windows: "strict timing requirements (PTP, ST2110) necessitate the use of a BlueField card". PTP runs on the DPU's Arm cores (DOCA Firefly) and locks the NIC clock. — [Rivermax FAQ](https://developer.nvidia.com/networking/rivermax/faq)
- The Sync card's framelock frame counter is the cross-machine counter when hardware exists: the `WGL_NV_swap_group` frame counter and WATCHOUT's switch from NTP to the board counter. — [WGL_NV_swap_group](https://registry.khronos.org/OpenGL/extensions/NV/WGL_NV_swap_group.txt); [WATCHOUT Show Properties](https://docs.dataton.com/guide/watchout/working-with-shows/show-properties.html)

### Inferences
- PlayMap's software sync group (leader clock, anchors, per-output vblank reports, a phase board) reflects the state of the art for content alignment. Its honest ceiling without hardware is "same frame content, phase offset up to one refresh". It should keep reporting that ceiling as measured phase rather than as "locked", which PlayMap's `same vblank` verdict already gates on.
- Clock accuracy beyond ~1 ms (NTP) buys little for presentation unless phase can be moved. PTP with hardware timestamps on Windows 11 is worth it for tighter vblank-phase measurement (and for ST 2110), not for removing tearing.
- The only software lever on phase is the refresh itself: tiny custom-timing adjustments (pixel clock) to slew one output's phase toward a reference, or VRR-based present-triggered refresh. I found no product or API documentation doing pixel-clock slewing on Windows. It would be a research item, needing a measured cause and a deterministic test under the PlayMap doctrine.
- Products combine the layers the same way: network time (NTP/PTP or a software barrier) chooses which frame; the Sync card's swap barrier and frame counter guarantee when it flips. PlayMap's frame-lock machine can treat hardware lock as a strictly better driver behind the same `ANCHOR … @lock` contract.

### Gaps
- No measured data found for the Windows PTP client's achievable accuracy with hardware timestamping on common NICs (Intel I210/I225, Mellanox) on Windows 11.
- No source found for any Windows API that adjusts a running output's scanout phase (genlock-in-software) on NVIDIA or AMD consumer GPUs.
- No Resolume statement on genlock/framelock support was found in this pass.

## 7. Broadcast / ST 2110 and SDI outputs: when and how they genlock

### Takeaway
Media servers output SDI (AJA, Blackmagic DeckLink, Deltacast, disguise VFC) or ST 2110 (NVIDIA Rivermax on ConnectX/BlueField; AJA IP products) when feeding broadcast, camera/LED-processor chains or long-haul routing. These outputs genlock on the I/O card (reference input or ST 2059 PTP), not on the GPU's display engine. The renderer must be paced to the card's clock (frame-scheduled output, alignment points), and GPUDirect (NVIDIA DVP for DeckLink/AJA; Rivermax GPUDirect) removes host copies.

### Cited Findings
- WATCHOUT 7 "Genlock SDI" locks SDI output timing to an external reference (blackburst or tri-level) at the card's genlock input. It is a show-level property, separate from GPU Hardware Sync Groups. — [WATCHOUT 7 SDI Output](https://docs.dataton.com/watchout-7-new/watchout/displays-and-outputs/sdi-output.html); [Show Properties](https://docs.dataton.com/guide/watchout/working-with-shows/show-properties.html)
- TouchDesigner Video Device Out (Blackmagic, Bluefish444, AJA, Deltacast): on AJA a "Reference Source" can be external ref or SDI inputs 1–8. "Sync Outputs" (Pro license; Deltacast FLEX and Blackmagic) keeps independent outputs in lock-step; "Blackmagic requires a reference input". Without it, "each output will have it's own output queue length which may be off from the other nodes by 1 or 2 frames". — [TD Video Device Out TOP](https://derivative.ca/UserGuide/Video_Device_Out_TOP)
- The DeckLink API reports genlock reference status (`bmdReferenceLocked`/`Unlocked`/`NotSupportedByHardware`). "NVIDIA GPUDirect is supported on Windows and Linux … requires the use of the DVP library supplied by NVIDIA" (sample `LoopThroughWithOpenGLCompositing`). — [DeckLink BMDReferenceStatus](https://sdk-doc.blackmagicdesign.com/decklink-sdk/DeckLinkAPI/enums/bmdreferencestatus.html); [DeckLink SDK Manual](https://documents.blackmagicdesign.com/UserManuals/DeckLinkSDKManual.pdf?_v=1775631610000)
- Rivermax supports SMPTE 2110-20/-22/-30/-31/-40, 2022-7, 2022-6 and IPMX (JT-NM tested), with GPUDirect "on Linux and Windows". On Windows, PTP requires a BlueField DPU. — [Rivermax FAQ](https://developer.nvidia.com/networking/rivermax/faq)
- Unreal's Rivermax output "Alignment Point" mode schedules each frame on ST 2059 alignment points. The Rivermax custom timestep "genlock[s] the Engine for a specific frame rate and align[s] it based on the ST2059 alignment point formulas", requiring the PTP clock. On Windows with BlueField-2 the PTP clock is handled by the DPU. GPUDirect input is "currently globally disabled using a CVAR because of performance problems when receiving more than one stream". — [UE SMPTE 2110 reference (5.8)](https://dev.epicgames.com/documentation/unreal-engine/smpte-2110-ux-reference-in-unreal-engine)
- "ST 2110 compliance requires the Precision Time Protocol (PTP)". — [NVIDIA Holoscan for Media: Rivermax](https://docs.nvidia.com/holoscan-for-media/latest/user-guide/getting-help/rivermax-st-2110.html)
- AJA: "Without a PTP clock, there is no way to ensure lock. SDI output may appear miss aligned and HDMI may be intermittent." — [AJA FAQ](https://www.aja.com/support/item/6273)
- disguise VFC SDI cards with interlaced signals may not match the field of the incoming genlock. Apply Feed Settings is repeated "until the VFC card field sync matches", across all machines at once, "due to GPU genlock limitations". — [disguise Genlock Configuration](https://help.disguise.one/designer/configuration/genlock-configuration)
- The NVIDIA Sync card can output TTL sync to third-party equipment and accepts tri-level/bi-level house sync, so a GPU display engine and SDI/2110 gear can share one house reference. — [RTX PRO Sync User Guide v09](https://images.nvidia.com/aem-dam/Solutions/design-visualization/quadro-product-literature/nvidia-rtx-pro-sync-user-guide.pdf)

### Inferences
- In PlayMap's model, SDI/2110 outputs are a separate presenter type whose vblank truth comes from the I/O card (DeckLink reference status and scheduled-frame completion; Rivermax PTP time) rather than DXGI statistics. The leader-time function still applies: frame = f(time at the card's next alignment point).
- Mixing DisplayPort outputs (GPU display engine) and SDI/2110 outputs in one show needs a common house reference: tri-level sync to the RTX PRO Sync BNC and to the SDI card's reference, or a PTP grandmaster for 2110 plus a PTP-derived tri-level generator. Otherwise each clock domain drifts and needs frame repeat/drop.
- On Windows, ST 2110 with Rivermax implies BlueField DPU hardware for PTP. That is a heavy SKU decision; SDI cards with a reference input are the lighter path for broadcast-adjacent shows.

### Gaps
- AJA NTV2 SDK documentation for Windows genlock/reference APIs and GPUDirect specifics (beyond TouchDesigner's parameter list) was not fetched.
- No source found on Rivermax-on-Windows output latency, or on GPU-to-2110 frame pacing accuracy numbers.
- Deltacast and Bluefish444 genlock/SDK details were not researched.
