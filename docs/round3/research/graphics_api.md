# Primary graphics API for a Windows-only pro media server / projection-mapping renderer: OpenGL 4.6 vs Vulkan 1.4 vs Direct3D 12 (state as of October 2026)

Scope: Windows 11 (and Windows 10 22H2 where still relevant), x64, NVIDIA RTX / RTX PRO, AMD Radeon / Radeon PRO, Intel Arc. PlayMap today: .NET 10 engine with an OpenGL 3.3 core / GLES 3.0 renderer (Silk.NET + GLFW), an experimental D3D11 flip-model path through ANGLE, FFmpeg decode (D3D11VA slices copied once through ANGLE), Spout over its own D3D11 device, ISF effect chains translated to GLSL — see [docs/ARCHITECTURE.md](/home/user/mapper/docs/ARCHITECTURE.md). Framelock is covered by another researcher; presentation is covered here only enough to compare the APIs.

## 1. Driver quality, vendor investment and stability on Windows (NVIDIA, AMD, Intel)

### Takeaway
All three vendors now ship conformant Vulkan 1.4 drivers and current D3D12 (Agility SDK) drivers. New GPU features reach Windows first through D3D12, where Microsoft publishes a per-vendor driver list with each Agility SDK release, and through Vulkan extensions. OpenGL on Windows still gets maintenance but no new investment. AMD rewrote its OpenGL driver in 2022, which brought regressions with it, and Intel calls OpenGL "low priority". Pro media-server vendors standardise on NVIDIA, and some treat AMD as "test before you deploy" or no longer validate it at all.

### Cited Findings
- Vulkan 1.4 was announced in December 2024. By mid-2025, production drivers that passed Khronos conformance shipped from AMD, Intel, NVIDIA and others, and the Vulkan 1.4 SDK came out in January 2025 — [Khronos, "Vulkan: Continuing to Forge Ahead" (Aug 5, 2025)](https://www.khronos.org/blog/vulkan-continuing-to-forge-ahead-siggraph-2025)
- Microsoft ships D3D12 features in retail and preview Agility SDK pairs, each with a vendor driver matrix. Agility SDK 1.619 retail (Feb 26, 2026) shipped alongside 1.719-preview — [DirectX blog, SM 6.9 retail](https://devblogs.microsoft.com/directx/shader-model-6-9-retail-and-more/). Microsoft lists SM 6.9 support for AMD RX 9000, Intel Arc B-series and all NVIDIA RTX, and the 1.619 "customer-requested" features for AMD RX 7000/9000, Intel Arc B and all RTX — [VideoCardz summary of the DirectX blog table](https://videocardz.com/newz/microsoft-ships-shader-model-6-9-in-directx-12-agility-sdk-1-619)
- The Agility SDK release cadence is still active in 2026: 1.619.6 (Sep 14, 2026), 1.619.5 and 1.721.3-preview (Jul 30, 2026), with debug-layer, DRED and dump-file fixes in each point release — [DirectX 12 Agility SDK downloads page](https://devblogs.microsoft.com/directx/directx12agility/)
- Work Graphs 1.0 (Agility 1.613, Mar 11, 2024) launched with day-one AMD and NVIDIA drivers — [TechPowerUp](https://www.techpowerup.com/320213/microsofts-latest-agility-sdk-released-with-cutting-edge-work-graphs-api). AMD support required an RDNA 3 card — [AMD GPUOpen](https://gpuopen.com/news/microsoft-work-graphs-1-0-now-available/)
- **AMD OpenGL (Windows):** Adrenalin 22.7.1 (July 2022) brought "OpenGL Optimizations", up to +79% in Minecraft at 4K on an RX 6950 XT versus 22.6.1 — [AMD 22.7.1 release notes](https://www.amd.com/en/resources/support-articles/release-notes/RN-RAD-WIN-22-7-1.html). - Also on AMD: from 22.7.1 onward, a game that requested a 3.3 core context got a 4.6 compatibility context, with large performance losses. Users reproduced this on 24.3.1 in 2024; an AMD OpenGL engineer later saw 3.3 core on a newer build — [Vintage Story issue #2454](https://github.com/anegostudios/VintageStory-Issues/issues/2454). Older history from RPCS3's driver log: OpenGL rendered nothing on any AMD GPU with Adrenalin 19.12.1–20.1.3, and submit/flip latency regressed in 23.3.2–23.4.2 — [RPCS3 wiki, Graphics Driver Issues](https://github.com/RPCS3/rpcs3/wiki/Graphics-Driver-Issues/cb3fcbc11501b0fa29d195965b5876065f0a831f)
- **AMD Vulkan (Windows):** Vulkan 1.4 support arrived in Adrenalin 25.5.1 (May 7, 2025), and AMD continues to publish "Expanded Vulkan Extension Support" preview drivers up to 26.10.27.01 — [AMD Vulkan driver support page](https://www.amd.com/en/resources/support-articles/release-notes/RN-RAD-WIN-VULKAN.html). Users of 25.11.1 (Nov 13, 2025) reported a Vulkan regression (black/missing textures under DXVK) and said the new extensions in that driver (VK_KHR_swapchain_maintenance1, VK_EXT_host_image_copy, VK_KHR_maintenance9) were exposed only on RDNA 3+ — [DXVK issue #5332](https://github.com/doitsujin/dxvk/issues/5332) (user reports, not an AMD statement)
- AMD discontinued its open-source AMDVLK Vulkan driver (Linux) on Sep 15, 2025 in favour of Mesa RADV. In the same thread an AMD engineer said the PAL code base "is still used for Windows" — [AMDVLK discussion #416](https://github.com/GPUOpen-Drivers/AMDVLK/discussions/416)
- **AMD and Windows 10:** the Adrenalin 25.10.2 release notes list only "Windows 11 version 21H2 and later" — [AMD 25.10.2 notes](https://www.amd.com/en/resources/support-articles/release-notes/RN-RAD-WIN-25-10-2.html). Adrenalin 25.9.2 still listed "Windows 10 64-bit version 19044 and later" — [AMD 25.9.2 notes](https://www.amd.com/en/resources/support-articles/release-notes/RN-RAD-WIN-25-9-2.html)
- **Intel OpenGL:** an Intel community moderator wrote that "OpenGL unfortunately has low priority" on Arc — [IGCIT issue #402 (2023)](https://github.com/IGCIT/Intel-GPU-Community-Issue-Tracker-IGCIT/issues/402). On an Arc B580, Basemark scored OpenGL 4,570 against 12,281 for Vulkan and 12,082 for DX12, and Doom 2016 ran at roughly 30 fps in OpenGL against 199 fps in Vulkan; with ReBAR off, OpenGL fell 76% while Vulkan fell 3% — [IGCIT issue #1148 (June 2025)](https://github.com/IGCIT/Intel-GPU-Community-Issue-Tracker-IGCIT/issues/1148). Intel's support article says the B580 OpenGL Basemark issue is "resolved as of graphics driver 101.8974" (article last reviewed 08/20/2026) — [Intel support 000101542](https://www.intel.com/content/www/us/en/support/articles/000101542/graphics.html)
- Intel lists Arc A/B support as DirectX 12, OpenGL 4.6, OpenCL 3.0, Vulkan 1.3, and Vulkan 1.4 on Arc Pro — [Intel supported APIs](https://www.intel.com/content/www/us/en/support/articles/000005524.html)
- **Pro media vendors:** Smode requires GPUs with "OpenGL 4.6 and DirectX 12"; "Although AMD GPUs mostly work, they are no longer validated by SmodeTech". Smode R14 pins NVIDIA driver 582.16, Quadro Sync firmware 3.06, and Windows 10 22H2 / Windows 11 25H2 — [Smode requirements](https://doc.smode.io/userGuide/tutorialsAndHow-Tos/gettingStarted/requirements/)
- Notch's manual warns: "Some servers use AMD GPUs which have show-stopping driver bugs" — [Notch manual 2026.2, Using Notch in disguise](https://manual.notch.one/2026.2/en/docs/workflows/working-with-media-servers/blocks/using-notch-in-d3/). disguise's compatibility table marks Notch 2026.1+ blocks as not playable on its AMD GCN servers — [disguise Notch v1.0+ compatibility table](https://help.disguise.one/designer/layers/layer-types/generative/notch-1-compatibility-table). Notch v1.0 supports only NVIDIA Maxwell or newer, and v1.1 only Turing or newer — [disguise legacy help](https://legacy-help.disguise.one/en/Content/Sequencing/Layers/Layer-Types/Generative/Notch.html)
- Watchout 7: "While AMD GPUs may work, NVIDIA is recommended for full WATCHOUT feature support. AMD graphics cards require additional testing before deployment." Hardware genlock/framelock, EDID management and GPUDirect need NVIDIA professional GPUs — [Dataton Watchout 7 system requirements](https://docs.dataton.com/guide/watchout/getting-started/system-requirements.html)

### Inferences
- New capability ships to Windows in this order: D3D12 (Microsoft and the IHVs coordinate through the Agility SDK, with day-one drivers and a published support matrix), then Vulkan extensions (NVIDIA and AMD often ship beta drivers first; Intel trails on Windows). OpenGL gets maintenance and bug fixes only. Intel publicly deprioritises it, and AMD's one large investment (2022) brought compatibility regressions.
- For show reliability, the realistic tiers are NVIDIA RTX/RTX PRO as tier 1, AMD RDNA 3/4 as tier 2 (validated per driver), and Intel Arc B as tier 3. Peer products already work this way (Smode, Watchout, Notch/disguise).
- AMD dropping Windows 10 from 25.10.2 onward, and D3D12 features that require Windows 11 24H2 builds (GPU upload heaps need build 26080+, see section 2), both point to Windows 11 24H2+ as the realistic baseline. Windows 10 22H2 would be "best effort, older drivers".

### Gaps
- No primary source quantifies GPU crash/TDR rates per API per vendor. The evidence above is release notes plus user and issue-tracker reports.
- I found no 2025–2026 public NVIDIA statement on its OpenGL roadmap for Windows. NVIDIA still supports OpenGL 4.2–4.6 in its tools (section 5).
- I did not re-source the Windows 10 end-of-support date in this pass.
- Whether AMD has formally moved RDNA 1/2 to a maintenance branch is supported only by the user comment in DXVK #5332. I found no AMD primary statement.

## 2. Feature reach: what each API can express on 2026 hardware

### Takeaway
D3D12 and Vulkan both cover the modern feature set: bindless, mesh shaders, ray tracing, async compute and copy queues, timeline fences, HDR swapchains, and ReBAR-style upload. D3D12 has the cross-vendor lead in work graphs, sampler feedback, the SM 6.9 DXR 1.2 features, GPU upload heaps and Advanced Shader Delivery. Vulkan's 2026 additions are VK_EXT_descriptor_heap (a full replacement of descriptor sets) and the Roadmap 2026 profile. OpenGL 4.6 (2017) has none of the explicit multi-queue, ray tracing, work graph, sampler feedback or video-engine facilities.

### Cited Findings
- **Shader Model 6.9 (retail, Agility 1.619 with DXC 1.9.2602.16, Feb 26, 2026):** long vectors (up to 1024 elements); 16-bit float specials (IsNan, IsInf, IsFinite, IsNormal); 16-bit and 64-bit shader ops and wave ops become required; the HLSL side of DXR 1.2 (Opacity Micromaps, Shader Execution Reordering); revised resource-view creation APIs; periodic trim notifications; a raised dispatch-grid limit; CPU timeline query — [DirectX blog](https://devblogs.microsoft.com/directx/shader-model-6-9-retail-and-more/); [Agility downloads page](https://devblogs.microsoft.com/directx/directx12agility/)
- Hardware split for DXR 1.2: SER is supported by AMD RX 9000 without actual reordering, and with reordering on Intel Arc B and RTX 40+. Opacity Micromaps are RTX-only (hardware-accelerated on RTX 40+, emulated on older RTX) — [VideoCardz, from Microsoft's table](https://videocardz.com/newz/microsoft-ships-shader-model-6-9-in-directx-12-agility-sdk-1-619); [SER blog](https://devblogs.microsoft.com/directx/shader-execution-reordering/)
- Cooperative Vector was deprecated in favour of a unified matrix/vector linear-algebra design planned for SM 6.10 — [DirectX blog (Sep 11, 2025)](https://devblogs.microsoft.com/directx/shader-model-6-9-and-the-future-of-cooperative-vector/). Agility 1.721-preview (Jul 30, 2026) adds LinAlg VectorAccumulate (SM 6.10 preview), partial programs, GUID texture layout, UAVs of depth, and DX dump files — [Agility downloads page](https://devblogs.microsoft.com/directx/directx12agility/)
- Agility 1.719-preview (Feb 2026) adds **Fence Barriers**, which let command lists signal and wait on fences inside the command stream as an extension of Enhanced Barriers. It also adds **VPblit 3DLUT** (tone mapping and LUTs on the video-processing block) and an official **D3D12 Extensions** mechanism for vendor features. Fence Barriers support is listed for AMD RX 7000/9000 and Intel Arc B; NVIDIA is "vendor access" — [VideoCardz](https://videocardz.com/newz/microsoft-ships-shader-model-6-9-in-directx-12-agility-sdk-1-619)
- **Work Graphs 1.0, SM 6.8 and GPU Upload Heaps** went retail in Agility 1.613 (Mar 11, 2024). GPU upload heaps let the CPU write VRAM directly through resizable BAR, and the retail feature requires Windows 11 build 26080 or later — [DirectX blog 1.613](https://devblogs.microsoft.com/directx/agility-sdk-1-613-0/). AMD notes that GPU upload heaps work only where ReBAR is enabled in UEFI, and that its D3D12 Memory Allocator supports them — [AMD GPUOpen](https://gpuopen.com/news/microsoft-work-graphs-1-0-now-available/)
- Work-graph **mesh nodes** require SM 6.9 (`lib_6_9`) and AMD RX 7000/9000 — [GPUOpen mesh nodes getting started](https://gpuopen.com/learn/work_graphs_mesh_nodes/work_graphs_mesh_nodes-getting_started/)
- Vulkan has work graphs only through AMD's experimental **VK_AMDX_shader_enqueue** (RX 7000). Mesh nodes were added in a beta driver (Oct 2024), and AMD says it will "work towards standardizing it as an EXT or KHR extension eventually" — [GPUOpen, work graph mesh nodes in Vulkan](https://gpuopen.com/learn/gpu-workgraphs-mesh-nodes-vulkan/)
- **Bindless:** D3D12 SM 6.6 "dynamic resources" (descriptor-heap indexing) and Enhanced Barriers are among the Agility 1.606-era features WARP implements — [DirectX blog, WARP preview (Oct 2022)](https://devblogs.microsoft.com/directx/announcing-warp-preview-with-shader-model-6-7-support/). Vulkan's **VK_EXT_descriptor_heap** (spec 1.4.340, Jan 23, 2026) "is intended to completely replace Vulkan's existing descriptor set mechanism". It has two explicit heaps (sampler and resource) and needs buffer device address plus untyped pointers. It ships as an EXT that "is not going to change", with a KHR version to follow — [Khronos blog](https://www.khronos.org/blog/vulkan-introduces-roadmap-2026-and-new-descriptor-heap-extension); [Vulkan-Docs 1.4.340 changelog](https://github.com/KhronosGroup/Vulkan-Docs/commit/87e6442f335fc08453b38bbd092ca67c57bfd3ab); [Khronos, "Simplifying Vulkan One Subsystem at a Time" (Feb 5, 2026)](https://www.khronos.org/blog/simplifying-vulkan-one-subsystem-at-a-time); [Vulkan Guide, descriptor heap](https://docs.vulkan.org/guide/latest/descriptor_heap.html)
- **Vulkan Roadmap 2026** (Jan 23, 2026) requires variable rate shading, shader clock queries, host image copies, compute-shader derivatives, "various swapchain improvements", and higher descriptor and shader-interface limits. "Most Vulkan adopters supporting the Vulkan 2026 milestone will offer conforming devices by the end of this year" — [Khronos blog](https://www.khronos.org/blog/vulkan-introduces-roadmap-2026-and-new-descriptor-heap-extension)
- **Sampler feedback:** D3D12 Tier 0.9 on Intel Arc; the Vulkan column says "N/A". Mesh shading on Arc: D3D12 Tier 1, Vulkan "work in progress" (older Intel guide) — [Intel Arc A-series API guide](https://www.intel.com/content/www/us/en/developer/articles/guide/arc-a-series-gaming-api-developer-optimization.html)
- **Advanced Shader Delivery** (PSO/state-object database, app identity API, stats API; Agility 1.619; PIX shows its counters from the May 2026 release) — [DirectX blog, GDC 2026](https://devblogs.microsoft.com/directx/advanced-shader-delivery-whats-new-at-gdc-2026/)
- **Multi-queue:** NVRHI takes up to three queues (graphics, compute, copy) on DX12 and Vulkan, and maps DXR and KHR ray tracing — [NVRHI programming guide](https://github.com/NVIDIA-RTX/NVRHI/blob/main/doc/ProgrammingGuide.md). A Vulkan log on an RTX 3090 Ti (Windows) shows separate async-compute and transfer queue families, and a 224 MB DEVICE_LOCAL|HOST_VISIBLE heap when ReBAR is not in use — [X-Plane forum log (Oct 2022)](https://forums.x-plane.org/forums/topic/276396-xp12-dxgi-swap-chain-openglvulkan-in-nvidia-52647/)
- **Timeline sync:** D3D12 fences carry 64-bit values, which other engines consume as "fence points" (NVENC's D3D12 interface takes fence/value pairs) — [NVENC programming guide 13.0](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-video-encoder-api-prog-guide/index.html). The Vulkan SDK added synchronization validation for VK_KHR_timeline_semaphore in October 2024 — [Khronos](https://www.khronos.org/blog/vulkan-continuing-to-forge-ahead-siggraph-2025)
- **HDR / 10–16-bit:** a DXGI flip-model swapchain supports FP16 scRGB and HDR10 (R10G10B10A2 with DXGI_COLOR_SPACE_RGB_FULL_G2084_NONE_P2020), for Direct3D 11 or 12 — [Microsoft Learn, Advanced Color](https://learn.microsoft.com/en-us/windows/win32/direct3darticles/high-dynamic-range). HDR formats "aren't clamped unless composed to an SDR desktop" — [Microsoft Learn, flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model). NVIDIA's Windows Vulkan driver exposes R16G16B16A16_SFLOAT and A2B10G10R10 surface formats — [X-Plane log](https://forums.x-plane.org/forums/topic/276396-xp12-dxgi-swap-chain-openglvulkan-in-nvidia-52647/). Smode: its "Enforce OS Environment" setting "was primarily for 10-bit color depth with OpenGL. It's not necessary with DirectX12 with native 10-bit support" — [Smode GPU settings](https://doc.smode.io/reference/preferences/engine/other/gpu-settings/)
- In 2019 Notch built its ray tracer on DirectX 11 compute rather than DXR, citing "the lack of support for DirectX 12 … in current media servers" (historical) — [CG Channel (Feb 2019)](https://www.cgchannel.com/2019/02/sneak-peek-real-time-ray-tracing-in-notch-builder/)

### Inferences
- What OpenGL cannot do on Windows, beyond the items sourced above (background knowledge, not re-verified this pass): no hardware ray tracing in core, no work graphs, no sampler feedback, no explicit multi-queue or async compute, no explicit memory heaps or ReBAR placement, no video decode/encode engine access, no HDR/flip-model swapchain without driver layering, and no multithreaded command recording. Mesh shaders and bindless exist only as vendor or ARB extensions, not core.
- For PlayMap's workload (many video layers, warps/blends, ISF chains, 3D projection, network packing on the GPU, 10/12-bit output), the features that change outcomes are: async copy queues (uploads and readbacks off the render queue), timeline fences shared with decode and encode engines, HDR/10-bit flip-model output, and GPU upload heaps or ReBAR for per-frame data. Both D3D12 and Vulkan have all of these. Work graphs and SER are optional extras.
- The descriptor models are converging. D3D12's heap model has been stable since SM 6.6. Vulkan's equivalent (descriptor_heap) is brand-new as an EXT in 2026, so Vulkan bindless code written now may migrate once more when the KHR lands.

### Gaps
- Per-vendor Windows support for VK_EXT_descriptor_heap as of Oct 2026 was not found.
- I did not find a per-vendor matrix for Vulkan SER or opacity-micromap equivalents on Windows.
- GL_ARB_bindless_texture and GL_NV_mesh_shader availability per vendor on Windows were not verified.

## 3. Presentation and latency facilities (comparison level only)

### Takeaway
D3D12 sits directly on DXGI's flip model (DirectFlip, independent flip, MPO, waitable swapchains, tearing, frame statistics, HDR). It also has access to Windows 11's composition swapchain, whose presents can target a specific time, and to NVIDIA's present barrier for framelock. Vulkan on Windows gained real frame-pacing tools in 2025 (present_wait2/present_id2, and VK_EXT_present_timing with absolute or relative target times), but the timing extension is new and NVIDIA-first, and Windows presentation behaviour depends on each vendor's WSI layer. OpenGL has wgl swap control only. Getting flip-model behaviour on NVIDIA requires a driver setting ("Prefer layered on DXGI swapchain").

### Cited Findings
- DXGI flip model: DirectFlip, DirectFlip with panel fitters, DirectFlip with MPO, and "Independent Flip" (DWM bypassed). The waitable object (DXGI_SWAP_CHAIN_FLAG_FRAME_LATENCY_WAITABLE_OBJECT) can reach 1 frame of latency in independent flip on Windows 10 Fall Creators Update and later. DXGI_SWAP_CHAIN_FLAG_ALLOW_TEARING lowers latency further, even windowed, with MPO. IDXGIOutput6::CheckHardwareCompositionSupport queries what the hardware supports — [Microsoft Learn, use DXGI flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)
- Flip-model swapchains provide present statistics (IDXGISwapChain::GetFrameStatistics) in both windowed and full-screen mode; bitblt windowed swapchains return zeroes — [Microsoft Learn, DXGI flip model](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-flip-model)
- **Composition swapchain API (Windows 11):** presents can carry a target time (IPresentationManager::SetTargetTime, system interrupt time in 100 ns units), with a present-retiring fence and statistics (displayed time, present duration). Requirements: Windows 11 build 22000.194+ and WDDM 2.0; direct scanout and independent flip require WDDM 3.0. Microsoft: "the composition swapchain API offers the ability for presents to target a specific time … whereas DXGI doesn't", and its initial focus is media frameworks — [Microsoft Learn, composition swapchain](https://learn.microsoft.com/en-us/windows/win32/comp_swapchain/comp-swapchain); [portal](https://learn.microsoft.com/en-us/windows/win32/comp_swapchain/comp-swapchain-portal); [examples](https://learn.microsoft.com/en-us/windows/win32/comp_swapchain/comp-swapchain-examples)
- **NVIDIA present barrier (NvAPI, D3D12):** combines swap groups and swap barriers. It needs a full-screen window with no borders, desktop scaling or taskbar composition, and either a Quadro Sync board or Mosaic. The client is created from the D3D12 device and DXGI swapchain — [NVIDIA blog (Jul 2022)](https://developer.nvidia.com/blog/synchronizing-present-calls-between-applications-on-distributed-systems-with-directx-12/). It requires an "NVIDIA RTX / Quadro series card (GeForce is NOT supported)" and driver 472.12+ — [nvpro-samples/dx12_present_barrier](https://github.com/nvpro-samples/dx12_present_barrier). An NVIDIA moderator: "Present barrier is an updated API replacing the swap groups and barriers and available for both Vulkan and DX12", and it is non-blocking by default — [NVIDIA developer forum (Feb 2025)](https://forums.developer.nvidia.com/t/quadro-sync-ii-clarification-on-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/323309)
- Unreal nDisplay's NVIDIA sync policy uses NVIDIA swap groups and barriers (Quadro Sync), and nDisplay supports DX11 and DX12 — [UE 4.27 nDisplay synchronization](https://docs.unrealengine.com/4.27/en-US/WorkingWithMedia/IntegratingMedia/nDisplay/Synchronization/); [nDisplay whitepaper](https://cdn2.unrealengine.com/Unreal+Engine%2Fndisplay-whitepaper-final-updates%2FnDisplay_Whitepaper_FINAL-f87f7ae569861e42d965e4bffd1ee412ab49b238.pdf)
- Smode 10.2 (Dec 10, 2024) "is now by default using the DirectX12 graphics API to handle the GPU graphics outputs and genlock / multi server sync, as a replacement for OpenGL" — [Smode 10.2 changelog](https://doc.smode.io/changelog/Smode102/). Smode settings: "First Swap On Primary Screen Tricks and Swap Exchange are editable only for 'OpenGL' Presenting API, primarily to address legacy driver issues"; "Async Present is editable only for 'DirectX12' … allows some driver bug workarounds" — [Smode GPU settings](https://doc.smode.io/reference/preferences/engine/other/gpu-settings/)
- **Vulkan:** VK_KHR_present_wait2 (with VK_KHR_present_id2) replaces present_wait. It is queryable per surface and "not intended for time-to-light estimation" — [Vulkan refpage](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_present_wait2.html). **VK_EXT_present_timing** (announced Dec 4, 2025) adds timing feedback for past presents and "present at absolute/relative time", present stages including first pixel visible, and VRR properties. Drivers: "NVIDIA developer drivers — available now; Mesa — coming soon; Android 17 — coming soon"; "some use cases—such as driving complex display topologies—are not yet possible with this extension alone" — [Khronos blog](https://www.khronos.org/blog/vk-ext-present-timing-the-journey-to-state-of-the-art-frame-pacing-in-vulkan); [proposal](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_present_timing.html). It depends on VK_KHR_present_id2 and VK_KHR_calibrated_timestamps — [LunarG refpage, SDK 1.4.350](https://vulkan.lunarg.com/doc/view/1.4.350.0/windows/antora/refpages/latest/refpages/source/VK_EXT_present_timing.html)
- **NVIDIA "Vulkan/OpenGL present method"** (driver setting OGL_CPL_PREFER_DXPRESENT: Prefer disabled / Prefer enabled / Auto, default Auto) — [NVAPI driver settings reference](https://docs.nvidia.com/nvapi/NvApiDriverSettings_8h.html). It appeared around driver 526.47 (Oct 2022) and gives OpenGL and Vulkan apps DXGI flip-model presentation when set to "Prefer layered on DXGI Swapchain" — [X-Plane forum quoting 526.47 notes](https://forums.x-plane.org/forums/topic/276396-xp12-dxgi-swap-chain-openglvulkan-in-nvidia-52647/). A MonoGame user reported borderless full-screen broken under DesktopGL unless that setting was forced; the project "switched to DirectX for the Windows build" — [MonoGame #8629 (Jan 2025)](https://github.com/MonoGame/MonoGame/issues/8629). DXVK-on-Windows users needed the same setting; "without this setting … the Nvidia driver tries to use a direct native GDI copy present method" — [DXVK #5171](https://github.com/doitsujin/dxvk/issues/5171)
- Intel recommends flip-model swapchains and verifying "Hardware Composed: Independent Flip" in PresentMon — [Intel Arc API guide](https://www.intel.com/content/www/us/en/developer/articles/guide/arc-a-series-gaming-api-developer-optimization.html)

### Inferences
- D3D12 gives first-party, documented control over every Windows presentation mode that matters for latency and for a "content = f(show time at vblank)" doctrine: iflip with a 1-frame waitable, frame statistics with QPC sync times, the composition swapchain's target-time presents, and NVIDIA's present barrier. With Vulkan, the same outcomes depend on how each IHV maps Vulkan WSI onto DXGI or its own path, which is why NVIDIA needed a control-panel switch. present_timing is the strongest Vulkan argument, but in late 2025 it was NVIDIA developer drivers only.
- PlayMap's experimental "D3D11 flip model through ANGLE" exists because GL cannot do this natively on Windows. A D3D12 renderer removes the ANGLE indirection and keeps the same DXGI semantics.

### Gaps
- I found no source on AMD's or Intel's Windows Vulkan WSI implementation (DXGI-layered or not), or on their VK_EXT_present_timing plans.
- I found no source confirming that the composition swapchain API accepts D3D12-allocated buffers (the docs discuss D3D11 surfaces). It needs verification before relying on it from D3D12.
- VK_EXT_present_mode_fifo_latest_ready and VK_NV_low_latency2 were not researched.

## 4. Video: decode/encode APIs, zero-copy and interop (D3D11/Spout, NDI, FFmpeg)

### Takeaway
On Windows, the zero-copy paths cluster around the DirectX family. FFmpeg's D3D11VA and D3D12VA decoders, NVENC's D3D12 interface, the D3D12 Video encode API (H.264/HEVC since Windows 11; AV1 since Windows 11 24H2), and Spout's D3D11 shared textures all use D3D resources and fences. Vulkan Video gives one cross-vendor API, and FFmpeg 8.0 supports it broadly, but Windows driver maturity is uneven (Intel lags). Importing D3D11 shared textures into Vulkan is an optional feature that fails on some GPUs. That breaks Spout under TouchDesigner on Intel iGPUs.

### Cited Findings
- **D3D12 Video encode:** added in Windows 11 (WDDM 3.0) for H.264 and HEVC; "AV1 Encode is added in Windows 11 24H2 (WDDM 3.2)" — [Microsoft Learn, D3D12 video encoding (driver docs)](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/video-encoding-d3d12). The spec calls out efficient interop between D3D12 video encode and D3D12 graphics, compute and ML — [DirectX-Specs, D3D12 Video Encoding](https://microsoft.github.io/DirectX-Specs/d3d/D3D12_Video_Encoding_H264_HEVC.html)
- Agility 1.619.5 adds ETW logging "in the case D3D12 Video Encode support is not available due to exclusive engine access taken by another actor" — [Agility downloads page](https://devblogs.microsoft.com/directx/directx12agility/)
- **FFmpeg (changelog):** D3D12VA hardware decoding for H.264, HEVC, VP9, AV1, MPEG-2 and VC-1; a D3D12VA HEVC encoder; and "D3D12 AV1 encoder" in master after 8.0. Vulkan decode for H.264, HEVC and AV1; Vulkan H.264 and H.265 encoders — [FFmpeg Changelog (master)](https://github.com/FFmpeg/FFmpeg/blob/master/Changelog). **FFmpeg 8.0 "Huffman" (Aug 22–23, 2025)** added Vulkan VP9 decode, Vulkan AV1 encode, and "Vulkan compute-based codecs" (FFv1 encode/decode, ProRes RAW decode) that run "on any implementation of Vulkan 1.3"; ProRes and VC-2 Vulkan compute implementations were "in review" — [FFmpeg 8.0 announcement](https://ffmpeg.org/pipermail/ffmpeg-devel/2025-August/347886.html); [FFmpeg 8.0 Changelog](https://github.com/FFmpeg/FFmpeg/blob/n8.0/Changelog)
- **Vulkan Video timeline:** H.264/H.265 decode finalized Dec 2022; AV1 decode in SDK 1.3.277 (Feb 2024); AV1 encode and quantization map in 1.3.302 (Nov 2024); VP9 decode in 1.4.317 (June 2025); encode intra-refresh in 1.4.321 (July 2025) — [Igalia, Vulkanised 2025](https://www.vulkan.org/user/pages/09.events/vulkanised-2025/T31-Stephane-Cerveau-Igalia.pdf); [Khronos SIGGRAPH 2025](https://www.khronos.org/blog/vulkan-continuing-to-forge-ahead-siggraph-2025)

Motion-estimation-only mode is not supported on D3D12 — [NVENC guide 13.0](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.0/nvenc-video-encoder-api-prog-guide/index.html). - **Spout (D3D11 shared textures):** Spout's DirectX 12 support class uses D3D11On12. - D3D11On12 notes: the D3D11 immediate context must be flushed before more D3D12 work goes on the shared queue, and resource state coherency is maintained only through Acquire/ReleaseWrappedResources — [Microsoft Learn, D3D11On12](https://learn.microsoft.com/en-us/windows/win32/direct3d12/direct3d-11-on-12)
- Zero-copy D3D11↔D3D12 without 11on12: NT-handle shared textures plus shared fences (ID3D11Device5; Windows 10 1703+), "GPU-side fence synchronization — no CPU blocking" — [VL.Stride.DX12Bridge (vvvv)](https://www.nuget.org/packages/VL.Stride.DX12Bridge/)
- **Vulkan import of D3D11 textures:** handle types D3D11_TEXTURE (NT, from CreateSharedHandle) and D3D11_TEXTURE_KMT (global, from GetSharedHandle). Both require the same device UUID and driver UUID and report DEDICATED_ONLY — [Vulkan spec, capabilities](https://docs.vulkan.org/spec/latest/chapters/capabilities.html). Some Intel iGPUs do not support the KMT type at all — [vulkan-interop-directx issue #2](https://github.com/malstraem/vulkan-interop-directx/issues/2). wgpu had to add dedicated allocation to make D3D11 shared-handle import work on AMD and NVIDIA (June 2025) — [wgpu commit](https://github.com/gfx-rs/wgpu/commit/65337894f609b536d0016fbabfea6324c5b98faf). In TouchDesigner (Vulkan), Spout failed on an Intel UHD 730 ("Spout may not be Vulkan compatible on this GPU"). Derivative: the needed Vulkan feature "isn't necessarily available on all GPUs … It's an optional feature"; the user downgraded to the pre-Vulkan TD 2021 build, which worked — [TouchDesigner forum (Oct 2025)](https://forum.derivative.ca/t/spout-on-intel-uhd-graphics-card/811529)
- Before moving to Vulkan, Derivative expected Vulkan Video to give "GPU decoding/encoding of H264/H265 with a single API vs having to do it separately for Intel/AMD/Nvidia" — [TouchDesigner forum (2020)](https://forum.derivative.ca/t/what-does-the-adoption-of-vulcan-mean-for-the-future-of-touchdesigner/144033); [Experimental 2021.38110](https://derivative.ca/release/experimental-202138110/65595)
- WARP (NuGet) can run D3D12 video encode and decode through Media Foundation (H.264/H.265), which is useful for CI — [Microsoft.Direct3D.WARP 1.0.21](https://www.nuget.org/packages/Microsoft.Direct3D.WARP)
- PlayMap today decodes with D3D11VA on the renderer's device and copies once through ANGLE; Spout runs on its own D3D11 device — [docs/ARCHITECTURE.md](/home/user/mapper/docs/ARCHITECTURE.md)

### Inferences
- **D3D12 renderer:** FFmpeg's D3D12VA decode produces ID3D12Resource frames in the renderer's own API, so frames can be sampled with fence waits and no copy. The current D3D11VA path can be kept through shared NT handles and shared fences. Spout works through D3D11On12 or a D3D11 side device, which is how SpoutDX12 does it. NVENC and D3D12 Video encode take D3D12 resources and fences directly, which suits the record path, network send, and the GPU HAP encoder's outputs. This is the most uniform zero-copy story on Windows.
- **Vulkan renderer:** FFmpeg Vulkan decode yields VkImages, and Vulkan Video gives one API on NVIDIA and AMD. Intel's Windows Vulkan Video and the D3D11-texture import used for Spout are both weak spots. A Vulkan engine on Windows would still need a D3D11 device for Spout and as a fallback decode path.
- NDI and OMT frames arrive as CPU buffers (background, not re-verified), so the API choice affects only the upload path: GPU upload heaps or ReBAR on D3D12, host-visible device-local memory on Vulkan.
- HAP is BCn texture data, which every desktop D3D12 and Vulkan device samples natively (background), so HAP is API-neutral.

### Gaps
- AMD AMF's D3D12 support level (decode/encode surfaces) was not found in this pass.
- NVDEC's direct D3D12 output (versus CUDA external-memory interop) was not confirmed.
- I did not verify a 9.0 release or its release notes. PlayMap already references FFmpeg 9.0 / FFmpeg.AutoGen 9.0 in its tree; D3D12 AV1 encode appears in the post-8.0 changelog.
- No source compared the real-world latency of D3D12VA versus Vulkan Video decode on Windows.

## 6. Shader toolchain and keeping ISF / Shadertoy-style GLSL working

### Takeaway
The industry is converging on SPIR-V. DXC compiles HLSL to DXIL or SPIR-V, Microsoft has committed that Shader Model 7 will accept SPIR-V in D3D12 (a multi-year plan), and glslang can compile unmodified OpenGL-style GLSL to Vulkan SPIR-V with the "relaxed" mode (-R). On D3D12 today, user GLSL reaches DXIL either through Mesa's Microsoft-authored spirv_to_dxil (the route Godot chose) or through SPIRV-Cross to HLSL and then DXC. TouchDesigner's experience shows the practical risk: stricter Vulkan semantics break or crash previously tolerated GLSL.

### Cited Findings
- DXC 1.9.2602 (Feb 2026) adds production SM 6.9 and "significant SPIR-V backend updates" (layout/ABI correctness, debug info). It is also on NuGet as Microsoft.Direct3D.DXC — [DXC release](https://github.com/microsoft/DirectXShaderCompiler/releases/tag/v1.9.2602)
- "Once Shader Model 7 is released, DirectX 12 will accept shaders compiled to SPIR-V." The HLSL team is building HLSL support in Clang/LLVM and "translation tools to translate SPIR-V to DXIL and DXIL to SPIR-V". It is a multi-year process (announced Sep 19, 2024) — [DirectX blog](https://devblogs.microsoft.com/directx/directx-adopting-spir-v/)
- **Mesa spirv_to_dxil:** a Microsoft-copyrighted, MIT-licensed library that compiles a Vulkan-environment SPIR-V module to DXIL with a configurable maximum shader model and validator version — [Mesa source (Fossies)](https://fossies.org/linux/mesa/src/microsoft/spirv_to_dxil/spirv_to_dxil.c). It is still present in Mesa 26.2 — [Fossies doxygen](https://fossies.org/dox/mesa-26.2.0/spirv__to__dxil_8c.html). It was created for WebGPU-on-D3D12 work — [Phoronix](https://www.phoronix.com/news/Microsoft-SPIRV-DXIL-Mesa-Lib) — and is used by Dozen (Vulkan on D3D12) — [Phoronix](https://www.phoronix.com/news/Mesa-Dozen-VLK-D3D12)
- **Godot's D3D12 renderer** first tried SPIRV-Cross to HLSL, which needed DXIL reflection to recover bindings. It then switched to Mesa's NIR SPIR-V→DXIL path, using a callback to map set/binding to registers (register = set×100000000 + binding×100000) and patchable specialization constants. Godot called it "much more convenient" — [Godot, "Direct3D 12: Adventures in Shaderland" (Apr 2023)](https://godotengine.org/article/d3d12-adventures-in-shaderland/)
- **glslang -R (GL_EXT_vulkan_glsl_relaxed):** compiles "existing OpenGL GLSL and ESSL legal shaders without requiring any edits for Vulkan compliance". It re-adds default (loose) uniforms, which are grouped into gl_DefaultUniformBlock with a configurable set and binding, plus gl_VertexID/gl_InstanceID and atomic counters, and silently ignores shared/packed layouts. It applies to GLSL #version 140+ and ESSL 310+ — [Khronos GLSL extension spec](https://github.com/KhronosGroup/GLSL/blob/main/extensions/ext/GL_EXT_vulkan_glsl_relaxed.txt); "enabled by passing the -R option to glslang" — [glslang issue #1433](https://github.com/KhronosGroup/glslang/issues/1433)
- **TouchDesigner's Vulkan move and GLSL:** "TouchDesigner's main supported version of GLSL is 4.60. Support for versions of GLSL 3.30 and earlier have been removed due to the switch to Vulkan"; "With the changeover to Vulkan, it's much easier for incorrectly written GLSL to cause a full application crash"; image stores are range-checked because "Although GLSL states these functions are safe for out-of-bounds access, Vulkan does not" — [Derivative, Write a GLSL TOP](https://derivative.ca/UserGuide/Write_a_GLSL_TOP). Point sprites had to switch from gl_PointCoord to TDPointCoord() — [Experimental 2021.38110](https://derivative.ca/release/experimental-202138110/65595). A 2024 bug: reading from `out` variables did not work; a shader that ran on GL-era TD 2021 broke silently — [TouchDesigner forum (Feb 2024)](https://forum.derivative.ca/t/glsl-shader-not-working-on-vulkan-version-no-error-in-the-glsl-info-dat/435306)
- Diligent Engine uses HLSL as its universal language, accepts GLSL for GL and Vulkan, and states "There is currently no GLSL to HLSL converter" — [Diligent, using the API](https://diligentgraphics.com/diligent-engine/using-the-api/). Its Vulkan backend links glslang for run-time HLSL/GLSL→SPIR-V — [DiligentEngine README](https://github.com/DiligentGraphics/DiligentEngine/)
- NVRHI does not compile shaders at run time; the app supplies DXBC, DXIL or SPIR-V — [NVIDIA blog on NVRHI](https://developer.nvidia.com/blog/writing-portable-rendering-code-with-nvrhi/)
- The Vulkan SDK supports Slang (2025) — [Khronos](https://www.khronos.org/blog/vulkan-continuing-to-forge-ahead-siggraph-2025)
- .NET access to the toolchain: Silk.NET 2.x ships Shaderc, SPIRV.Cross and SPIRV.Reflect packages — [Silk.NET v3 docs page listing packages](https://dotnet.github.io/Silk.NET/docs/v3/). Silk.NET 3.0 is adding glslang, Shaderc, SPIRV-Cross/Tools/Reflect and VMA (draft PR, June 2026) — [Silk.NET PR #2590](https://github.com/dotnet/Silk.NET/pull/2590). Vortice ships Vortice.Dxc — [Vortice CHANGELOG](https://github.com/amerkoleci/Vortice.Windows/blob/main/CHANGELOG.md)
- PlayMap's ISF translator lives in Core and emits GLSL (with ES fixups). The engine's own programs are about 20 #version-tagged GLSL sources embedded in `ShaderLibrary.*.cs` (local tree: `src/PlayMap.Core/Effects/IsfTranslator.cs`, `src/PlayMap.Render/Shaders/`)

### Inferences
- The proposed ISF pipeline for either modern API: ISF JSON + GLSL → PlayMap's IsfTranslator (normalise to GLSL 4.50 with explicit in/out; ISF inputs become loose uniforms) → glslang `-R` with fixed set/binding for gl_DefaultUniformBlock and images → SPIR-V. Then either feed Vulkan directly, or for D3D12 run spirv_to_dxil (Mesa, MIT; native interop) or SPIRV-Cross→HLSL→DXC. The second D3D12 route is pure .NET-reachable today but needs binding reflection, which Godot found brittle. The front half is shared between D3D12 and Vulkan, and SM7's SPIR-V acceptance would eventually remove the last step on D3D12.
- Engine-owned shaders are best rewritten once in HLSL, compiled with DXC to DXIL (and to SPIR-V if a Vulkan backend is kept). That gives DXC PDBs, which RGD 1.5+ and PIX use for crash and debug source mapping.
- The compile lane must treat user shaders as untrusted. Under explicit APIs, undefined behaviour (out-of-bounds image writes, NaNs, infinite loops) produces TDRs and device loss rather than benign garbage, which matches TouchDesigner's experience. This argues for validating SPIR-V (spirv-val), robust buffer access, a per-shader GPU timeout guard, and device-lost recovery as part of the "attempts are not facts" discipline.

### Gaps
- How well spirv_to_dxil can be used from .NET (no NuGet package found) and how big it is as a dependency were not researched.
- I did not verify that ISF's common `#version 110/120`-style shaders survive normalisation to ≥140 for `-R` without semantic change; PlayMap's existing translator likely already does most of it.
- I found no public detail on how Resolume, Pixera or Smode compile user GLSL/ISF on non-GL backends.

## 7. .NET bindings and rendering-abstraction layers (RHIs)

### Takeaway
For D3D12 in .NET 10, two maintained, current binding sets exist. Vortice.Windows is idiomatic, at 3.8.3, targets net9/net10 and has a D3D12MemoryAllocator wrapper. TerraFX.Interop.Windows is raw, close to the headers, and tracks Agility 1.619.2. Silk.NET 2.x still covers Vulkan and D3D12 but is volunteer-maintained "ad-hoc" while 3.0 is rebuilt. A WebGPU layer (Dawn/wgpu) would hide the native device that NVIDIA's present barrier, NvAPI and D3D12 video need.

The 3.0 Vulkan bindings were merged Nov 24, 2025 — [PR #2457](https://github.com/dotnet/Silk.NET/pull/2457). The 3.0 Win32/DirectX bindings PR opened Jan 3, 2026 — [Silk.NET pulls](https://github.com/dotnet/Silk.NET/pulls)
- **Veldrid:** "As of February 2023, I'm no longer able to publicly share updates to Veldrid" — [Veldrid README](https://github.com/veldrid/veldrid)
- **Stride (vvvv gamma's engine):** Direct3D 11 is the default on Windows; "Stride's implementation for [Direct3D 12] isn't as stable as the one for 11"; Vulkan is the default elsewhere — [Stride manual](https://doc.stride3d.net/latest/en/manual/graphics/graphics-api.html). The community VL.Stride.DX12Bridge (built on Silk.NET D3D12 2.22) bridges D3D11 and D3D12 for mesh shaders, ray tracing, async compute and DLSS — [NuGet](https://www.nuget.org/packages/VL.Stride.DX12Bridge/)
- **NVRHI:** a C++ abstraction over D3D11, D3D12 and Vulkan (1.2) with reference-counted lifetimes, automatic or optional manual barriers, bindless layouts, ray tracing, and native-handle escape hatches (ID3D12Resource, vk::Image) — [NVIDIA blog](https://developer.nvidia.com/blog/writing-portable-rendering-code-with-nvrhi/); [programming guide](https://github.com/NVIDIA-RTX/NVRHI/blob/main/doc/ProgrammingGuide.md)
- **Diligent Engine:** backends for Direct3D 11, Direct3D 12, OpenGL/GLES, Vulkan and WebGPU (Metal commercial), with interop to attach to existing native devices — [DiligentCore](https://github.com/DiligentGraphics/DiligentCore); [DiligentEngine](https://github.com/DiligentGraphics/DiligentEngine/)
- **WebGPU:** Dawn implements webgpu.h on D3D12, Metal, Vulkan and OpenGL, with the Tint WGSL compiler — [dawn-prebuilt README](https://github.com/eliemichel/dawn-prebuilt); [Chrome WebGPU ecosystem](https://developer.chrome.com/docs/web-platform/webgpu/webgpu-ecosystem). wgpu has a `texture_from_d3d11_shared_handle` path on its Vulkan backend (fixed for AMD and NVIDIA, June 2025) — [wgpu commit](https://github.com/gfx-rs/wgpu/commit/65337894f609b536d0016fbabfea6324c5b98faf)
- NVIDIA's present barrier client is created from the D3D12 device and the DXGI swapchain and registers the swapchain's buffers and a fence — [NVIDIA blog](https://developer.nvidia.com/blog/synchronizing-present-calls-between-applications-on-distributed-systems-with-directx-12/)

### Inferences
- **Recommended .NET stack for D3D12:** Vortice.Direct3D12/DXGI/Dxc (plus Vortice.D3D12MemoryAllocator) for productivity, or TerraFX for raw zero-allocation interop under the analyzers' "dispose what you own" rule. Both track the 1.618/1.619 Agility SDK within months. Silk.NET is acceptable for Vulkan, but its 2.x line is in volunteer maintenance and 3.0 is unfinished as of mid-2026.
- **RHI choice:** an in-house thin RHI in C# is better than adopting a C++ RHI. It would sit at PlayMap's existing seams (GlDevice wrapper, render graph, IOutputPresenter), with D3D12 as the reference backend and GL 3.3 as the transitional backend. NVRHI's design (lifetime tracking, auto barriers, explicit queues, native escape) is a good template. A WebGPU layer would cost vendor extensions, NVAPI present barrier, D3D12 Video and NVENC fence interop, Spout/D3D11 interop, multi-queue control, timeline-fence sharing with decode and encode engines, and HDR/flip-model control (inference from the native-device requirements above).

### Gaps
- No benchmark of interop overhead was found for Vortice versus TerraFX versus Silk.NET.
- I did not confirm Vortice.Vulkan's (separate repo) current status.
- No .NET packaging of NvAPI's present barrier was found; it would likely need a P/Invoke layer over nvapi64.dll.

## 8. What comparable products use, and why

### Takeaway
There is no single industry answer, but every product that rewrote its renderer since 2021 left OpenGL. Cross-platform products went to Vulkan (TouchDesigner, via MoltenVK on macOS). Windows-only Watchout 7 also chose Vulkan 1.3. Windows-focused products that care most about outputs and genlock went to D3D12 (Smode 10.2) or stayed in the DirectX family (Notch, Ventuz, Unity's default, Unreal nDisplay's DX11/DX12). Resolume and older Pixera material are still OpenGL-centred.

### Cited Findings
- **TouchDesigner:** "The openGL engine used for the last 20 years is gone and TouchDesigner's graphics API is now Vulkan" (2022 Official, May 25, 2022). Reasons given: lower driver overhead, better SDI I/O performance, NotchLC on macOS, and "Vulkan's better support of HDR color space outputs" — [Derivative 2022 Official Update](https://derivative.ca/community-post/2022-official-update/66222). Also future-proofing and Metal via MoltenVK on macOS, with geometry shaders gone on macOS — [Derivative Vulkan page](https://derivative.ca/UserGuide/Vulkan). "TOP CPU cook times are often about 50% less on the Vulkan version", while GPU shader time is the same — [TouchDesigner forum (2020)](https://forum.derivative.ca/t/what-does-the-adoption-of-vulcan-mean-for-the-future-of-touchdesigner/144033)
- **Watchout 7 (Dataton, Windows-only):** "WATCHOUT 7 uses Vulkan for its rendering engine to achieve lower overhead and efficient GPU resource management" — [Installing Watchout](https://docs.dataton.com/watchout-7-new/watchout/getting-started/installing-watchout.html). The display GPU must support Vulkan 1.3, with Windows 10 or later — [hardware recommendations](https://docs.dataton.com/watchout-7/appendices/hardware_recommendations.html). It recommends NVIDIA RTX PRO with a Sync board for framelock — [system requirements](https://docs.dataton.com/guide/watchout/getting-started/system-requirements.html)
- **Smode:** DX12 has been the default for outputs and genlock/multi-server sync since 10.2 (Dec 10, 2024), with OpenGL still selectable as the "Presenting API" — [Smode 10.2](https://doc.smode.io/changelog/Smode102/); [GPU settings](https://doc.smode.io/reference/preferences/engine/other/gpu-settings/). A later fix: "DirectX12 Window resize swapchain crash" (R13) — [Smode R13 revision](https://doc.smode.io/changelog/R13/revision/)
- **Notch:** "a proprietary DirectX-based rasterisation render engine" (2019). Its ray tracing was then built on DirectX 11 because media servers lacked DX12 — [CG Channel](https://www.cgchannel.com/2019/02/sneak-peek-real-time-ray-tracing-in-notch-builder/). Notch 2026.1 (Feb 3, 2026) ships the NURA ray-traced and path-traced renderers — [Notch manual 2026.1](https://manual.notch.one/2026.1/en/docs/whats-new/everything/). It requires Windows 10+ x64 and a discrete GPU — [Notch get started](https://www.notch.one/get-started)
- **Ventuz:** "Ventuz Designer, Director, and Runtime are based on DirectX and Microsoft .Net and are therefore compatible with Microsoft Windows systems only", with a Direct3D 11.1+ GPU required — [Ventuz system requirements](https://www.ventuz.com/resources/system-requirements/)
- **Unity:** "As of Unity 6.1, DirectX 12 is now set as the default graphics API for new projects" on Windows (Apr 2025) — [Unity blog](https://unity.com/blog/directx-12-improvements-in-unity-6); [Unity 6.1 manual](https://docs.unity3d.com/6000.3/Documentation/Manual/WhatsNewUnity61.html)
- **Unreal nDisplay:** supports DX11 and DX12, and NVIDIA framelock uses NVIDIA swap groups/barriers — [nDisplay whitepaper](https://cdn2.unrealengine.com/Unreal+Engine%2Fndisplay-whitepaper-final-updates%2FnDisplay_Whitepaper_FINAL-f87f7ae569861e42d965e4bffd1ee412ab49b238.pdf); [UE docs](https://docs.unrealengine.com/4.27/en-US/WorkingWithMedia/IntegratingMedia/nDisplay/Synchronization/)
- **vvvv gamma:** Stride with D3D11 by default, plus a community D3D12 bridge — [Stride manual](https://doc.stride3d.net/latest/en/manual/graphics/graphics-api.html); [VL.Stride.DX12Bridge](https://www.nuget.org/packages/VL.Stride.DX12Bridge/)
- **Resolume Arena:** FFGL plugins are C++/OpenGL; the SDK master moved to OpenGL 4.6 via glew — [resolume/ffgl](https://github.com/resolume/ffgl). Resolume's support pages refer to "our OpenGL rendering" — [Resolume, Lots of Outputs](https://resolume.com/support/en/lots-of-outputs). This conflicts with Spout's author, who says Resolume developers "integrated Spout into their Vulkan code" — [Spout2 #69](https://github.com/leadedge/Spout2/issues/69)
- **Pixera:** an older training handout lists "Nvidia Quadro graphics card with sync board, OpenGL 4.5" (undated, likely 2019–2021) — [Pixera Online Training Module 1](https://pixera.one/fileadmin/user_upload/downloads/en/pixera_online-training/Pixera_Online_Training_-_Module_1_Handout.pdf). The Dec 2025 brochure mentions importing "GLSL shaders" and Unreal integration — [Pixera brochure 2025-12](https://pixera.one/fileadmin/user_upload/downloads/en/pixera_brochures/Software%26Hardware%20Overview%20Brochure/2025-12%20Software%26Hardware%20Brochure_WEB.pdf)

### Inferences
- The products that rewrote most recently for multi-output show reliability (Smode's output/sync layer, Watchout 7) chose D3D12 and Vulkan respectively. Both work on Windows. The split is less about capability than about team history and portability: Watchout ships only on Windows but chose Vulkan; TouchDesigner needed macOS.
- Products that host other engines (disguise, Pixera and Smode hosting Notch/Unreal/TouchDesigner) must interoperate with DirectX textures (Notch is DirectX-based and Spout is D3D11). That favours a DirectX-family host or at least robust D3D11 interop.

### Gaps
- The graphics API of disguise designer (r-series), Green Hippo Hippotizer and Millumin (Windows) was not found in primary sources.
- Notch 1.0/2026's current API (DX12 vs DX11) was not confirmed by a primary source; the GPU requirements (Turing+ for v1.1) suggest DX12/DXR but this is unverified.
- Resolume's current Windows renderer (pure GL vs a newer Vulkan or D3D path) is contradictory in the sources above.
- Unreal Engine 5's default RHI on Windows (DX12) and its Vulkan status were not re-sourced in this pass.

## 9. Effort and risk of moving PlayMap's GL 3.3 renderer, and how to keep GL during migration

### Takeaway
Moving to an explicit API is a multi-quarter rewrite of the GPU layer, not a port. TouchDesigner took about 18–24 months from announcement to official release and broke plugin and shader compatibility. Stride's D3D12 backend is still "less stable" years in. PlayMap is relatively well placed: GL calls are concentrated in about 10 files behind a `GlDevice` wrapper used by about 40 files, with an existing render graph and an `IOutputPresenter` seam. The low-risk path is an RHI at that seam, with GL 3.3 kept as a backend until the D3D12 backend passes the same pixel and timing tests.

### Cited Findings
- **TouchDesigner timeline and costs:** in 2020, Derivative was "aiming for the 2020.60000 series" — [forum](https://forum.derivative.ca/t/what-does-the-adoption-of-vulcan-mean-for-the-future-of-touchdesigner/144033). Experimental Vulkan build Dec 17, 2021 — [Experimental 2021.38110](https://derivative.ca/release/experimental-202138110/65595). Official release May 25, 2022 — [2022 Official](https://derivative.ca/community-post/2022-official-update/66222). Breakages: the Custom TOP API had to be reworked, the SVG TOP was removed ("the OpenGL feature it was based on does not exist in Vulkan"), and point-sprite shaders changed — [Experimental 2021.38110](https://derivative.ca/release/experimental-202138110/65595). Derivative also wrote that "With OpenGL the driver handles it. With Vulkan I need to. It's likely that kind of situation will be worse in Vulkan, at least to start" — [forum](https://forum.derivative.ca/t/what-does-the-adoption-of-vulcan-mean-for-the-future-of-touchdesigner/144033)
- Stride's D3D12 backend is still "not as stable" as D3D11 and not the default — [Stride manual](https://doc.stride3d.net/latest/en/manual/graphics/graphics-api.html)
- Smode staged its migration: DX12 became the default presenting API with OpenGL still selectable, and swapchain crash fixes followed in later releases — [Smode GPU settings](https://doc.smode.io/reference/preferences/engine/other/gpu-settings/); [R13 revision](https://doc.smode.io/changelog/R13/revision/)
- D3D11On12 "enables incremental porting of an application from D3D11 to D3D12, by enabling portions of the app to continue targeting D3D11" — [Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3d12/direct3d-11-on-12)
- Godot's D3D12 backend needed custom shader translation work (patches to Mesa, a binding scheme, specialization-constant patching) — [Godot](https://godotengine.org/article/d3d12-adventures-in-shaderland/)
- NVRHI shows a viable shape for keeping several backends behind one API: binding layouts become root signatures or descriptor set layouts, command lists aggregate native lists, and barriers are automatic with an opt-out — [NVRHI guide](https://github.com/NVIDIA-RTX/NVRHI/blob/main/doc/ProgrammingGuide.md)
- **PlayMap's tree (local measurement, Oct 16, 2026):** `src/PlayMap.Render` has 89 C# files and about 21,160 lines. Direct GL API usage is in about 10 files. `GlDevice` (split into Content/Decode/Fx/Resources/VideoIo partials) is referenced by about 40 files. There are about 20 GLSL `#version` sources across `ShaderLibrary.*.cs`, `GlDialect.cs` and the ISF translator. A render graph, `IOutputPresenter`, `GpuPlatform` and `RenderContext` already exist — local repo and [docs/ARCHITECTURE.md](/home/user/mapper/docs/ARCHITECTURE.md)

### Inferences
- **Migration plan shape (risk-ordered):**
  1. Extract an RHI interface from `GlDevice` (resources, pipelines, binding sets, command lists, queues, fences, presenters, importers) and keep the GL 3.3 backend as the reference implementation.
  2. Add a D3D12 backend for offscreen passes first (content, FX, projection, warp, blend), validated by the existing pixel tests running on WARP in CI.
  3. Move presentation to D3D12 DXGI flip-model presenters, which replaces ANGLE, then add the composition swapchain or NVIDIA present barrier as framelock tiers.
  4. Move the decode importers to D3D12VA and shared NT handles, and Spout to a D3D11 side device with shared fences.
  5. Move the ISF chain to the SPIR-V/DXIL route.
  6. Retire GL only after parity on the existing STATE-observed timing and pixel tests ("attempts are not facts").
- **Biggest risk items:** explicit synchronization and resource lifetimes (fences per frame-in-flight, upload-arena lifetime), descriptor management, device-lost recovery during a show, user-shader robustness, and HDR/colour-space correctness on outputs. GL's driver did most of this implicitly.
- Keeping ANGLE/D3D11 as a "second" path does not add capability once D3D12 exists. A temporary GL backend is cheaper to keep than a permanent D3D11 one.

### Gaps
- No public effort figures (person-months) were found for TouchDesigner's, Smode's or Watchout's migrations.
- PlayMap-specific estimation needs a code-level audit of GlDevice's API surface and of how many passes rely on GL-only behaviours (implicit sync, glReadPixels PBO rings, sRGB defaults); this pass did not do that audit.

## 10. Synthesis: primary API and whether a second one is worth keeping

### Takeaway
For a Windows-only, NVIDIA-first, latency- and reliability-driven media server in 2026, **Direct3D 12 (Agility SDK 1.619+, SM 6.9, HLSL/DXC)** is the strongest primary API. **OpenGL 3.3** should be kept only as a transitional backend behind an RHI. **Vulkan** is not worth carrying as a second production backend on Windows unless a specific Vulkan-only capability (VK_EXT_present_timing, or one cross-vendor Vulkan Video path) becomes decisive or Linux render nodes return as a goal. In that case, sharing the SPIR-V shader front end keeps the option open.

### Cited Findings
- D3D12 strengths with sources above: the Agility SDK cadence and day-one vendor drivers ([DirectX blog](https://devblogs.microsoft.com/directx/shader-model-6-9-retail-and-more/)); flip model, independent flip, waitable swapchains and HDR ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/for-best-performance--use-dxgi-flip-model)); composition-swapchain target-time presents ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/comp_swapchain/comp-swapchain)); NVIDIA present barrier ([NVIDIA](https://developer.nvidia.com/blog/synchronizing-present-calls-between-applications-on-distributed-systems-with-directx-12/)); D3D12 Video with AV1 encode on 24H2 ([Microsoft Learn](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/video-encoding-d3d12)); NVENC D3D12 ([NVIDIA](https://developer.nvidia.com/blog/encoding-for-directx-12-with-video-codec-sdk-11-1/)); WARP at FL 12_2 for CI ([NuGet](https://www.nuget.org/packages/Microsoft.Direct3D.WARP)); PIX, RGD and Aftermath ([RGD](https://gpuopen.com/radeon-gpu-detective/), [Aftermath](https://developer.nvidia.com/nsight-aftermath/getting-started)); maintained .NET bindings ([Vortice](https://github.com/amerkoleci/Vortice.Windows/blob/main/CHANGELOG.md), [TerraFX](https://github.com/terrafx/terrafx.interop.windows)); Smode's move of outputs and genlock to DX12 ([Smode](https://doc.smode.io/changelog/Smode102/)); and the future SPIR-V intake in SM7 ([DirectX blog](https://devblogs.microsoft.com/directx/directx-adopting-spir-v/))
- Vulkan strengths with sources: present_timing ([Khronos](https://www.khronos.org/blog/vk-ext-present-timing-the-journey-to-state-of-the-art-frame-pacing-in-vulkan)); the descriptor heap and Roadmap 2026 ([Khronos](https://www.khronos.org/blog/vulkan-introduces-roadmap-2026-and-new-descriptor-heap-extension)); Vulkan Video and FFmpeg's Vulkan compute codecs ([FFmpeg 8.0](https://ffmpeg.org/pipermail/ffmpeg-devel/2025-August/347886.html)); native GLSL via glslang `-R` ([Khronos GLSL](https://github.com/KhronosGroup/GLSL/blob/main/extensions/ext/GL_EXT_vulkan_glsl_relaxed.txt)); Watchout 7 and TouchDesigner as precedents ([Dataton](https://docs.dataton.com/watchout-7-new/watchout/getting-started/installing-watchout.html), [Derivative](https://derivative.ca/community-post/2022-official-update/66222))
- Vulkan risks on Windows with sources: NVIDIA's present path depends on a driver setting ([NVAPI](https://docs.nvidia.com/nvapi/NvApiDriverSettings_8h.html), [DXVK #5171](https://github.com/doitsujin/dxvk/issues/5171)); D3D11 texture import for Spout is optional and fails on some GPUs ([TD forum](https://forum.derivative.ca/t/spout-on-intel-uhd-graphics-card/811529)); Intel's Windows Vulkan Video conformance is weak ([Igalia deck](https://www.vulkan.org/user/pages/09.events/vulkanised-2025/T31-Stephane-Cerveau-Igalia.pdf)); no PIX ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/direct3dtools/pix/articles/general/pix-overview)); AMD Windows Vulkan regressions are reported ([DXVK #5332](https://github.com/doitsujin/dxvk/issues/5332))
- OpenGL risks with sources: Intel's "low priority" stance and OpenGL at half of DX12/Vulkan performance ([IGCIT #402](https://github.com/IGCIT/Intel-GPU-Community-Issue-Tracker-IGCIT/issues/402), [#1148](https://github.com/IGCIT/Intel-GPU-Community-Issue-Tracker-IGCIT/issues/1148)); AMD's 2022 rewrite regressions ([Geeks3D](https://geeks3d.com/20220804/amd-radeon-adrenalin-22-7-1-opengl-changes-tested/)); no RGP, RGD or Aftermath support ([RGP](https://github.com/GPUOpen-Tools/radeon_gpu_profiler/blob/master/docs/source/index.rst)); flip-model presentation needs ANGLE or NVIDIA driver layering ([MonoGame #8629](https://github.com/MonoGame/MonoGame/issues/8629))

### Inferences
- **Decision matrix (Windows-only).** Columns are D3D12 / Vulkan / OpenGL 4.6:
  - **Vendor investment:** D3D12 highest (Agility + IHV day-one) / high / maintenance only.
  - **Presentation and latency control:** D3D12 best (DXGI iflip, composition target time, present barrier) / good but vendor-WSI-dependent, present_timing new / poor.
  - **Video zero-copy:** D3D12 best (D3D11VA/D3D12VA/NVENC/Spout all DX) / good on NVIDIA and AMD, weak on Intel, Spout import optional / via WGL_NV_DX_interop and ANGLE copies.
  - **Tools and CI:** D3D12 best (PIX, WARP) / good / weak.
  - **User GLSL/ISF:** D3D12 needs a SPIR-V→DXIL step / native SPIR-V / native.
  - **.NET bindings:** D3D12 Vortice/TerraFX current / Silk.NET 2.x volunteer, 3.0 pending / Silk.NET.
  - **Portability:** Windows-only (not a goal) / cross-platform / cross-platform.
- **Second API:** the only good reason to keep Vulkan is optionality: Linux nodes, macOS through MoltenVK, or Vulkan-only timing and video features. That cost can be cut to near zero now by making SPIR-V the shader interchange (glslang `-R` for ISF, DXC `-spirv` for engine HLSL) and keeping the RHI free of D3D12-only concepts where cheap. GL 3.3 should survive only as the migration and reference backend and as a "safe mode" during the transition. ANGLE/D3D11 should be retired once D3D12 presenters land.
- **Baseline platform:** Windows 11 24H2+ (GPU upload heaps, AV1 D3D12 encode, WDDM 3.x iflip for the composition swapchain), NVIDIA RTX/RTX PRO with driver branch pinning, AMD RDNA 3/4 validated per release, and Intel Arc B as best effort.

### Gaps
- I found no head-to-head latency measurement (D3D12 vs Vulkan vs GL) on identical Windows show hardware. PlayMap would have to measure this with its own present ledger before committing (in line with "measured, then governed").
- NVIDIA's VK_NV_present_barrier details and Windows driver status were not separately sourced beyond the NVIDIA forum statement.
