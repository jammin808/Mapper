# Design: `wp3-d3d12-core` — the Direct3D 12 device behind the RHI

*How `PlayMap.Render.D3D12` will implement `rhi.md`'s contracts: the device and the order it is made in, queues and fences,
memory, descriptors, the root signature, pipelines, state tracking, the diagnostics armed before anything can fail, and WARP in
CI. Package section: `PLAN.md` §3.7. Presenters are `present.md`'s; the plans that replace automatic barriers are `graph.md`'s.*

**The decision in one paragraph.** One device per node, on the adapter that drives the outputs, made through the Agility SDK's
device factory with DRED (and Aftermath on NVIDIA) armed first; an output whose display hangs off another adapter is presented
composed and said so (§2, this round's rule). A direct queue at high priority and a copy queue, each with a
timeline fence; frame resources for frames in flight plus one. Every product program shares one root signature: its constants in
a root CBV from the frame's ring, its textures and samplers as indices into directly indexed heaps (Shader Model 6.6), so a draw
copies no descriptor. Resources are tracked per subresource and transitioned automatically until a render plan takes them over.
Pipelines come from embedded DXIL through a pipeline library keyed by adapter, driver and build. Every release waits for the
fence value of the resource's last use. The device also implements the contracts the later packages build on, so none of them
adds a primitive to a folder it does not own: the render graph's transient memory, aliasing barriers, discards and the
plan-managed opt-out of state tracking (§6, §7), and the exporter — shared committed textures, shared fences and their NT handles
(§6) — that the Spout bridge (wp3-video) and the shared previews (wp3-desk-gpu) both use.

## 1. The floor and the features recorded

| Requirement | Why | Hardware that has it |
|---|---|---|
| Feature level 12_1 | the level every GPU that has the two rows below reaches; nothing of 12_2 is required | NVIDIA Turing+, AMD RDNA 2+, Intel Arc, WARP |
| Shader Model 6.6 | directly indexed descriptor heaps (`ResourceDescriptorHeap`, `SamplerDescriptorHeap`) for bindless textures and samplers | the same |
| Resource binding tier 3 | unbounded descriptor tables | the same |

A device below the floor is refused with words naming what it lacks, and the node runs GL (the fuse, `present.md` §2). Recorded,
not required, and each feature's use probed before it is taken: enhanced barriers, GPU upload heaps (build 26080 and ReBAR), the
maximum shader model, wave intrinsics, 16-bit types, the video decode profiles (wp3-video), the copy queue's timestamp support.

## 2. Start-up, stage by stage

Each stage has a word, as the D3D11 path's `DxgiStartStage` has, so a refusal names where it stopped:

| # | Stage (`D3D12StartStage`) | What it does | On failure |
|---|---|---|---|
| 1 | `runtime` | `D3D12GetInterface(CLSID_D3D12SDKConfiguration)` → `ID3D12SDKConfiguration1::CreateDeviceFactory(sdkVersion, ".\\D3D12\\")` (M7) | the OS runtime, with words in `render.agility` |
| 2 | `diagnostics` | DRED settings (`ID3D12DeviceRemovedExtendedDataSettings1`: auto-breadcrumbs, page-fault reporting, breadcrumb context) on; Aftermath's crash dumps enabled where its library is found (§9; NVIDIA requires it before any device); in tests the debug layer and GPU-based validation | runs without the missing tool, said |
| 3 | `adapter` | `CreateDXGIFactory2`; the adapter by LUID — the one driving the most outputs' displays (`EnumAdapterByLuid`), WARP when asked (`EnumWarpAdapter`) | GL with words |
| 4 | `device` | the device from the factory at feature level 12_1; the floor checked (§1) | GL with words |
| 5 | `queues` | a direct queue at `HIGH` priority (`GLOBAL_REALTIME` only when `MACHINE SET GPU-PRIORITY REALTIME` asks and the privilege is held; creation then fails rather than downgrades, and the refusal is said); a copy queue; a timeline fence each | GL with words |
| 6 | `heaps` | the shader-visible CBV/SRV/UAV heap, the sampler heap (four static samplers), RTV and DSV heaps; the memory allocator | GL with words |
| 7 | `pipelines` | the root signature; the pipeline library opened from the cache (a mismatched driver discards it, with words) | an empty library |
| 8 | `rings` | upload, readback and constant rings per frame in flight | GL with words |

The rebuild path of wp3-stability-2 runs stages 3–8 again on a new epoch.

**Outputs on a second adapter (this round's rule).** One device per node. An output whose display is driven by another adapter is
still presented — DXGI copies its buffer across adapters, so it is composed, never Independent Flip — and STATE and preflight say
it in amber ("op_5 is on the second GPU: presented composed, a copy across adapters every frame"); `SYNC APPLY` refuses it from a
lock group, naming the adapter (wp3-framelock's precondition). A device per adapter is next round's. wp3-present's
`AdapterRuleTests` hold it with a fake display list of two adapters.

## 3. Queues, frames and fences

- **Per submission, not per frame.** One frame number opens several direct lists in turn — the frame's own, one for each preview
  drawn after it, a resolve or an upload asked between frames (numbered 0) — and the number is a label (`IGpuDevice.BeginFrame`).
  So a list takes its resources (a command allocator, constant-ring and upload-ring pages, its deferred-release entries) from pools
  fenced per submission: each is back once the value that list's `Submit` returned has completed. The pools are sized for the
  frames in flight (`framesInFlight + 1`, at most 3) times the lists a frame opens — its own, its previews and its side lists — and
  a pool with none back makes one more, counted, rather than hold the render thread; the check is `IsComplete`, never a wait. Never
  one slot per displayed frame: keyed by frame number, a ring resets an allocator a preview's list may still be running; keyed by
  count, it has no slot free by a frame's fourth preview.
- **Timelines.** One `ID3D12Fence` per queue; `FenceValue(queue, n)` is a point on it. The direct queue's list `Wait`s on the copy
  queue's values for the uploads it reads.
- **Copy queue.** Uploads (HAP blocks, CPU-decoded planes, live inputs) and readbacks (sends, LED, previews' ring path) are copy
  work recorded on lanes, submitted with their values. AMD's guidance — copy several frames early, double-buffered — is the
  arena's design (wp3-video).

## 4. The root signature and the binding block

One root signature for every product program:

| Parameter | Register | Holds |
|---|---|---|
| Root CBV | `b0` | the program's constant block (its `ProgramLayout`), written into the frame's constant ring by the `DrawBuilder` |
| 32 root constants | `b1` | the binding block: 16 texture descriptor indices and 16 sampler indices, one per layout slot |
| — | flags | `CBV_SRV_UAV_HEAP_DIRECTLY_INDEXED`, `SAMPLER_HEAP_DIRECTLY_INDEXED` |

A draw writes its constants, writes the binding block with `SetGraphicsRoot32BitConstants`, and draws: no descriptor is copied
per draw. HLSL reads a slot's texture and sampler through two macros over `b1` (`shaders.md` §2). The sampler heap holds the four
filter × wrap combinations; a texture's own filter and wrap pick its slot's sampler index, as GL's texture state does today.

## 5. Descriptors

- **Shader-visible heap.** One CBV/SRV/UAV heap (a million descriptors). A texture's SRV is written once at creation into a slot
  from a free list; its index rides in the binding block. A slot returns to the free list only after the fence value of the
  texture's last use completes — the rule DRED's documentation says matters most ("premature release of objects in flight is
  one of the top causes" of removal).
- **CPU heaps.** RTVs and DSVs from free lists, released the same way.
- **Samplers.** Four static entries, never changed.

## 6. Memory

| What | Where |
|---|---|
| Render targets, textures | placed in pooled heaps by the D3D12 Memory Allocator (TerraFX's port; PlayMap's own pools if the port lags), `ResourcePool` reusing by size, format and attachments as today |
| Constants | a per-frame linear ring in an upload heap (256-byte aligned), sized at warm-up; a frame that would exceed it takes one more page from a pre-made list and counts it (`render.memory.constantSpills`) |
| Uploads | a per-frame ring in an upload heap, or a GPU upload heap where ReBAR and the build allow (probed, recorded) |
| Readbacks | a ring in a readback heap, copied on the copy queue |
| Transients | `ITransientMemory`: one heap per plan's memory block; `Place` makes a placed resource at the plan's offset; an aliasing barrier (`Alias`) before a texture takes over memory another used this frame, `DiscardResource` (`Discard`) on its first use |
| Shared textures | committed with `D3D12_HEAP_FLAG_SHARED` (previews, Spout's bridge), created by the exporter (`Share/`): `ITextureExporter.Export` gives the NT handle (`CreateSharedHandle`), `ExportFence` a fence made with `D3D12_FENCE_FLAG_SHARED` and its handle; the handles' duplication into another process is wp3-desk-gpu's |

Nothing on this list allocates managed memory after warm-up; the rings are unmanaged and sized once.

## 7. State tracking and barriers

Until a render plan takes a resource over (`graph.md`), the command list tracks each subresource's last state and inserts the
transition the next use needs, batched at the next `BeginPass`, `Draw`, `Copy` or present: `PIXEL_SHADER_RESOURCE` to sample,
`RENDER_TARGET` to draw, `COPY_SOURCE`/`COPY_DEST` to copy, `PRESENT` for a back buffer. The legacy barrier API is used everywhere;
enhanced barriers are recorded as a feature and adopted when every supported tier has them. A resource a plan manages (`SetPlanManaged`) carries a
flag that turns tracking off for it, and the plan's own barriers take over; the debug layer checks both. This package builds the
flag, the aliasing barrier and the discard with their tests; wp3-d3d12-passes only calls them.

## 8. Pipelines

- **From key to pipeline.** A `PipelineKey` gives the program's vertex and pixel DXIL (embedded by wp3-shaders), the blend, depth,
  rasteriser state and topology, and the target formats; the program table gives the input layout (`ProgramLayout.Inputs`: each
  attribute's location, float count, offset, stride, buffer and divisor — semantic `ATTR`n for location n, a `R32…_FLOAT` format of
  its float count, input slot 0 per vertex or slot 1 with `D3D12_INPUT_CLASSIFICATION_PER_INSTANCE_DATA` and the divisor as its
  step rate). A key alone so makes its pipeline before any mesh is at hand, as `TryGet` and `WarmAsync` need: they take keys, and a
  key carries no mesh. A program with no inputs makes its geometry from `SV_VertexID` and takes an empty layout; `ProgramLayoutTests`
  hold every mesh a pass draws to its program's inputs.
- **The library.** An `ID3D12PipelineLibrary1` stored at `%LOCALAPPDATA%\PlayMap\cache\pso\<key>.bin`, where the key is the
  adapter's LUID, its driver version, the build (`BuildInfo.Informational`) and the hash of the embedded shaders. A driver update
  makes the library mismatch: it is discarded with words and warmed again.
- **The interim.** Until wp3-d3d12-passes-2 makes every key before the show, a `TryGet` miss in `Draw` makes the pipeline there and
  counts it (`render.pipelines.renderThreadMakes`); preflight is amber while the count since the last arm is not zero.

## 9. Diagnostics

| Tool | Armed | Read |
|---|---|---|
| DRED | before the device, always | on removal (`stability.md` §7): auto-breadcrumbs (the last pass the GPU completed, the first outstanding), page-fault address and recently freed allocations |
| Breadcrumb context | every pass's `Marker` | names the pass in DRED's report and in PIX |
| Aftermath (NVIDIA) | before the device, when `GFSDK_Aftermath_Lib.x64.dll` is found where the user put it (below) | its dump, beside the WER dump with the same manifest |
| Radeon GPU Detective (AMD) | by the driver, with the tool | maps a crash to source through the DXC PDBs |
| PDBs | built with the DXIL, kept in the CI's symbols artifact, never in the MSI | PIX and RGD by shader hash |
| The debug layer and GPU-based validation | tests only (and `GPU DEBUG` next round) | the info queue's callback collects every message; a test fails on any warning or above it does not name |

**Aftermath's library is never shipped** (`PLAN.md` §9 decision 7: "Load from wherever"). The engine looks, before the device, in
the node's `gpu.aftermathPath` (`NodeSettings.Gpu`; a file or a folder), `PLAYMAP_AFTERMATH_DIR`, then the exe's folder (only
because the user put it there). Each is an absolute path, loaded by that full path; a relative value is refused with the words, and
the system's loader is never asked by bare name, since on Windows its search takes in the current directory and `PATH`. No line names the path: a library path on the wire would let any client load code into the engine.
`render.aftermath` says where the library was found and its version, or "not found" with the words, and a node without it keeps
DRED's evidence alone (`AftermathFindTests`; `LicenceTests` find no `GFSDK_Aftermath_Lib*` in the MSI).

## 10. CI on WARP

The Windows job (`windows-2025`, pinned) restores `Microsoft.Direct3D.WARP` (WARP at feature level 12_2 with Shader Model 6.9) and
the Agility SDK (`Microsoft.Direct3D.D3D12`, its debug layer included) beside every test host. `BackendFixture`'s Direct3D 12 leg
makes a WARP device with the debug layer and GPU-based validation, registers the info-queue callback, and runs every pixel scene;
each test reads back through `ReadNow` and compares with the same goldens as GL. WARP's binaries never leave CI.

**The tolerance table.** WARP is not llvmpipe: its filtering, blending and float rounding differ, and many GL tolerances are ±0 or
±1 because they were tuned on llvmpipe. `PixelParityTests` therefore read their own per-scene table
(`tests/PlayMap.Render.Tests/Parity/D3D12Tolerances.cs`): a scene's D3D12 tolerance starts at its GL one, and a widening is a row
with the measured maximum and mean difference, the pixels' share over the GL tolerance and the reason, reviewed at the merge gate
(§5.4 of the plan). Byte-exact holds only for the programs that only `Load` integers (`video.pack`, `video.unpack`). The table is
filled from the first WARP run of the suite, never guessed.

**Seeing a failure from Linux.** The job's `workflow_dispatch` input (the spine's) runs one filtered Direct3D 12 leg and uploads
its diff images, the info-queue log and DRED's output as artifacts, with the leg's minutes in the summary.

## 14. Risks

- **WARP is not a GPU** (`PLAN.md` R4): it validates correctness and API use, not timing or vendor drivers; the lab checklist owns
  those.
- **Agility from a .NET apphost** (M7, measured on the spine's day because the spine's WARP test and the debug layer behind the hard
  gate depend on it): if the device factory does not load the app's runtime, the OS runtime is used and named, and the job installs
  Windows' Graphics Tools optional feature for that runtime's debug layer; nothing this round needs a newer runtime than 24H2's.
- **The interim render-thread makes** are visible, counted and amber in preflight; wp3-d3d12-passes-2 removes them.
- **Binding gaps** (`PLAN.md` R7): a call TerraFX lacks is declared raw, with a layout golden, the way `ComSlots` is today.
